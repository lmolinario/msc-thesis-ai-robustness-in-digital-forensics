\chapter{Implementation and Experimental Setup}
\label{chap:implementation}
% ─────────────────────────────────────────────────────────────────────────────

This chapter documents the concrete implementation of the \gls{fairlab}
methodology introduced in Chapter~\ref{chap:methodology}. It describes the
preparation and freezing of the image corpus, deterministic data partitioning,
fold-aware proxy-model training, adversarial and anti-forensic artifact
generation, construction of the forensic evaluation bundle, normalization of
black-box software outputs, explainability analysis, and the controls used to
preserve artifact identity, provenance, integrity, and reproducibility.

The chapter reports how the protocol was instantiated and which technical
artifacts were produced. Quantitative outcomes and their operational
interpretation are reported separately in Chapter~\ref{chap:results}, preventing
implementation choices, software configurations, and data-management
procedures from being conflated with measured robustness.

Both evaluation levels operate on the same frozen source population. The
1\,000 clean binary images and 500 clean \gls{ood} images constitute the source
corpus, while 10\,000 adversarial and anti-forensic artifacts are derived
exclusively from the binary subset. The proxy models process manifest-linked
inputs and derived artifacts, whereas the selected black-box software systems
receive neutrally identified, byte-identical copies through the forensic
evaluation bundle. Equivalence between these views is verified through
\gls{sha256} digests.

\section{Experimental Workflow and Implementation Environment}
\label{sec:implementation-overview}
% ─────────────────────────────────────────────────────────────────────────────

phase produces explicit records or artifacts used by subsequent phases. The

At the repository level, the implementation is divided into functional
components. Dataset preparation, split generation, and bundle construction are
maintained under \codepath{datasets/}; perturbation manifests and reports under
\codepath{attacks/}; proxy architectures, checkpoints, and training records
under \codepath{models/}; proxy predictions and normalized black-box outputs
under \codepath{evaluation/}; commercial-tool documentation and sanitized
extracts under \codepath{forensic_tools/}; explainability scripts and artifacts
under \codepath{explainability/}; and consolidated metrics, reporting assets,
and validators under \codepath{results/}. The authoritative thesis source is
maintained under \codepath{docs/LatexThesis/}.

The implementation was managed through Python virtual environments and executed
across Windows PowerShell and Linux/Kali environments according to the
requirements of each stage. Black-box processing additionally required licensed
installations of the selected software systems. The repository-level
\codepath{requirements.txt} file defines the Python dependency set, including
the libraries used for data processing, image manipulation, proxy-model
training and inference, adversarial generation, source acquisition,
visualization, and explainability. PyTorch and Torchvision provide the
deep-learning framework, \texttt{open\_clip\_torch} supports the
\gls{clip}-based proxy model, and Captum supports the \gls{ig} workflow.

The code supports CPU and CUDA-enabled execution. Manifest inspection, output
normalization, metric validation, and reporting audits can be performed without
dedicated acceleration, whereas proxy-model training, iterative adversarial
generation, and explainability regeneration constitute the most computationally
demanding stages.

The repository is distributed as a research artifact rather than as a
self-contained software package or a byte-identical operating-system image.
Procedural reproducibility and artifact-level auditability are supported
through numbered scripts, frozen manifests, fold-aware checkpoints, prediction
tables, explicit parameters, integrity digests, validation reports, and
controlled experimental artifacts. The public repository provides the material
required for structural inspection, metric recomputation, reporting validation,
and audit, while the complete image corpora, exact frozen black-box input
bundle, and complete proprietary software exports remain subject to controlled
access.

\section{Dataset Preparation and Organization}

\subsection{Technical Preparation and Source Consolidation}
\label{subsec:implementation-dataset-preparation}
% ─────────────────────────────────────────────────────────────────────────────

The initial candidate pool was assembled from five source collections maintained
under \codepath{datasets/raw/}: a public Kaggle-based collection, the
specialized DeepFirearm corpus, open-web images, content acquired from Telegram
and YouTube, and material collected from non-indexed web sources. The
collections remained organized according to acquisition provenance, while
source names, directory structures, and inherited labels were retained only as
provenance information and were not used as final operational assignments.

Technical preparation was performed by
\codepath{datasets/scripts/prepared/08_build_prepared_dataset.py}. The script
processes the five configured source directories in a fixed order, recursively
enumerates supported image files, and constructs the unified candidate pool
under \codepath{datasets/prepared/final_pool/}. It does not perform semantic
annotation or final sample selection, which are handled by the human review
procedure described in
Section~\ref{subsec:implementation-human-review}.

Candidate discovery was restricted to files with the extensions
\texttt{.jpg}, \texttt{.jpeg}, \texttt{.png}, \texttt{.bmp},
\texttt{.webp}, \texttt{.tif}, and \texttt{.tiff}. Each file was opened and
structurally verified using Pillow. Images that could not be decoded or
verified were recorded as \texttt{unreadable\_image}, whereas images whose
width or height was below 300 pixels were excluded under the
\texttt{below\_min\_size} condition. Unexpected failures were recorded with
the corresponding exception type.

For every technically valid image, the script computed a \gls{sha256} digest
over the original file bytes. Exact-duplicate detection was performed globally
across all five source collections. Because the source directories and their
contents were processed deterministically, the first occurrence of each digest
was retained, while every subsequent occurrence was recorded as a discarded
duplicate and linked to the retained sample.

Accepted images were assigned stable identifiers following the format
\texttt{img\_00000001} and copied to
\codepath{datasets/prepared/final_pool/images/}. The original file extension
was preserved, and no resizing, recompression, or format conversion was
performed. After each copy operation, the destination file was hashed again and
compared with the source digest. A mismatch caused execution to terminate,
preventing modified, corrupted, or incomplete copies from entering the prepared
pool.

The resulting prepared pool contained 15\,321 technically valid and
byte-distinct images from 19\,769 candidate files. Of the remaining files,
3\,124 were excluded because they were unreadable, structurally invalid, or
below the minimum dimensional threshold, and 1\,324 were discarded as exact
duplicates.

The preparation stage generated four principal audit records:

\begin{itemize}
\item \codepath{datasets/prepared/final_pool/metadata.csv}, containing one
record for each retained image;

\item
\codepath{datasets/prepared/final_pool/reports/invalid_images.csv},
documenting technically excluded files and their exclusion reasons;

\item
\codepath{datasets/prepared/final_pool/reports/duplicates_discarded.csv},
linking each discarded duplicate to the retained sample and its
\gls{sha256} digest;

\item
\codepath{datasets/prepared/final_pool/reports/prepared_build_summary.json},
containing global and source-specific preparation statistics.
\end{itemize}

For each retained image, \texttt{metadata.csv} records the stable image
identifier, prepared filename and relative path, source group, source dataset,
original relative path and filename, \gls{sha256} digest, dimensions, file
size, extension, and technical-validity state. These fields preserve the
relationship between the prepared sample and its acquisition source.

The output of this stage is a technically validated and globally deduplicated
candidate pool, not the final experimental dataset. Reduction of the
15\,321-image prepared pool to the frozen experimental corpus was performed
only through the human review and final-selection procedure described in the
following subsection.

\subsection{Review Documentation and Human-in-the-Loop Validation}
\label{subsec:implementation-human-review}
% ─────────────────────────────────────────────────────────────────────────────

The transition from technical preparation to semantic assessment was
implemented through the full review manifest generated by
\codepath{datasets/scripts/prepared/09_generate_review_manifest_full.py} and
stored at
\codepath{datasets/prepared/manifests/review_manifest_full.csv}. The script
creates one review record for each of the 15\,321 images retained in the
prepared pool.

Identity, provenance, and technical metadata are propagated from
\codepath{datasets/prepared/final_pool/metadata.csv}, including the stable image
identifier, \gls{sha256} digest, prepared path, source dataset, original source
path, dimensions, file size, extension, and technical-validity state. The
digest is not recomputed because it was already established and verified during
technical preparation.

The manifest extends these fields with separate columns for semantic assessment
and review-state management. It also reserves fields for optional automatic
prelabeling. These fields were initialized without model outputs, and
\texttt{prelabel\_status} was set to \texttt{pending}. No automatic score,
model prediction, or class suggestion was used to determine the final human
assignments.

Manual assessment was performed through the interactive application implemented
by
\codepath{datasets/scripts/final/10_manual_selection_protocol_reviewer.py}.
At its first execution, the application initializes the persistent working
database
\codepath{datasets/final/manifests/manual_selection_protocol_db.csv}
from the full review manifest. Subsequent executions resume the existing
database and the previously saved session state.

The interface presents images in batches of ten arranged in a five-column grid
and supports mouse- and keyboard-based assignment to \texttt{weapon},
\texttt{non\_weapon}, and \texttt{ood}, together with the review-only
\texttt{exclude} disposition. Additional controls support zooming, page
navigation, undo operations, explicit assignment removal, saving, and
resumption.

Two operating modes were implemented:

\begin{itemize}
\item in \texttt{review\_pending} mode, the reviewer inspects pending images
from a selected source and assigns an operational class or exclusion
disposition;

\item in \texttt{review\_selection} mode, the reviewer re-examines images
already assigned to one selected experimental group, optionally filters them by
source, and may remove an unsuitable assignment by returning the sample to the
pending pool.
\end{itemize}

The second mode provides an explicit quality-control mechanism for reviewing
the selected corpus without treating an initial assignment as immutable.

Figure~\ref{fig:implementation-human-review-interface} documents the
interactive environment used during the human-in-the-loop selection process.

The interface displays the operational criteria established in
Chapter~\ref{chap:methodology}. Clear and realistic firearm-related content is
assigned to \texttt{weapon}; realistic and interpretable negative content is
assigned to \texttt{non\_weapon}; borderline, synthetic, replica-like,
strongly degraded, anomalous, or otherwise out-of-task content is assigned to
\texttt{ood}; and unusable or irrelevant content is assigned to
\texttt{exclude}. Borderline samples are not forced into either binary class.

The application enforces global targets of 500 images for each of the
\texttt{weapon}, \texttt{non\_weapon}, and \texttt{ood} groups. Once a target
is reached, further assignments to that group are blocked until an existing
selection is removed. Soft source-level targets of 100 samples per group and
source are displayed as advisory balancing alerts and do not constrain reviewer
decisions.

The implemented procedure is therefore target-driven rather than an exhaustive
semantic annotation of the prepared pool. The global targets define the final
sample counts, while the source-level alerts support composition control
without requiring equal representation from every source.

Each assignment, clearing, removal, or undo operation records the timestamp,
reviewer identifier, session mode, source filter, image identifier, source
dataset, preceding assignment, new assignment, and review state in
\codepath{datasets/final/reports/manual_selection_log.csv}. The current
position, operating mode, active filters, last action, and recent undo history
are stored in
\codepath{datasets/final/reports/manual_selection_state.json}.

The application automatically saves the working database, updates the session
state, and regenerates the principal output records after review actions.
Existing CSV files are backed up with timestamped names before replacement, and
temporary files followed by atomic replacement are used to reduce the risk of
partial or corrupted writes.

The final working database contained 1\,500 reviewed records and 13\,821

1\,000-image binary subset.

The implemented process separates technical file validity, semantic suitability
for the experimental task, and final inclusion in the frozen corpus. The final
dataset composition and the consistency controls applied to its canonical
manifests are described in
Section~\ref{subsec:implementation-dataset-freezing}.

checks. In the frozen execution,
\texttt{final\_1500\_exact} and
\texttt{adversarial\_subset\_1000\_exact} were both set to
\texttt{true}, confirming the expected sizes of the complete corpus and binary

Freezing was implemented at the manifest level. After the target counts and
consistency checks had been satisfied, the exported manifests became the
canonical inputs for all downstream stages. Subsequent scripts consume their
image identifiers, paths, assignments, source information, and
\gls{sha256} digests without modifying the human-reviewed decisions.

Any replacement, removal, or reassignment of a frozen sample therefore requires
regeneration of all dependent partitions, derived artifacts, bundle records,
predictions, and metrics. An isolated downstream modification would no longer
correspond to the canonical dataset definition.

The frozen manifests define which images belong to the experiment and their
reference operational assignments. The deterministic generation of the binary
folds and the separate \gls{ood} evaluation manifest is described in
Section~\ref{subsec:implementation-split-generation}.

\subsection{Dataset Partitioning and Fold Generation}
\label{subsec:implementation-split-generation}
% ─────────────────────────────────────────────────────────────────────────────

\codepath{datasets/final/manifests/manual_selection_final_1500.csv} and the
balanced binary manifest
\codepath{datasets/final/manifests/manual_selection_adversarial_subset.csv}.

Before generating any output, the script verifies the presence of the required

condition is not satisfied.

secondary objective because the source distributions of the two classes are
not uniform.

Fold assignment is performed independently within each class--source stratum.
The records in each stratum are shuffled using a deterministic pseudo-random
generator initialized from the global seed, class assignment, and source
identifier. Each sample is then assigned to a fold that has not reached its
class quota. Among eligible folds, the implementation selects the fold with the
lowest existing count for the same class and source, followed by the lowest
current class occupancy and the fold identifier as deterministic tie-breaking
criteria.

\subsection{Training Configuration and Fold-Aware Checkpoints}
\label{subsec:implementation-training}
% ─────────────────────────────────────────────────────────────────────────────

The proxy models were trained through a fold-aware leave-one-fold-out
procedure. For each architecture and target fold, the target fold was reserved
as the held-out evaluation partition, while the remaining four folds were used
to construct the training and internal validation sets. No checkpoint was
therefore trained on the fold on which it was subsequently evaluated or used
for fold-matched model-dependent adversarial generation.

For each architecture--fold run, the four non-held-out folds contained 800
images. A deterministic stratified split reserved 15\% of these records for
internal validation, independently within each binary class. The resulting
partitions contained:

\begin{itemize}
\item 680 images for parameter optimization;
\item 120 images for internal validation;
\item 200 images in the untouched held-out fold.
\end{itemize}

The training--validation split was generated using seed 42. Records were
separated by class, shuffled deterministically within each class, and
recombined, preserving equal representation of \texttt{weapon} and
\texttt{non\_weapon}. The held-out fold was not used for parameter updates or
checkpoint selection.

Class weighting was not applied because the training and validation partitions
remained balanced between the two supervised classes. Parameter updates used

Before training, the script validates the complete clean-fold manifest by
checking:

\begin{itemize}
\item the presence of the required columns;
\item the exclusive use of the two accepted binary assignments;
\item the presence of all five expected folds;
\item the exact count of 100 images per class and fold;
\item the uniqueness of the image identifiers;
\item the availability of every referenced image file;
\item the correspondence between each file and its recorded
\gls{sha256} digest.
\end{itemize}

Execution terminates when an image is missing or its digest does not match the
split manifest, preventing a checkpoint from being produced from a dataset
state inconsistent with the frozen partition definition.

The fixed seed is propagated to the Python standard-library pseudo-random
generator, NumPy, PyTorch, and all available CUDA devices. The implementation
disables cuDNN benchmark-based algorithm selection and requests deterministic
cuDNN behavior. These controls reduce variation from the principal
pseudo-random sources, although exact numerical reproduction may still depend
on the software and hardware environment.

The execution device may be selected as \texttt{cpu} or \texttt{cuda}, or
resolved automatically according to CUDA availability. Device selection does
not modify the frozen folds or declared optimization parameters. The preserved
complete-suite execution log records CPU-based training for the reported
checkpoints.

During each epoch, the script records training loss, training accuracy,
validation loss, and validation accuracy. All 10 epochs are executed; no early
stopping is applied. The checkpoint is overwritten whenever the current
validation accuracy is greater than or equal to the best value observed during
the preceding epochs. When the same maximum accuracy occurs in multiple
epochs, the latest qualifying checkpoint is retained. The held-out fold remains
excluded from this selection procedure.

\codepath{models/checkpoints/<model_name>/<fold>.pt}. The complete suite
contains:

\begin{equation}

\times
5\ \text{held-out folds}
=
15\ \text{checkpoints}.
\end{equation}

For \gls{resnet18} and \gls{efficientnetb0}, each checkpoint contains the trained model

checkpoint was saved. For the \gls{clip}-based proxy, the checkpoint stores the
trained binary-head parameters and identifies the external ViT-B/32
architecture and pretrained weights required to reconstruct the frozen visual

\subsection{Adversarial Attack Implementation}
\label{subsec:implementation-adversarial}
% ─────────────────────────────────────────────────────────────────────────────

Adversarial generation was implemented through
\codepath{datasets/scripts/attacks/14_generate_adversarial_attacks.py}, using
\codepath{datasets/splits/manifests/clean_folds_manifest.csv} as the canonical
input. The script generates one perturbed artifact from each of the 1\,000
clean binary images for every selected condition.

The frozen suite comprises four model-dependent attacks---\gls{fgsm}, One
Pixel, Sigma-Zero, and SuperDeepFool---and the model-agnostic Color Shift
condition. FGSM, Sigma-Zero, and SuperDeepFool require white-box access to
gradients or decision-boundary information. One Pixel uses score-based access
to the output probabilities of the target proxy model. Color Shift does not
query a model and is therefore recorded as an adversarial-style condition
rather than as a white-box or score-based attack.

\gls{efficientnetb0} was used as the primary proxy target for all model-dependent
conditions. For each source image, the generator reads the fold identifier from
the clean manifest and loads the corresponding checkpoint from
\codepath{models/checkpoints/efficientnet_b0/<fold>.pt}. Because that checkpoint
was trained while excluding the associated fold, the source image was not part
of the checkpoint's training data.

binary assignments, uniqueness of image identifiers, availability of all clean
inputs, and correspondence of their \gls{sha256} and \gls{md5} values with the
clean-fold manifest. Model-dependent conditions additionally require the

\paragraph{\gls{fgsm}.}

The FGSM implementation preprocesses the clean image according to the
\gls{efficientnetb0} normalization and computes the loss gradient with respect to
the reference operational assignment. The normalized gradient is converted to
pixel space before applying the perturbation:

\begin{equation}
\mathbf{x}_{\mathrm{adv}}
=
\operatorname{clip}_{[0,1]}
\left(
\mathbf{x}
+
\epsilon\,
\operatorname{sign}
\left(
\nabla_{\mathbf{x}}
\mathcal{L}(\mathbf{x},y)
\right)
\right),
\end{equation}

where \(y\) is the encoded reference operational assignment and
\(\epsilon = 8/255\). The adversarial tensor is converted to RGB and stored as
a lossless PNG file. The generation record includes clean and adversarial predictions, maximum
predicted-class probability, reference-class probability, and pixel-space
perturbation measurements.

\paragraph{One Pixel.}

The One Pixel implementation uses Differential Evolution to optimize the
coordinates and RGB value of one modified pixel. Each candidate is represented
by
\(\boldsymbol{\theta}=(u,v,r,g,b)\), where \((u,v)\) identifies the pixel and
\((r,g,b)\) specifies its replacement value. Let
\(T(\mathbf{x};\boldsymbol{\theta})\) denote the corresponding transformed
image. The implemented score-based objective is:

\[
\begin{aligned}
\min_{\boldsymbol{\theta}}\quad &
p_y\!\left(T(\mathbf{x};\boldsymbol{\theta})\right)
\\
\text{subject to}\quad &
\left|
\left\{
(i,j):
T(\mathbf{x};\boldsymbol{\theta})_{ij}
\neq
\mathbf{x}_{ij}
\right\}
\right|
\leq 1.
\end{aligned}
\]

where \(p_y(\cdot)\) is the probability assigned by the fold-specific target
model to the reference class \(y\). The constraint applies to pixel locations,
since all three channels of the selected pixel may change jointly.

A deterministic image-specific seed is derived from the base seed, condition
name, and stable image identifier through \gls{sha256}. Optimization terminates
early when a candidate changes the prediction relative to the reference
assignment. Otherwise, the best candidate identified before the iteration
limit is exported.

\paragraph{Sigma-Zero.}

Sigma-Zero was integrated through the reference implementation exposed by the
\texttt{adversarial-library} project, pinned to commit
\nolinkurl{b14f81a3e1c414a573b969b402c99e65bfe2ca33}. The FAIRLab adapter
invokes the reference function directly rather than reimplementing it.

The reference function operates on unnormalized tensors in \([0,1]\). The
adapter therefore converts the model-normalized input to pixel space and wraps
the \gls{efficientnetb0} checkpoint so that model normalization is reapplied before
logit computation. The untargeted sparse-perturbation objective can be
summarized as:

\[
\begin{aligned}
\min_{\mathbf{x}_{\mathrm{adv}} \in [0,1]^d}\quad &
\left\|
\mathbf{x}_{\mathrm{adv}}-\mathbf{x}
\right\|_0
\\
\text{subject to}\quad &
\operatorname*{arg\,max}_{k}
f_k(\mathbf{x}_{\mathrm{adv}})
\neq
y.
\end{aligned}
\]

where \(f_k(\cdot)\) is the logit associated with class \(k\). The discrete
objective is approximated through the iterative optimization and adaptive
threshold procedure configured in
Table~\ref{tab:implementation-adversarial-parameters}.

\paragraph{SuperDeepFool.}

SuperDeepFool was implemented internally from the published
\(\mathrm{SDF}(\infty,1)\) procedure and does not vendor or copy the official
repository. The implementation first performs DeepFool-style iterations to
identify an adversarial boundary point and then applies a projection based on
the gradient difference between the boundary and reference classes.

The frozen untargeted objective is:

\[
\begin{aligned}
\min_{\boldsymbol{\delta}}\quad &
\left\|
\boldsymbol{\delta}
\right\|_{\infty}
\\
\text{subject to}\quad &
\operatorname*{arg\,max}_{k}
f_k(\mathbf{x}+\boldsymbol{\delta})
\neq
y,
\\
&
\mathbf{x}+\boldsymbol{\delta}
\in [0,1]^d.
\end{aligned}
\]

At a boundary point \(\mathbf{x}_{b}\), the projection uses:

\begin{equation}
\mathbf{w}_{b}
=
\nabla_{\mathbf{x}} f_{k_b}(\mathbf{x}_{b})
-
\nabla_{\mathbf{x}} f_{y}(\mathbf{x}_{b}),
\end{equation}

where \(k_b\) is the boundary class. If the projected point remains
adversarial, it is retained; otherwise, the implementation falls back to the
adversarial boundary point. The manifest records iteration counts, convergence
status, and whether the projection preserved adversariality.

\paragraph{Color Shift.}

Color Shift modifies the RGB channels in the original image space and then
applies the configured saturation and contrast factors. No model is queried
during generation, and the generation-time attack-success field is marked as
not applicable. JPEG quality 95 is used because controlled recompression forms
part of the condition. The target-model field is set to
\texttt{model\_agnostic}, and checkpoint-related fields are left empty or
marked as not applicable.

Model-dependent outputs follow the pattern
\codepath{attacks/adversarial/<attack_name>/<target_model>/<fold>/<label>/}.
Color Shift uses the same structure with
\texttt{target\_model = model\_agnostic}. Generated filenames follow the pattern
\codepath{<image_id>__<attack_name>__<target_model>.<extension>}.

Each condition produces 1\,000 artifacts, comprising 500
\texttt{weapon} and 500 \texttt{non\_weapon} samples, with 200 artifacts per
fold. The complete stage therefore produces:

\begin{equation}

\times
1\,000\ \text{binary images}
=
5\,000\ \text{perturbed artifacts}.
\end{equation}

\subsection{Anti-Forensic Transformation Implementation}
\label{subsec:implementation-antiforensic}

Anti-forensic artifact generation was implemented through
\codepath{datasets/scripts/attacks/13_generate_anti_forensic_attacks.py}, using
\codepath{datasets/splits/manifests/clean_folds_manifest.csv} as the canonical
input. Each transformation was applied to all 1\,000 clean binary images,
comprising 500 \texttt{weapon} and 500 \texttt{non\_weapon} samples. The 500
clean \gls{ood} inputs remained outside this stage.

The frozen suite comprises five deterministic and model-agnostic
transformations: \gls{jpegrecompression}, \gls{resampleresize},
\gls{gaussianblur}, \gls{histogrammodification}, and
\gls{contraststretching}. These conditions do not access model gradients,
logits, probabilities, or checkpoints. The reference operational assignment of
each source image is propagated unchanged to the corresponding transformed
artifact.

Before generation, the script verifies the required manifest fields, accepted
binary assignments, and uniqueness of image identifiers. It also checks the
existence of every clean input and recomputes its \gls{sha256} and \gls{md5}
digests. Missing files or mismatches between the recorded and computed values
terminate execution. SHA-256 remains the primary integrity control, whereas
MD5 is retained as an auxiliary interoperability identifier.

Each source image is opened with Pillow, corrected according to its embedded
orientation through an EXIF transpose operation, and converted to RGB before
the transformation-specific operation is applied. All generated artifacts are
stored as \gls{jpeg} files. The dedicated recompression condition uses quality
70, while the remaining transformations use quality 95 to limit additional
encoding effects beyond the principal operation.

\paragraph{\gls{jpegrecompression}.}

The recompression condition does not apply an explicit spatial or tonal
operation before serialization. The RGB image is re-encoded at JPEG quality 70,
introducing a controlled lossy-compression condition through quantization and
block-based encoding effects.

\paragraph{\gls{resampleresize}.}

For an image with original dimensions \(W \times H\), the intermediate
dimensions are computed as:

\begin{equation}
W_{\mathrm{down}}
=
\max\left(1,\operatorname{round}(0.5W)\right),
\qquad
H_{\mathrm{down}}
=
\max\left(1,\operatorname{round}(0.5H)\right).
\end{equation}

The image is first resized to
\(W_{\mathrm{down}} \times H_{\mathrm{down}}\) and then restored to
\(W \times H\). Both operations use bicubic interpolation. The output
therefore retains the original spatial dimensions while incorporating the
information loss introduced by the intermediate downsampling and
reconstruction.

\paragraph{\gls{gaussianblur}.}

The Gaussian Blur condition applies a radius of 1.5 to suppress high-frequency
spatial detail. Image dimensions remain unchanged before final JPEG
serialization.

\paragraph{\gls{histogrammodification}.}

Histogram Modification is implemented through
\texttt{ImageOps.equalize}, which performs histogram equalization on the RGB
image channels. The same deterministic operation is applied to every sample,
without image-specific thresholds or model-derived information.

\paragraph{\gls{contraststretching}.}

Contrast Stretching is implemented through
\texttt{ImageOps.autocontrast} with a cutoff value of 1.0. The operation
remaps the remaining intensity range after excluding the configured proportion
of extreme values, modifying global contrast while retaining the original
image dimensions.

filename pattern:

\codepath{<image_id>__<transformation>.jpg}.

The hierarchy preserves the deterministic fold and binary reference assignment
of the source image. The transformation name remains separate from the
reference assignment, and no relabeling is performed during generation.

Each transformation produces 1\,000 files, comprising 500
\texttt{weapon} and 500 \texttt{non\_weapon} artifacts, with 200 files per
fold. The complete stage therefore produces:

\times
1\,000\ \text{binary images}

\end{equation}

This separation prevents experiment-specific descriptors from being disclosed
directly through the imported directory hierarchy or file names and limits the
analyst's access to the hidden control mapping during the initial evaluation.
It does not conceal the visual content of an image, perceptible perturbation
effects, or information that may remain embedded within the image file itself.

Every logical item was assigned a sequential identifier from
\texttt{bundle\_000001} through \texttt{bundle\_011500}. Blind file names
contain only this identifier and the source file's format extension, as in
\texttt{bundle\_000001.jpg} or \texttt{bundle\_000002.png}.

The identifiers are neutral and deterministic rather than semantically
descriptive. The bundle builder does not claim to randomize the logical item
ordering; blindness is achieved through neutral naming, flat-path
materialization, exclusion of the internal mapping, and separation of control
metadata from the imported directory.

The source file format is retained, with the corresponding extension
normalized to lowercase. The builder performs no conversion, resizing,
recompression, or metadata sanitization. Files are copied without modifying
their byte content.

Blind file names are checked against a list of forbidden semantic and
experimental tokens, including binary assignment values, \gls{ood}
indicators, perturbation names, fold identifiers, and proxy-model names. The
file stem must also correspond exactly to the assigned bundle identifier.

The structured audit view reproduces the experimental hierarchy separately.
Clean inputs are organized by fold and reference assignment; \gls{ood} inputs
are maintained under the dedicated evaluation branch; adversarial artifacts are
organized by condition, target model, fold, and reference assignment; and
anti-forensic artifacts are organized by transformation, fold, and reference
assignment. This view supports internal verification and must not be imported
into the black-box software systems.

input file name, the sample type, the perturbation family and name, the target
proxy model when applicable, the experimental fold, the reference operational
assignment, and the source dataset.

originating manifest and source file path, and the corresponding blind and
structured bundle paths. In addition, it records the original,
manifest-reported, and materialized-file hashes, the result of their comparison,
and the relevant file metadata, including size, extension, layout, and creation
timestamp.

This mapping reconnects a black-box result associated with a neutral file name
to its source image, reference assignment, fold, and experimental condition.

as described in

The prompt set was defined before the frozen evaluations and was not modified
on the basis of the observed retrieval results. The broader term
\texttt{weapon} was intentionally excluded because the experimental positive
class was firearm-oriented rather than a general category encompassing all
types of weapons.

Each prompt was executed separately under the semantic-distance limits 20, 50,
and 80. This procedure produced:

\begin{equation}
8\ \text{fixed prompts}
\times
3\ \text{distance settings}
=
24\ \text{prompt-level export files}.
\end{equation}

The export names follow the pattern
\texttt{excire\_<prompt>\_distance<limit>.csv}. For file-system
compatibility, the multiword prompt \texttt{assault rifle} is represented as
\texttt{assault\_rifle} in the corresponding file name. The prompt and
distance configuration can therefore be reconstructed deterministically from
each export name.

The Excire outputs are retrieval hit lists rather than complete classification
tables. Each file contains the paths of the images returned for one prompt
under one distance setting, generally as a headerless list with one path per
line. An image may occur in multiple files when it is retrieved by more than
one prompt. Consequently, the raw hit totals reported in
Table~\ref{tab:implementation-excire-configuration} represent prompt-level
memberships and may exceed the number of unique positive images.

The normalizer reads each hit list deterministically, removes surrounding
quotation marks, ignores an optional path-oriented header, extracts the file
name from each exported path, and matches it against the neutral file names in
the canonical bundle manifest. The original local directory component does not
contribute to the experimental decision.

For a bundle image \(x\), semantic-distance setting \(d\), and frozen prompt
set \(\mathcal{P}\), the operational rule is:

\[
\texttt{weapon\_detected}(x;d)
=
\begin{cases}
\texttt{true},
&
\text{if }
\exists p \in \mathcal{P}:
\operatorname{retrieved}(x,p,d),
\\
\texttt{false},
&
\text{otherwise}.
\end{cases}
\]

The corresponding common normalized prediction is \texttt{weapon} when
\texttt{weapon\_detected = true} and \texttt{non\_weapon} otherwise.
Images absent from all eight hit lists under the same distance setting are
completed against the canonical 11\,500-item bundle as operational negative
decisions.

This rule is an operational recoding of semantic-retrieval membership. It does
not imply that \gls{excirefoto2025} internally performs binary
\texttt{weapon}/\texttt{non\_weapon} classification. Similarly, the
software-specific distance limits must not be interpreted as calibrated
probabilities, numerical confidence values, or thresholds directly comparable
with those of another system.

The D20, D50, and D80 settings were retained as separate system configurations
throughout normalization and metric computation. Their retrieval results were
not combined into a single Excire decision. Each setting produced one complete
table containing exactly 11\,500 normalized predictions.

For auditability, each normalized record preserves the semantic-distance limit,
the complete frozen prompt set, and the number and names of the prompts that
retrieved the image. It also includes one binary membership indicator for each
of the eight prompts, together with the corresponding bundle identifier, neutral
input file name, and \gls{sha256} and \gls{md5} values.

The record further retains the sample type, perturbation family, experimental
condition, fold, reference operational assignment, source dataset, and
source-image identifiers, as well as the resulting
\texttt{weapon\_detected} and normalized-prediction fields.

Preserving the individual prompt memberships prevents the union operation from
discarding relevant retrieval information. Two images may receive the same
positive normalized decision even when one is retrieved by a single prompt and
the other by several semantically related prompts.

After the union and bundle-completion procedures, every configuration contained
exactly one normalized prediction for each of the 11\,500 bundle items, and no
bundle item remained unmatched. The three configurations therefore produced
34\,500 normalized Excire records in total. Complete matching establishes
output coverage but does not establish the correctness of the resulting
operational decisions.

The 24 original CSV files contained local Windows paths in addition to the
neutral bundle file names. They were therefore retained as controlled-access
artifacts and excluded from the public repository. Their expected local
location is
\codepath{forensic_tools/excire_foto_2025/raw_exports/}.

associated percentage values correspond to probabilities comparable across
images, categories, or software systems.

The original report contained 11\,829 image rows. Of these, 11\,500 were
matched to the complete forensic evaluation bundle, whereas 329 did not
correspond to bundle items. The non-bundle records were preserved in the local
unmatched-output artifact and summarized by tool in the public normalization
report. They were excluded from the canonical bundle-level prediction table
and from the quantitative robustness analysis.

The resulting canonical Cellebrite output contains one matched decision for
each of the 11\,500 bundle items. Complete bundle coverage confirms that an
observable exported decision was available for every experimental item but
does not establish classification correctness.

The matching procedure associates report records with the canonical bundle
using available \gls{sha256} values, followed by \gls{md5}, the exact neutral
bundle file name, or a bundle file name embedded within an exported path or
text field. The matching method is preserved in each normalized record.

For every successfully matched record, the normalized representation retains the
\texttt{bundle\_id}, neutral input file name, matching method, and matched
state, together with the available \gls{sha256} and \gls{md5} values. It also
records whether the item is clean, \gls{ood}, or perturbed, as well as the
corresponding perturbation family and condition, experimental fold, reference
operational assignment, source dataset, and original and generated image
identifiers.

In addition, the normalized record preserves the original observable
\texttt{Classifications} value, the resulting normalized binary decision, and
the reason supporting the applied mapping.

The complete XLSX report also contained file-system, evidence, and case-export
information not required for the classification mapping. Because these fields
may expose local paths or case-specific metadata, the raw report is managed as
a controlled-access artifact and is excluded from the public repository. Its
expected local location is
\codepath{forensic_tools/cellebrite_inseyets/raw_exports/%
FAIRLAB_CELLEBRITE_INSEYETS_RUN_01/}.

The public repository retains the sanitized prediction extract
\codepath{forensic_tools/cellebrite_inseyets/public_extracts/%
cellebrite_classifications_extract.csv}.
It contains the neutral bundle identifiers, experimental-condition fields,
observable classification values, and normalized decision fields for all
11\,500 matched bundle items. Local paths and the 329 non-bundle report rows are
not included in this public extract.

The run registry, software-version log, export audit, normalization summary,
public-extract validation, canonical normalized prediction table, and metric
artifacts provide the remaining records required to inspect the frozen
configuration and verify the equivalence between the controlled raw report and
the sanitized public representation.

The common matching, normalization, completeness, and deduplication procedures
applied across the selected black-box software systems are described in
Section~\ref{subsec:implementation-normalization}. The resulting behavior of
\gls{cellebriteinseyets} is reported in
Section~\ref{subsec:results-cellebrite}.

\subsection{Output Matching and Normalization}
\label{subsec:implementation-normalization}
% ─────────────────────────────────────────────────────────────────────────────

The heterogeneous outputs produced by the selected black-box software systems
were converted into a common sample-level representation through the canonical
entry point
\codepath{evaluation/scripts/19_normalize_forensic_ai_tool_predictions.py}.
The entry point acts as a controlled-output wrapper around the preserved
normalization implementation. It adds overwrite protection, field
minimization, explicit preservation of unmatched records, complete version
metadata, strict JSON serialization, and optional generation of separate
per-configuration prediction files.

The normalization implementation reads the controlled-access exports associated
with the frozen runs and associates their observable records with the forensic
evaluation bundle. Its primary bundle inputs are
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_manifest.csv}
and
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}.

These records provide the association among neutrally identified software-input
files, cryptographic hashes, reference operational assignments, folds, sample
types, perturbation conditions, source-image identifiers, and generated-image
identifiers. Reference assignments and experimental metadata are joined to the
observable software outputs only after export and were not supplied to the
evaluated systems during their analysis.

The normalization pipeline processes four software families while retaining the
three \gls{excirefoto2025} semantic-distance settings as distinct operational
configurations:

\begin{itemize}
\item \texttt{magnet\_axiom};
\item \texttt{griffeye};
\item \texttt{excire\_foto\_2025\_d20};
\item \texttt{excire\_foto\_2025\_d50};
\item \texttt{excire\_foto\_2025\_d80};
\item \item \item \texttt{cellebrite\_inseyets}.
\end{itemize}

Each configuration is evaluated against the same 11\,500-item bundle. The
complete normalized population therefore contains:

\begin{equation}
6\ \text{configurations}
\times
11\,500\ \text{bundle items}
=
69\,000\ \text{matched decisions}.
\end{equation}

\paragraph{Bundle indexing and record matching.}

When the bundle metadata is loaded, the implementation constructs three lookup
indexes:

\begin{enumerate}
\item a \gls{sha256}-based index;
\item an \gls{md5}-based index;
\item a neutral file-name index.
\end{enumerate}

For conventional row-oriented exports, each parsed software record is matched
according to the following priority:

\[
\begin{aligned}
\texttt{SHA-256}
&\succ \texttt{MD5} \\
&\succ \texttt{exact file name} \\
&\succ \texttt{file name embedded in an exported path or text field}.
\end{aligned}
\]

The selected matching method is retained in the normalized record. This permits
subsequent verification of whether an association was established through the
primary cryptographic identifier or through a fallback identifier exposed by
the software export.

Hash values are normalized before comparison by removing separators and
non-hexadecimal formatting characters. Exported paths are reduced to their base
file names before lookup so that differences between Windows paths and
repository-relative paths do not prevent association with the neutral bundle
files.

The Griffeye export is filtered before matching to exclude unallocated-space,
system-file, and other non-bundle records. The Excire workflow instead requires
a bundle-completion procedure because its exports contain only the images
retrieved by each semantic query. Neutral file names found in the eight
prompt-level hit lists are associated with bundle items, and the union of the
retrieval results is subsequently completed against the full bundle manifest.
This produces an explicit operational decision for every bundle item, including
images absent from all prompt exports.

\paragraph{Controlled normalized schema.}

During controlled local execution, the normalized representation separates
software-observable information from the reference assignments and experimental
metadata recovered from the bundle. Its principal fields include
\texttt{tool\_name}, \texttt{bundle\_id}, \texttt{matched}, and
\texttt{match\_method}, together with \texttt{sample\_type},
\texttt{attack\_family}, \texttt{attack\_name}, and
\texttt{attack\_target\_model}. The record also preserves the experimental
\texttt{fold}, \texttt{final\_label}, \texttt{source\_dataset},
\texttt{original\_image\_id}, and \texttt{generated\_image\_id}, as well as
the neutral input file name and the available \gls{sha256} and \gls{md5}
values.

The original software-observable tag, classification, bookmark, or
prompt-membership information is retained alongside
\texttt{weapon\_detected}, \texttt{normalized\_prediction}, and
\texttt{mapping\_reason}. When the reference operational assignment is
\texttt{weapon} or \texttt{non\_weapon}, the normalized representation also
includes binary correctness, false-negative, and false-positive indicators.

The literal field name \texttt{final\_label} is retained because it belongs to
the implemented schema. Semantically, its value represents the reference
operational assignment inherited from the frozen bundle.

Software-specific information is preserved in dedicated fields rather than
being discarded after binary recoding. These fields include the original AXIOM
tags, Cellebrite classifications, Excire distance limit and per-prompt
membership indicators, and the primary and secondary Griffeye bookmarks.

For records whose reference operational assignment is \texttt{ood}, the binary
correctness, false-negative, and false-positive fields remain undefined. An
\gls{ood} input is not treated as either a positive or negative binary reference
instance. Its normalized detection state is preserved separately for
calculation of the \gls{ood} weapon-flag rate.

\paragraph{Deduplication and completeness.}

The normalizer supports deterministic consolidation to a single row for each
normalized-configuration and bundle-identifier pair. When multiple matched
records refer to the same pair, the consolidated decision follows a fixed
precedence rule: it is set to \texttt{true} if at least one row contains a
positive decision; otherwise, it is set to \texttt{false} if at least one row
contains an explicit negative decision. If neither condition is satisfied, the
consolidated decision is assigned as \texttt{unknown}.

The consolidation procedure preserves the combined export references, row
numbers, observable labels, mapping reasons, and contributing-row count. When
multiple numerical values are exposed by the same software for the consolidated
records, the maximum value may be retained as part of the original observable
information. It is not converted into a cross-system calibrated confidence
measure, and no numerical confidence is fabricated for systems that do not
expose one.

Unmatched records are excluded from the canonical matched population because
they do not correspond to official bundle items. They are preserved separately
in the controlled local output and summarized in the public normalization
report.

After the preliminary exclusion of the 553 non-bundle Griffeye records, the
normalization workspace contained 69\,329 candidate records. This population
comprised 69\,000 matched bundle-level decisions and 329 unmatched Cellebrite
report records:

\begin{equation}
69\,329
-
329
=
69\,000\ \text{matched decisions}.
\end{equation}

Deduplication was enabled in the frozen execution. The matched population
already contained one decision for every configuration--bundle pair, and its
size therefore remained 69\,000 rows after consolidation. Every configuration
covered all 11\,500 bundle items, and no matched decision remained in the
\texttt{unknown} state.

Complete coverage establishes the availability of an observable and matched
decision for every bundle item. It does not establish classification
correctness.

\section{Metric Computation and Explainability Implementation}

\subsection{Metric Computation and Evaluation Artifacts}
\label{subsec:implementation-metrics}
% ─────────────────────────────────────────────────────────────────────────────

Proxy-model outputs and normalized black-box software decisions were processed
through two separate computational pipelines. This separation preserves the
distinction between predictions obtained from fully accessible models and
operational decisions reconstructed from observable commercial-software
exports.

Proxy-model predictions and metrics were generated through
\codepath{evaluation/scripts/15_evaluate_proxy_models.py}. Black-box software
metrics were generated as part of the normalization pipeline implemented
through
\codepath{evaluation/scripts/19_normalize_forensic_ai_tool_predictions.py}.

Both pipelines use the same binary reference classes:

\[
\text{positive class}
=
\texttt{weapon},
\qquad
\text{negative class}
=
\texttt{non\_weapon}.
\]

The \gls{ood} branch is handled separately and does not contribute to the
denominators of binary accuracy, precision, recall, F1-score, \gls{fpr}, or
\gls{fnr}.

\paragraph{Proxy-model prediction generation.}

The proxy-model evaluation pipeline consumes the clean-fold manifest, the
separate \gls{ood} evaluation manifest, the five canonical
adversarial-generation manifests, the anti-forensic transformation manifest,
and the 15 fold-specific proxy-model checkpoints.

The public evaluation entry point wraps the preserved implementation with
additional integrity controls. Before inference, it verifies that the loaded
population contains exactly 1\,000 clean binary inputs, 500 \gls{ood} inputs,
5\,000 adversarial artifacts, and 5\,000 anti-forensic artifacts. Manifest
discovery is restricted to the five frozen adversarial conditions rather than
accepting every file matching a generic naming pattern.

The wrapper verifies the existence and manifest-recorded \gls{sha256} value of
every evaluated image. It also recomputes and validates the \gls{sha256} digest
of each of the 15 checkpoints against
\codepath{models/model_registry.json}. Missing inputs, digest mismatches, or
inference errors terminate the canonical execution.

A run using fewer than all three architectures, a limited input population, or
a single-fold \gls{ood} mode cannot write to the canonical output locations.
Such partial executions require an explicit diagnostic output directory.

Each clean or perturbed binary sample is evaluated using the checkpoint
associated with its assigned fold. Consequently, the checkpoint used for
prediction was trained while excluding the fold containing the corresponding
source image.

For each evaluated input, the implementation records the evaluated architecture
and fold-specific checkpoint, together with whether the sample is clean,
\gls{ood}, or perturbed. It also preserves the perturbation family, condition,
and attack target model, as well as the original and generated image
identifiers, the assigned fold, the reference operational assignment, the image
path, and the recomputed \gls{sha256} and \gls{md5} values.

The resulting evaluation record includes the predicted class, the maximum
predicted-class probability, and the probabilities assigned to
\texttt{weapon} and \texttt{non\_weapon}. For binary samples, it additionally
stores the probability assigned to the reference class, together with the
correctness state and any error encountered during evaluation.

The complete prediction-level record is stored in
\codepath{evaluation/proxy_models/proxy_model_predictions.csv}. Before
inference, every image is opened through the EXIF-aware RGB-loading procedure
used elsewhere in the pipeline, and the fold-aware adapter applies the
architecture-specific preprocessing defined by the model implementation.

The evaluation population contains 11\,500 distinct experimental inputs:

\begin{equation}
\begin{aligned}
1\,000\ \text{clean binary inputs}
&+ 500\ \text{\gls{ood} inputs} \\
&+ 5\,000\ \text{adversarial artifacts} \\
&+ 5\,000\ \text{anti-forensic artifacts} \\
&= 11\,500\ \text{inputs}.
\end{aligned}
\end{equation}

Clean and perturbed binary samples are evaluated once by each of the three
proxy architectures, using the checkpoint associated with their assigned fold:

\begin{equation}
1\,000
\times
3
=
3\,000\ \text{clean prediction rows},
\end{equation}

and:

\begin{equation}
10\,000
\times
3
=
30\,000\ \text{perturbed prediction rows}.
\end{equation}

The \gls{ood} branch follows a different protocol. Each of the 500 unique
\gls{ood} inputs is evaluated by all five fold-specific checkpoints of each
architecture:

\begin{equation}
500
\times
5
\times
3
=
7\,500\ \text{\gls{ood} prediction rows}.
\end{equation}

The complete proxy-model prediction table therefore contains:

\begin{equation}
3\,000
+
30\,000
+
7\,500
=
40\,500\ \text{prediction rows}.
\end{equation}

The 2\,500 \gls{ood} responses associated with each architecture correspond to
500 unique images processed by five different fold-specific checkpoints. They
must not be interpreted as 2\,500 distinct or statistically independent
out-of-distribution samples.

\paragraph{Binary metric computation.}

For each binary evaluation group, the confusion matrix uses the fixed layout:

\begin{equation}
\mathbf{C}
=
\begin{bmatrix}
\mathrm{TN} & \mathrm{FP} \\
\mathrm{FN} & \mathrm{TP}
\end{bmatrix}.
\end{equation}

The resulting metric records contain accuracy and balanced accuracy, together
with class-specific precision, recall, and F1-score and their corresponding
macro-averaged values. They also report the \gls{tp}, \gls{tn}, \gls{fp}, and
\gls{fn} counts, the \gls{fpr} and \gls{fnr}, and the overall
misclassification rate. Since all evaluated binary groups contain one
interpretable prediction for every sample, the misclassification rate is equal
to \(1-\mathrm{accuracy}\). It is retained in the consolidated records for
schema completeness and automated validation but is not reported separately in
Chapter~\ref{chap:results}, where accuracy and the direction-specific error
measures provide the same information in a more operationally interpretable
form.

In addition, the records preserve the directional
\texttt{weapon}-to-\texttt{non\_weapon} and
\texttt{non\_weapon}-to-\texttt{weapon} error counts, as well as the mean
maximum predicted-class probability.

The \gls{fpr} and \gls{fnr} are implemented as:

\begin{equation}
\mathrm{FPR}
=
\frac{\mathrm{FP}}
{\mathrm{FP}+\mathrm{TN}},
\qquad
\mathrm{FNR}
=
\frac{\mathrm{FN}}
{\mathrm{FN}+\mathrm{TP}}.
\end{equation}

Clean metrics are grouped by proxy architecture. Adversarial-stage metrics are
grouped by evaluated architecture, perturbation condition, and attack target
model. Anti-forensic metrics are grouped by evaluated architecture and
transformation condition.

The attack-target field is retained because the model-dependent adversarial
artifacts were generated against fold-aware \gls{efficientnetb0} checkpoints but
were subsequently evaluated by all three proxy architectures. This distinction
supports separate analysis of direct target-model behavior and cross-model
transfer. Color Shift remains marked as model-agnostic and is not interpreted
as a transfer attack.

The maximum predicted-class probabilities stored by the evaluation pipeline are
used only as intra-model diagnostic values. They are not assumed to be
calibrated across architectures and are not used as directly comparable
confidence measures between \gls{resnet18}, \gls{efficientnetb0}, and the
\gls{clip}-based proxy.

\paragraph{Clean-to-perturbed comparison.}

Each perturbed prediction is associated with its corresponding clean prediction
through the tuple:

\[
\left(
\texttt{evaluated\_model},
\texttt{evaluation\_fold},
\texttt{original\_image\_id}
\right).
\]

The perturbed prediction record is enriched with the clean prediction, clean
correctness state, clean class probabilities, clean maximum predicted-class
probability, and probability difference relative to the perturbed input.

For each proxy architecture and perturbation condition, the comparative layer
records clean and perturbed accuracy, the schema field
\texttt{robust\_accuracy}, and the corresponding accuracy drop. The stored
value of \texttt{robust\_accuracy} is identical to the perturbed-condition
accuracy. It is retained for schema compatibility with the evaluation pipeline
and does not represent an additional robustness metric; consequently, it is
not reported separately in Chapter~\ref{chap:results}.

The comparative layer also computes the clean and perturbed macro F1-scores and
their difference. The macro-F1 difference is preserved as a secondary
descriptive indicator in the consolidated records. The results chapter
prioritizes accuracy degradation, false-negative and false-positive behavior,
and clean-correct decision transitions because these quantities provide a more
direct operational interpretation for forensic triage. The macro-F1 difference
is therefore not reported as a separate primary robustness measure.

The resulting comparative record further includes the induced-error count and
rate, the schema field \texttt{attack\_success\_rate}, the shift in mean
maximum predicted-class probability, and both the counts and rates of the
directional
\texttt{weapon}-to-\texttt{non\_weapon} and
\texttt{non\_weapon}-to-\texttt{weapon} transitions.

Chapter~\ref{chap:results} reports the directional transition counts together
with the overall induced-error rate or attack success rate. The corresponding
direction-specific rates remain available in the consolidated records but are
not tabulated separately because the frozen binary evaluation groups are
class-balanced and have fixed denominators. The counts therefore provide an
immediate operational interpretation of newly missed target images and
additional false-positive review workload. The normalized directional rates
remain relevant for machine-readable comparison and for possible future
evaluations with unequal class distributions.

Let \(\mathcal{C}_{\mathrm{clean}}\) denote the set of samples correctly
classified under the corresponding clean condition. The induced-error rate for
perturbation condition \(p\) is:

\begin{equation}
\mathrm{IER}_{p}
=
\frac{
\left|
\left\{
i \in \mathcal{C}_{\mathrm{clean}}
:
\hat{y}^{(p)}_{i} \neq y_{i}
\right\}
\right|
}{
\left|
\mathcal{C}_{\mathrm{clean}}
\right|
}.
\end{equation}

Samples already misclassified in the clean condition are excluded from the
denominator because they cannot represent newly induced errors.

The implementation stores this clean-correct transition rate in the
\texttt{attack\_success\_rate} schema field for every perturbation group. It is
interpreted as attack success rate only for FGSM, One Pixel, Sigma-Zero, and
SuperDeepFool. For Color Shift and the five anti-forensic transformations, the
same numerical transition is reported and interpreted as an induced-error rate,
not as adversarial or transfer success.

The maximum-probability shift is computed as:

\begin{equation}
\Delta c
=
c_{\mathrm{perturbed}}
-
c_{\mathrm{clean}},
\end{equation}

and averaged within each architecture--condition group. This quantity compares
the maximum probability assigned to the predicted class before and after
perturbation. If the predicted class changes, it does not compare the
probability assigned to the same semantic class. It is therefore retained only
as an intra-model diagnostic.

\paragraph{Proxy-model \gls{ood} metrics.}

The \gls{ood} branch is summarized independently for each proxy architecture.
The resulting records report the fold-aggregated number of checkpoint responses,
the number and rate of predictions assigned to \texttt{weapon}, and the number
assigned to \texttt{non\_weapon}. They also preserve the mean maximum
predicted-class probability, the adopted high-Max-P threshold, and the number
and rate of responses whose maximum predicted-class probability meets or exceeds
that threshold.

The frozen threshold is:

\begin{equation}
\tau_{\mathrm{high}}
=
0.90.
\end{equation}

The high-Max-P count includes responses assigned to either binary class and
characterizes closed-set assignments whose maximum predicted-class probability
meets or exceeds 0.90. The predicted-weapon rate instead characterizes the
tendency to flag \gls{ood} content as firearm-related.

Neither quantity represents supervised correctness because the \gls{ood}
branch has no positive or negative binary reference assignment. The associated
probabilities remain architecture-specific diagnostic outputs and are not
treated as calibrated across proxy models.

\paragraph{Black-box software metric computation.}

Black-box software metrics are computed from the normalized decisions described
in Section~\ref{subsec:implementation-normalization}. Only matched binary
records with an interpretable \texttt{true} or \texttt{false}
\texttt{weapon\_detected} value contribute to the binary confusion matrix.
Records assigned to \texttt{unknown} are excluded from binary denominators and
reported separately.

The black-box metric layer computes accuracy and balanced accuracy, together
with precision, recall, and F1-score for the \texttt{weapon} class and
specificity for the \texttt{non\_weapon} class. It also reports the
\gls{fpr}, \gls{fnr}, and the corresponding \gls{tp}, \gls{tn}, \gls{fp},
and \gls{fn} counts.

The evaluation further records the number and rate of \texttt{unknown}
decisions. For the separate \gls{ood} branch, it reports the number and rate of
inputs flagged as \texttt{weapon}, together with the number assigned to
\texttt{non\_weapon} or \texttt{unknown}.

Binary metrics are computed only for records whose reference operational
assignment is \texttt{weapon} or \texttt{non\_weapon}. The \gls{ood}
weapon-flag rate uses the complete matched \gls{ood} population of the
corresponding configuration as its denominator. This rate characterizes
observable flagging behavior and is not interpreted as supervised accuracy or
error.

Metrics are generated at multiple aggregation scopes, including the complete
normalized configuration, the sample type, the perturbation family, the
individual perturbation condition, and the combined sample-type and
perturbation-condition level.

Each of the six normalized configurations produces 31 metric rows:

\begin{equation}
6
\times
31
=
186\ \text{black-box software metric rows}.
\end{equation}

The canonical consolidated record is
\codepath{results/metrics/forensic_tools_metrics.csv}. Corresponding
per-configuration files follow the pattern
\codepath{results/metrics/<tool_name>_metrics.csv}.

The normalizer verifies that every per-configuration file contains the expected
number of rows and that the consolidated record was generated from the same
in-memory metric population. The frozen validation confirmed consistency
across all 186 rows.

\paragraph{Canonical reporting layer.}

CSV and JSON metric records remain the canonical sources for numerical
reporting. Figures and thesis-ready tabular extracts are generated from these
records rather than edited manually.

The downstream reporting entry point is
\codepath{results/scripts/20_generate_experimental_reporting_assets.py}. It
reads the consolidated proxy-model and black-box metric files and generates
presentation-layer assets without recreating datasets, perturbations,
predictions, or metrics.

The frozen reporting execution generated PDF and PNG outputs at 300 dpi,
together with a manifest and summary under
\codepath{results/figures/chapter_5/}. It produced 24 unique figure or table
identifiers and 41 materialized files.

The reporting layer intentionally contains a broader set of presentation assets
than those selected for inclusion in Chapter~\ref{chap:results}. Some generated
figures and tabular extracts provide alternative views of the same consolidated
metrics and are retained as auditable reporting artifacts without being
referenced by the final thesis text. Their absence from the chapter therefore
does not indicate missing experimental results. The reporting-asset audit

\begin{enumerate}

\end{enumerate}

\subsection{Integrated Gradients Implementation}
\label{subsec:implementation-explainability}
% ─────────────────────────────────────────────────────────────────────────────

The explainability layer was implemented using \gls{ig}, following the method
introduced by Sundararajan et al.~\cite{Sundararajan2017}. The canonical entry
point is
\codepath{explainability/scripts/17_generate_integrated_gradients_case_studies.py},
which wraps the preserved implementation in
\codepath{explainability/scripts/_17_generate_integrated_gradients_case_studies_impl.py}.

The wrapper adds headless-safe execution, checkpoint and input-integrity
verification, adaptive convergence diagnostics, pseudonymous reviewer
identifiers, and run-specific output cleanup. Interactive manual review uses a
graphical backend, whereas noninteractive attribution generation uses a
headless-safe backend.

The \gls{xai} workflow is restricted to transparent proxy models. It is not
used to explain \gls{magnetai}, \gls{t3kcore},
\gls{excirefoto2025}, or \gls{cellebriteinseyets}, because the gradients,
internal representations, and model parameters required by \gls{ig} are not
accessible for these black-box software systems.

The prediction-level source used for case selection is
\codepath{evaluation/proxy_models/proxy_model_predictions.csv}. This record
provides the prediction, maximum predicted-class probability, fold, reference
operational assignment, perturbation condition, clean-to-perturbed association,
and input path required to identify diagnostically relevant cases.

The frozen thesis workflow applies \gls{ig} exclusively to \gls{efficientnetb0},
which was also the primary proxy target used for model-dependent adversarial
generation. The corresponding attribution maps must therefore be interpreted
as evidence concerning the transparent \gls{efficientnetb0} proxy rather than as
explanations of the selected black-box software systems.

For each selected case, the implementation loads the checkpoint associated with
the input's assigned fold. The hardened entry point computes the checkpoint
\gls{sha256} digest and compares it with the canonical value recorded in
\codepath{models/model_registry.json}. Generation terminates when the
checkpoint is missing, when no expected digest is available, or when the
computed and recorded digests differ.

The input-image SHA-256 value is also verified whenever an expected digest is
available in the prediction or perturbation metadata. The image is then opened
through the common EXIF-aware RGB-loading procedure and processed using the
same \gls{efficientnetb0} transformation applied during proxy-model evaluation.

The resulting model-input tensor is passed to the Captum implementation of
\gls{ig}. The baseline is generated as a tensor of zeros having the same shape
as the preprocessed input:

\[
\mathbf{x}'
=
\mathbf{0}
\qquad
\text{in normalized model-input space}.
\]

This baseline does not represent an independently stored reference image and
must not be interpreted as a black RGB image in the original pixel space.

The frozen thesis cases use the proxy model's predicted class as the attribution
target. This configuration produces an attribution map for the output actually
selected by the model, including incorrect binary predictions and
\gls{ood} assignments. The implementation also supports attribution to the
reference binary class or to both binary outputs, but these alternatives were
not used for the retained thesis assets.

\paragraph{Case-selection procedure.}

The thesis-oriented selection procedure organizes the prediction records into
five diagnostic categories. These comprise a correctly classified clean
\texttt{weapon} image, a clean \texttt{weapon} false negative, and a
high-Max-P \gls{ood} input assigned to \texttt{weapon}. The remaining
categories include an image that is correctly classified in its clean state but
rendered incorrect by an anti-forensic transformation, and an image that is
correctly classified in its clean state but rendered incorrect with a high
maximum predicted-class probability under an adversarial condition.




Candidates are ordered deterministically using the maximum predicted-class
probability, fold, and image path. For perturbation-induced failures, the
ranking prioritizes \texttt{weapon}-to-\texttt{non\_weapon} transitions,
followed by \texttt{non\_weapon}-to-\texttt{weapon} transitions and other
clean-correct-to-incorrect transitions.

The frozen selection summary records 1\,175 candidate records across the five
buckets. Human review retained three cases per bucket, producing a 15-case
intermediate selection. The reviewer inspected the image together with its
fold, reference operational assignment, prediction, maximum predicted-class
probability, perturbation condition, and selection rationale.

Selection and deselection actions were logged together with timestamps, ranks,
case identifiers, and the pseudonymous reviewer identifier. A subsequent
thesis-level reduction purposively retained one case from each
diagnostic bucket.

\paragraph{Attribution processing and visual outputs.}

For each target, the channel-wise attribution tensor is converted into a
two-dimensional map by summing the absolute attribution magnitudes across the
three input channels. The resulting map is min--max normalized to the interval
\([0,1]\).

Because absolute values are used, the visualization represents attribution
magnitude rather than contribution direction. It identifies regions associated
with larger attribution magnitudes for the selected model output along the
baseline-to-input path, but it does not distinguish positive evidence from
negative evidence.

For each selected case, the implementation produces a resized RGB input image,
a colorized attribution heatmap, and an overlay combining the input with the
heatmap. It also generates a normalized grayscale attribution mask, a binary
high-attribution mask, a side-by-side diagnostic comparison, and a histogram of
the normalized attribution values.

The heatmap uses the \texttt{inferno} color map. The overlay combines the
resized input and colorized map using an attribution opacity of 0.45. The
binary high-attribution mask retains pixels whose normalized magnitude is at or
above the 90th-percentile threshold.

This threshold identifies approximately the 10\% of image locations with the
largest attribution magnitudes. The exact proportion may differ when multiple
locations share the percentile value.

For each selected case, the thesis retains four visual assets: the input image,
the standalone attribution heatmap, the heatmap overlay, and the top-10\%
attribution mask.

The resulting thesis-level visual corpus contains:

\begin{equation}
5\ \text{cases}
\times

=
20\ \text{images}.
\end{equation}

\codepath{docs/LatexThesis/images/}. The complete generated diagnostic tree
under
\codepath{explainability/outputs/integrated_gradients/} remains a local output
and is not distributed through the public repository.

\paragraph{Convergence diagnostics.}

The historical thesis assets were generated using 32 integration steps. Their
raw Captum convergence deltas are retained in
\codepath{explainability/manifests/chapter5/thesis_selection.csv}. These
historical outputs were not generated under the adaptive acceptance rule
subsequently introduced by the hardened entry point.

The hardened procedure evaluates the normalized convergence delta:

\begin{equation}
\delta_{\mathrm{norm}}
=
\frac{
\left|\delta_{\mathrm{IG}}\right|
}{
\max\left(
\left|
f_t(\mathbf{x})-f_t(\mathbf{x}')
\right|,
10^{-12}
\right)
},
\end{equation}

where \(f_t\) is the target-class output, \(\mathbf{x}\) is the preprocessed
input, and \(\mathbf{x}'\) is the baseline.

Starting from the requested integration resolution, the procedure doubles the
number of steps until either:

\[
\delta_{\mathrm{norm}}
\leq
0.05,
\]

or the maximum of 256 integration steps is reached. A regenerated case is
marked as \texttt{passed} only when the threshold is satisfied; otherwise, the
state \texttt{threshold\_not\_met} is retained.

Adaptive regeneration had not been completed for the five historical thesis
assets at the time of artifact freezing. Their validation state is therefore
recorded as \texttt{pending\_adaptive\_regeneration}. The figures are
interpreted exclusively as qualitative diagnostic visualizations, and no
strict numerical convergence or completeness claim is made for them.

\section{Traceability, Integrity, and Reproducibility Controls}
\label{sec:implementation-traceability}
% ─────────────────────────────────────────────────────────────────────────────

Traceability, integrity, and controlled reproducibility were implemented as
cross-cutting properties of the experimental workflow rather than as controls
introduced only after evaluation. The resulting framework links the frozen
dataset, deterministic partitions, proxy-model checkpoints, derived
perturbations, black-box inputs, normalized software outputs, metric tables,
explainability cases, and reporting assets through stable identifiers,
cryptographic digests, manifests, registries, and version-controlled metadata.

The implementation distinguishes three related but non-equivalent objectives.
\emph{Traceability} refers to the ability to reconstruct the provenance and
processing history of an experimental input, derived artifact, model, or result
record. \emph{Integrity} concerns the ability to verify that an input, artifact,
model, or record has not changed relative to its canonical recorded state.
\emph{Controlled reproducibility} refers to the extent to which the workflow can
be inspected or rerun under the constraints imposed by data-access restrictions,
licensed-software requirements, human-review stages, and the available execution
environment.

This distinction is necessary because public availability of code, manifests,
and sanitized results does not imply unrestricted redistribution of the source
images or availability of the proprietary software required to repeat the
black-box processing.

\paragraph{Stable identity and provenance chain.}

Stable identifiers are assigned at successive processing stages. Prepared
source images receive an \texttt{image\_id}; generated perturbations receive a
\texttt{generated\_image\_id}; black-box inputs receive a semantically neutral
\texttt{bundle\_id}; and selected explainability cases receive a
\texttt{case\_id}. Proxy-model checkpoints are identified through the
combination of architecture and held-out fold.

The principal provenance chain is:

\[
\begin{aligned}
\texttt{image\_id}
&\longrightarrow \texttt{generated\_image\_id}
\longrightarrow \texttt{bundle\_id} \\
&\longrightarrow \texttt{normalized\_prediction}
\longrightarrow \texttt{metric\_row} \\
&\longrightarrow \texttt{reporting\_asset}.
\end{aligned}
\]

For clean binary samples and \gls{ood} inputs, the original and generated
identifiers may coincide because no derived image artifact is created. For
adversarial and anti-forensic artifacts, the generated identifier preserves the
association with the corresponding clean source image while distinguishing the
perturbation condition and, where applicable, the target proxy model.

Canonical sample-level manifests use repository-relative paths to associate
artifacts with the logical repository structure independently of the local
workspace. Run summaries and registries additionally preserve configurations,
timestamps, sample counts, fold assignments, and output locations. Raw
commercial exports, execution logs, and controlled local workspaces may contain
machine-specific paths and are therefore subject to the distribution and
sanitization boundary described later in this section.

\paragraph{Cryptographic integrity controls.}

\gls{sha256} is the primary integrity digest throughout the pipeline.
\gls{md5} is retained only as an auxiliary interoperability identifier because
some forensic software exports expose MD5-oriented fields or matching
workflows. It is not treated as the primary integrity mechanism.

Per-file \gls{sha256} values are recorded or verified at the principal
transformation and transfer boundaries. These include the prepared and frozen
source images, the deterministic clean and \gls{ood} partitions, the
adversarial and anti-forensic artifacts, and the blind and structured copies
contained in the forensic evaluation bundle.

Integrity verification also covers the proxy-model checkpoints, the selected
explainability inputs and their corresponding fold-specific checkpoints, the
sanitized extracts produced by the black-box software systems, and the canonical
normalized black-box prediction table together with the associated commercial
metric table.

Thesis-level explainability images are validated through their canonical
manifest paths, case metadata, and asset audits rather than being treated as
independently authenticated model artifacts.

Whenever an image is copied between controlled stages, its destination digest
is recomputed and compared with the canonical value recorded in the originating
manifest. A mismatch causes the corresponding operation to terminate rather
than silently accepting a different file.

The checkpoint digests stored in
\codepath{models/model_registry.json} bind every proxy architecture and
held-out fold to its serialized checkpoint. They are checked before canonical
proxy evaluation, model-dependent adversarial generation, and hardened
explainability generation.

Archive-level integrity is maintained separately from per-file integrity. The
canonical complete-archive digests are stored in
\codepath{docs/artifact/CONTROLLED_ARTIFACT_CHECKSUMS.sha256}. This file
identifies:

\begin{itemize}
\item \texttt{00\_raw\_datasets\_bundle.zip};
\item \texttt{16\_frozen\_forensic\_evaluation\_bundle.zip}.
\end{itemize}

The archive digest authenticates the complete downloaded ZIP file. Restoration
of the frozen forensic evaluation bundle additionally uses
\codepath{datasets/forensic_evaluation_bundle/metadata/%
bundle_hashes_sha256.csv} to verify the expected file-name population and the
SHA-256 value of each of the 11\,500 blind inputs.

The restoration entry point also rejects malformed ZIP files, corrupt members,
symbolic links, path-traversal attempts, unexpected archive roots, missing
files, additional files, and content-hash mismatches. Public metadata already
committed to the repository remains authoritative and is not overwritten by
metadata packaged within the controlled archive.

This separation prevents successful verification of a complete ZIP file from
being treated as a substitute for verifying the expected file population after
extraction.

\paragraph{Deterministic configuration controls.}

A fixed seed of 42 is used for the principal stochastic procedures, including
fold construction, internal training--validation partitioning, and
image-specific randomized-search initialization where applicable. The seed is
recorded in the corresponding machine-readable configuration and summary
records.

The use of a fixed seed supports repeatability of logical partitions and
pseudo-random initialization. It does not imply that all numerical results are
guaranteed to be bit-identical across different operating systems, hardware
architectures, library versions, or CPU and GPU implementations.

PyTorch and cuDNN deterministic options reduce nondeterministic behavior where
supported, but the execution environment remains part of the reproducibility
boundary.

The frozen machine-readable configurations specify the accepted reference
assignments and expected group counts, the five clean folds, and the separate
\gls{ood} branch. They also define architecture-specific preprocessing and
normalization, training hyperparameters, checkpoint-selection rules, and the
parameters associated with adversarial and anti-forensic conditions.

The configurations further preserve the associations among models, checkpoints,
and folds, together with the black-box software versions and observable-output
mappings. In addition, they document the metric definitions, confusion-matrix
layout, and explainability settings, including the selected architecture,
attribution target, baseline, historical number of integration steps,
case-selection criteria, and convergence status.

These values are retained in CSV or JSON records rather than being represented
only in narrative documentation.

\paragraph{Overwrite and rerun controls.}

The principal generation and evaluation scripts implement fail-visible output
guards. Existing canonical outputs are not silently replaced. A rebuild
generally requires an explicit \texttt{--force} option, which removes or
replaces only the output scope associated with the selected run.

This policy reduces the risk of combining artifacts produced under different
configurations or overwriting a frozen result with a partial diagnostic
execution. Partial, limited, single-model, or single-fold experiments must use
separate diagnostic output locations and cannot replace canonical manifests,
prediction tables, or metric records.

An explicit forced rebuild does not establish equivalence with the frozen
research artifact. Regenerated outputs must still satisfy the expected counts,
identifier constraints, integrity values, configuration requirements, and
downstream validation procedures.

\paragraph{Machine-readable invariants and completeness checks.}

Each major stage produces sample-level records and a run-level summary. Summary
files record input manifests, parameters, output paths, expected and actual
counts, validation states, and creation metadata. These records permit
structural checks without requiring manual inspection of every image or
prediction.

The principal frozen invariants comprise 1\,500 records in the final dataset,
including 1\,000 binary samples and 500 \gls{ood} inputs. The binary subset is
partitioned into five clean folds containing 200 images each and is associated
with 15 fold-aware proxy-model checkpoints. The experimental pipeline also
produces 5\,000 adversarial and 5\,000 anti-forensic artifacts, resulting in
11\,500 unique items in the forensic evaluation bundle.

At the evaluation level, the frozen outputs include 40\,500 proxy-model
prediction rows, 69\,000 canonical sanitized black-box software decisions, and
186 black-box software metric rows. The explainability branch retains five
canonical thesis-level cases and 20 associated visual assets.

These counts are implementation invariants and completeness checks. Their
satisfaction does not establish model or software robustness. The quantitative
behavior of the evaluated systems is analyzed separately in
Chapter~\ref{chap:results}.

\paragraph{Black-box output correspondence and equivalence controls.}

Complete black-box software exports are excluded from the public repository
because they may contain proprietary structures, local paths, case metadata,
device-related fields, file-system information, or data unrelated to the
experimental decision mapping.

The public artifact retains minimized decision extracts for the four software
families. These extracts are combined into
\codepath{evaluation/forensic_tools/normalized_predictions.csv}, which contains
69\,000 sanitized decisions across the six normalized configurations.

The canonical public table excludes complete raw-export fields, cryptographic
hash columns used only for local matching, and local execution paths. It
preserves the neutral bundle identifier, experimental condition, reference
operational assignment, observable decision-relevant value, and normalized
prediction required to audit the reported metrics.

The table can be reconstructed through
\codepath{forensic_tools/scripts/build_canonical_normalized_predictions.py}.

Decision-level and metric-level equivalence is evaluated through
\codepath{forensic_tools/scripts/validate_public_extract_equivalence.py}. The
validation confirms that the four sanitized extracts reconstruct all 69\,000
normalized decisions and that the reconstructed records are identical to the
canonical public prediction table. It also verifies that the same decision
population reproduces all 186 frozen black-box software metric rows.

In addition, the procedure checks that the canonical prediction and metric
digests match the values recorded in the validation report and that each
sanitized source extract matches its corresponding recorded \gls{sha256}
digest.

This procedure does not establish field-level equivalence with every column of
the complete raw exports. It establishes that the sanitized records preserve
the complete normalized decision population and reproduce the quantitative
values derived from the controlled local normalization workspace.

\paragraph{Environment and public-distribution boundary.}

The pipeline was developed through Python virtual environments in Windows and
Linux contexts, including Windows PowerShell and Kali Linux, with CPU- or
CUDA-enabled execution selected according to the computational stage.
Black-box evaluation additionally requires compatible licensed software and a
suitable workstation.

The repository records dependency specifications and operational assumptions
but does not claim to reproduce a byte-identical operating-system environment.
Exact numerical reproduction may depend on hardware, operating-system,
dependency, driver, and licensed-software behavior.

The public-release policy excludes unrestricted copies of the image corpora,
complete raw exports generated by the black-box software systems, proprietary
case databases, and evidence-related material that is not required for the
experimental record. It also excludes credentials, API keys, session data,
commercial license information, and private or temporary artifact-access URLs.

Exact usernames, unnecessary local absolute paths, generated LaTeX auxiliary
files, and locally compiled PDF documents are likewise omitted from the public
release.

Tracked summaries, logs, and machine-readable outputs must be audited before
release to ensure that this policy is satisfied. Public sanitization is a
distribution control and does not modify the byte-identical image artifacts
used in the frozen black-box evaluation.

\paragraph{Version control, historical provenance, and artifact freezing.}

Source code, manifests, registries, sanitized decisions, metric tables,
documentation, and thesis sources are maintained through Git version control.
Large proxy-model checkpoints are managed through Git LFS, while their
SHA-256 values remain recorded independently in the model registry.

For historical provenance, the repository preserves the pre-cleanup state
through the protected branch
\texttt{archive/pre-commission-cleanup-2026-07-16} and the protected tag
\texttt{snapshot/pre-commission-cleanup-2026-07-16}. Both references identify
the same historical commit. This snapshot supports provenance and repository
audit but is not the current source of truth for final documentation or
experimental reporting.

The curated \texttt{main} branch remains the authoritative current artifact.
Substantive changes to the data, perturbations, checkpoints, normalized
decisions, metrics, or thesis conclusions require a new versioned release
rather than silent replacement of the frozen experimental state.
Documentation corrections, security fixes, citation updates, and
non-substantive archival improvements must remain clearly distinguishable from
changes to the experimental evidence.

Taken together, these controls provide a traceable connection between the
implemented protocol and the results reported in the following chapter. They do
not eliminate limitations associated with controlled data access, execution
environment variation, human review, historical explainability convergence,
or proprietary black-box systems. Instead, they make these boundaries explicit
and preserve the information required to audit the evaluation within them.

Chapter~\ref{chap:results} presents the quantitative outcomes obtained from the
frozen implementation and analyzes their implications for the operational
robustness of the evaluated proxy models and selected black-box software
systems.
