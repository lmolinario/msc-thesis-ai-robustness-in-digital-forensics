% ─────────────────────────────────────────────────────────────────────────────
\chapter{Implementation and Experimental Setup}
\label{chap:implementation}
% ─────────────────────────────────────────────────────────────────────────────


This chapter documents the concrete implementation of the \gls{fairlab}
methodology introduced in Chapter~\ref{chap:methodology}. It describes how the
experimental protocol was instantiated through the preparation and freezing of
the image corpus, the generation of deterministic data partitions, the
training of fold-aware proxy models, the generation of adversarial and
anti-forensic artifacts, and the construction of the forensic evaluation
bundle.

The chapter also reports the configurations adopted for the selected black-box
software systems, the procedures used to match and normalize their observable
outputs, and the technical controls introduced to preserve artifact identity,
provenance, integrity, and reproducibility. The implementation of the
explainability workflow and the generation of the consolidated evaluation
artifacts are documented as components of the same experimental pipeline.

The distinction between implementation and experimental evidence is maintained
throughout the chapter. The present chapter describes how the protocol was
realized and which technical artifacts were produced, whereas the quantitative
outcomes and their operational interpretation are reported separately in
Chapter~\ref{chap:results}. This separation prevents implementation choices,
software configurations, and data-management procedures from being conflated
with the measured robustness of the evaluated systems.

A central implementation principle is that the two evaluation levels operate
on the same frozen experimental corpus. The 1\,000 clean binary images and the
500 clean \gls{ood} images define the common source population, while the
10\,000 adversarial and anti-forensic artifacts are derived exclusively from
the binary subset. The proxy models process the manifest-linked experimental
inputs and derived artifacts, whereas the selected black-box software systems
receive byte-identical anonymized copies through the blind forensic evaluation
bundle. The equivalence between these two views is verified through
\gls{sha256} digests. Consequently, the parallel comparison is based on the
same samples and experimental conditions rather than on independently assembled
datasets.

\section{Experimental Workflow and Implementation Environment}
\label{sec:implementation-overview}
% ─────────────────────────────────────────────────────────────────────────────

The experimental protocol was implemented as a staged and traceable pipeline
covering source acquisition, dataset preparation, human-in-the-loop review,
data partitioning, proxy-model training, perturbation generation, proxy-model
evaluation, forensic bundle construction, black-box output normalization,
explainability analysis, and final reporting. Each stage produces explicit
intermediate records or artifacts that become inputs to the subsequent stage.
These outputs include manifests, model checkpoints, prediction tables,
integrity digests, validation reports, and consolidated metric files.

The implementation is organized as a numbered sequence of scripts. This
organization makes the execution order explicit and reduces ambiguity regarding
the provenance of the generated outputs. The numbered pipeline begins with the
controlled restoration or acquisition of the source corpora and continues
through dataset preparation, human review, model training, perturbation
generation, proxy-model evaluation, bundle construction, explainability
analysis, black-box normalization, and reporting. Additional validation
utilities operate on the frozen outputs without modifying the canonical
experimental inputs, derived artifacts, or result records.

At the repository level, the implementation is divided into functional
components. Dataset preparation and bundle construction are maintained under
\codepath{datasets/}; perturbation manifests are stored under
\codepath{attacks/}; proxy architectures, checkpoints, and training records are
maintained under \codepath{models/}; prediction generation and black-box output
normalization are organized under \codepath{evaluation/}; explainability
artifacts are maintained under \codepath{explainability/}; and consolidated
metrics, reporting assets, and validation utilities are stored under
\codepath{results/}. The authoritative thesis source is maintained separately
under \codepath{docs/LatexThesis/}.

The software implementation was managed through Python virtual environments.
The workflow was executed in Windows and Linux environments, including Windows
PowerShell and Kali Linux, depending on the requirements of each stage. The
black-box evaluations additionally required compatible licensed installations
of the selected software systems. The Python dependency set is declared in the
repository-level \codepath{requirements.txt} file and includes the libraries
used for numerical processing, image manipulation, proxy-model training and
inference, adversarial generation, explainability, visualization, and source
acquisition. The deep-learning implementation is based on PyTorch and
Torchvision, with \texttt{open\_clip\_torch} used for the \gls{clip}-based
proxy model and Captum used for the Integrated Gradients workflow.

The code supports both CPU and CUDA-enabled execution, with device selection
depending on the computational requirements of the individual stage and the
available execution environment. Lightweight operations, including manifest
inspection, output normalization, metric validation, and reporting audits, can
be performed without dedicated acceleration. Proxy-model training, iterative
adversarial generation, and explainability regeneration constitute the most
computationally demanding stages.

The repository is distributed as a research artifact rather than as a
self-contained software package or a byte-identical operating-system image.
Accordingly, procedural reproducibility and artifact-level auditability are
supported through numbered scripts, frozen manifests, fold-aware checkpoints,
prediction tables, explicit parameters, integrity hashes, validation reports,
and controlled experimental artifacts. The public repository retains the
material required for structural inspection, metric recomputation, and audit,
whereas the complete image corpora, the exact frozen black-box input bundle, and
the complete proprietary software exports remain subject to controlled access.
This boundary supports auditability and partial experimental reproduction
without redistributing restricted, licensed, or otherwise non-public material.

\section{Dataset Preparation and Organization}
\label{sec:implementation-dataset}
% ─────────────────────────────────────────────────────────────────────────────

% ─────────────────────────────────────────────────────────────────────────────
\subsection{Technical Preparation and Source Consolidation}
\label{subsec:implementation-dataset-preparation}
% ─────────────────────────────────────────────────────────────────────────────

The initial image pool was assembled from five heterogeneous source
collections maintained under \codepath{datasets/raw/}. These collections were
organized according to acquisition provenance rather than final experimental
assignment. The source structure comprised a public Kaggle-based collection,
the specialized DeepFirearm corpus, open-web images, content obtained from
Telegram and YouTube, and material collected from non-indexed web sources. This
organization preserved the origin of each sample while preventing source names,
directory structures, or pre-existing labels from being inherited automatically
as reference operational assignments.

The technical preparation stage was implemented by:

\begin{center}
\codepath{datasets/scripts/prepared/08_build_prepared_dataset.py}
\end{center}

The script scans the supported source directories in a fixed order and
constructs a unified candidate pool under:

\begin{center}
\codepath{datasets/prepared/final_pool/}
\end{center}

This stage is deliberately limited to technical preparation. It does not
perform semantic annotation, assign the final labels
\texttt{weapon}, \texttt{non\_weapon}, or \texttt{ood}, or determine whether
an image is suitable for inclusion in the frozen experimental dataset. These
decisions are deferred to the human-in-the-loop review process described in
Section~\ref{subsec:implementation-human-review}.

Candidate discovery was restricted to files with the extensions
\texttt{.jpg}, \texttt{.jpeg}, \texttt{.png}, \texttt{.bmp},
\texttt{.webp}, \texttt{.tif}, and \texttt{.tiff}. Each candidate file was
opened and verified using the Pillow image-processing library. Images that
could not be decoded or structurally verified were recorded as unreadable,
whereas images with either dimension below 300 pixels were excluded under the
\texttt{below\_min\_size} condition. Unexpected decoding failures were
preserved in the invalid-image report together with the corresponding
exception type.

For every technically valid image, the script computed a \gls{sha256} digest
over the original file bytes. Exact-duplicate detection was then performed
globally across all source collections rather than independently within each
source. When the same digest occurred more than once, the first instance
encountered according to the deterministic scan order was retained, and each
subsequent occurrence was recorded as a discarded duplicate. This procedure
prevented the same byte-identical image from appearing multiple times in the
prepared pool, including when it had been collected from different sources or
stored under different file names.

Accepted images were assigned stable identifiers using the format:

\begin{center}
\texttt{img\_00000001}
\end{center}

and copied to:

\begin{center}
\codepath{datasets/prepared/final_pool/images/}
\end{center}

The original file extension was preserved, and no resizing, recompression, or
format conversion was applied during this stage. After each copy operation, the
destination file was hashed again and compared with the digest of the source
file. A mismatch caused the pipeline to terminate, thereby preventing a
modified, corrupted, or incomplete copy from entering the prepared pool.

The resulting prepared pool contained 15\,321 technically valid and
byte-distinct images from an initial set of 19\,769 candidate files. A total of
3\,124 files were excluded because they were unreadable, structurally invalid,
or below the minimum dimensional threshold, while 1\,324 additional files were
discarded as exact duplicates.

The preparation stage generated four principal audit records:

\begin{itemize}
\item \codepath{datasets/prepared/final_pool/metadata.csv}, containing one
row for each retained image;

\item
\codepath{datasets/prepared/final_pool/reports/invalid_images.csv},
documenting technically excluded files and their corresponding exclusion
reasons;

\item
\codepath{datasets/prepared/final_pool/reports/duplicates_discarded.csv},
linking each discarded duplicate to the retained image and its
\gls{sha256} digest;

\item
\codepath{datasets/prepared/final_pool/reports/prepared_build_summary.json},
containing global and source-specific preparation statistics.
\end{itemize}

For each retained image, \texttt{metadata.csv} records the stable image
identifier, prepared file name and path, source group, source dataset, original
relative path and file name, \gls{sha256} digest, image dimensions, file size,
extension, and technical-validity state. This structure preserves candidate-pool
provenance without treating provenance as a semantic assignment.

The output of this stage is therefore a technically validated and deduplicated
candidate pool rather than the final experimental dataset. The reduction from
15\,321 prepared images to the frozen corpus used in the experiments was
performed only after explicit human assessment of semantic suitability,
operational assignment, visual interpretability, and corpus-composition
requirements.

\subsection{Review Documentation and Human-in-the-Loop Validation}
\label{subsec:implementation-human-review}
% ─────────────────────────────────────────────────────────────────────────────

The transition from technical preparation to semantic assessment was
implemented through a dedicated review manifest. The manifest was generated
from the prepared-pool metadata by:

\begin{center}
\codepath{datasets/scripts/prepared/09_generate_review_manifest_full.py}
\end{center}

and stored as:

\begin{center}
\codepath{datasets/prepared/manifests/review_manifest_full.csv}
\end{center}

The script creates one review record for each image retained in the prepared
pool. Identity, provenance, and technical metadata are propagated from
\codepath{datasets/prepared/final_pool/metadata.csv}, including the stable image
identifier, \gls{sha256} digest, prepared path, source dataset, original source
path, image dimensions, file size, extension, and technical-validity state. The
digest is not recomputed at this stage because it was already established and
verified during technical preparation.

The review manifest extends these technical fields with a separate set of
columns for semantic assessment and review-state management. These fields
include the final review assignment, review status, reviewer identifier,
timestamp, notes, exclusion reason, and information used to document
\gls{ood} cases. The schema also reserves fields for an optional automatic
prelabeling stage. However, these fields were initialized as empty, and their
status was set to \texttt{pending}. No automatic score, model prediction, or
class suggestion was used to determine the final human assignments.

The semantic review was conducted through the dedicated interactive
application implemented by:

\begin{center}
\codepath{datasets/scripts/final/10_manual_selection_protocol_reviewer.py}
\end{center}

The reviewer loads the full manifest into a persistent working database:

\begin{center}
\codepath{datasets/final/manifests/manual_selection_protocol_db.csv}
\end{center}

and presents the images in batches of ten, arranged in a five-column grid. The
interface supports mouse- and keyboard-based assignment to
\texttt{weapon}, \texttt{non\_weapon}, and \texttt{ood}, together with the
review-only \texttt{exclude} disposition. It also supports image zooming, page
navigation, decision reversal, session changes, saving, and resumption of a
previous review state.

Two operating modes were implemented. In \texttt{review\_pending} mode, the
reviewer inspects unassigned images from a selected source and assigns an
operational assignment or exclusion disposition. In
\texttt{review\_selection} mode, images already assigned to one of the selected
experimental groups can be inspected again, optionally filtered by source, and
returned to the pending pool when the previous assignment is considered
unsuitable. This second mode provides an explicit quality-control pass over the
selected images rather than treating the initial assignment as immutable.

The assignment criteria displayed by the reviewer reproduce the operational
definitions established in Chapter~\ref{chap:methodology}. Recognizable and
realistic firearm-related content is assigned to \texttt{weapon}; realistic and
interpretable negative content is assigned to \texttt{non\_weapon}; borderline,
synthetic, replica-like, source-degraded, anomalous, or semantically
out-of-task content is assigned to the separate \texttt{ood} branch; and
unusable or irrelevant material is assigned to the review-only
\texttt{exclude} disposition. When a sample cannot be assigned to either binary
class with sufficient semantic clarity, the interface directs the reviewer not
to force the case into \texttt{weapon} or \texttt{non\_weapon}.

The application enforces global targets of 500 images for each of the
\texttt{weapon}, \texttt{non\_weapon}, and \texttt{ood} groups. Once the target
for a group is reached, further assignments to that group are blocked unless an
existing selection is first removed. Advisory source-level targets of 100
samples per group and source are also displayed. These source-level targets do
not constrain reviewer decisions; they operate only as balancing alerts and
indicate sources that remain underrepresented.

The resulting procedure is therefore a target-driven selection workflow rather
than an exhaustive semantic annotation of the complete prepared pool. The
global targets define the stopping condition, while the advisory source-level
targets support composition control without guaranteeing equal representation
from every source.

Every assignment, clearing, or reassignment action is associated with the image
identifier, source dataset, reviewer identifier, timestamp, previous
assignment, new assignment, session mode, and review state. The events are
appended to:

\begin{center}
\codepath{datasets/final/reports/manual_selection_log.csv}
\end{center}

The current session position, review mode, active filters, and recent undo state
are preserved in:

\begin{center}
\codepath{datasets/final/reports/manual_selection_state.json}
\end{center}

This state-management mechanism allows the review to be interrupted and resumed
without discarding previous decisions. Before replacing existing working files,
the application also creates timestamped backups. Temporary files and atomic
replacement operations are used to reduce the risk of partial or corrupted
writes.

The frozen working database contained 1\,500 reviewed records and 13\,821

The implemented review process therefore separates three distinct elements:
technical file validity, semantic suitability for the experimental task, and
final inclusion in the frozen corpus. This distinction ensures that neither
source provenance nor technical readability is treated as sufficient evidence
of operational class membership. The resulting frozen composition and the
consistency checks applied to the exported manifests are described in
Section~\ref{subsec:implementation-dataset-freezing}.

\end{center}

assignment, and source identifier. Each image is then assigned to an eligible
fold that has not reached its class quota. Among the eligible folds, priority
is given to the fold containing the lowest current number of samples from the
same source and class. The current overall class occupancy and the fold
identifier are used as secondary tie-breaking criteria.

\section{Proxy-Model Implementation}
\label{sec:implementation-proxy-models}

\subsection{Architectures and Preprocessing}
\label{subsec:implementation-architectures}
% ─────────────────────────────────────────────────────────────────────────────

The controlled proxy-model layer was implemented through three fully
inspectable classification models: ResNet18, EfficientNet-B0, and a
\gls{clip}-based visual classifier. Consistent with the definition introduced
in Chapter~\ref{chap:methodology}, these proxy models serve as experimental
reference models for studying controlled classification behavior, robustness
degradation, transferability, confidence patterns, error direction, and, for
the selected model, feature attribution.

The proxy models are not replicas, functionally equivalent substitutes,
reverse-engineered reconstructions, or architectural reproductions of the
selected black-box software systems. Instead, they provide a controlled and
inspectable environment in which model architectures, preprocessing procedures,
training configurations, logits, probabilities, gradients, checkpoints, and
attribution outputs can be accessed directly.

The three architectures were selected to provide complementary experimental
references rather than to identify a universally superior classification
model. ResNet18 represents a conventional residual convolutional baseline,
whereas EfficientNet-B0 provides an efficiency-oriented convolutional
architecture based on a different design and scaling strategy. The
\gls{clip}-based proxy introduces a distinct representation paradigm through a
large-scale pretrained Vision Transformer whose visual encoder is kept frozen
and adapted to the binary task through a supervised linear classification
head.

This combination supports comparison between two convolutional architectures
adapted to the binary task and a proxy based on frozen pretrained visual
representations. It also enables analysis of whether model-dependent
adversarial artifacts generated against EfficientNet-B0 transfer to
architecturally different proxy models. The selection was therefore intended
to provide controlled architectural diversity within a reproducible and fully
inspectable evaluation layer rather than to reproduce the internal models of
the selected black-box software systems.

All three proxy models implement the same binary classification mapping:

\begin{equation}
\texttt{non\_weapon} \rightarrow 0,
\qquad
\texttt{weapon} \rightarrow 1.
\end{equation}

The separate \gls{ood} branch is not represented as a third supervised output
and is excluded from proxy-model training. Its inputs are processed only during
the dedicated \gls{ood} evaluation stage.

\end{center}

and its frozen architecture definitions are recorded in:

\end{center}

The \gls{clip}-based proxy is constructed from the

weights identified in the model registry.

A common image-loading procedure was applied across the three architectures.
Each file is opened using Pillow, corrected according to its embedded
orientation information through an EXIF transpose operation, and converted to
a three-channel RGB representation. The resulting image is then processed
through the preprocessing pipeline associated with the selected architecture.

All proxy-model inputs are resized to:

\begin{center}
\texttt{224 $\times$ 224 pixels}
\end{center}

\begin{enumerate}
\item deterministic resizing to \(224 \times 224\) pixels;
\item random horizontal flipping with probability \(0.5\);
\item conversion to a PyTorch tensor;
\item architecture-specific channel normalization.
\end{enumerate}

The validation and evaluation transformation uses the same resizing,
tensor-conversion, and normalization operations but does not apply random
horizontal flipping. No additional random cropping, rotation, color
augmentation, or geometric distortion is introduced by the training script.

\subsection{Training Configuration and Fold-Aware Checkpoints}
\label{subsec:implementation-training}
% ─────────────────────────────────────────────────────────────────────────────

The proxy models were trained according to a fold-aware leave-one-fold-out
protocol. For each architecture and each target fold, the target fold was
reserved as the held-out evaluation partition, while the remaining four folds
were used to construct the training and internal validation sets. Consequently,
no checkpoint was trained on the same fold on which it was subsequently
evaluated or used to generate fold-matched model-dependent adversarial
artifacts.

For each run, the four non-held-out folds contained 800 images. The
implementation created an internal stratified validation partition by reserving
15\% of these samples independently within each binary class. This produced:

\begin{itemize}
\item 680 images for parameter optimization;
\item 120 images for internal validation;
\item 200 images in the untouched held-out fold.
\end{itemize}

The split between training and internal validation data was generated
deterministically using seed 42. Records were first separated by class,
shuffled within each class, and then recombined, thereby preserving the balance
between \texttt{weapon} and \texttt{non\_weapon}. The held-out fold was not
involved in parameter optimization or checkpoint selection.

ResNet18 and EfficientNet-B0 were fine-tuned from their ImageNet-initialized

\texttt{--freeze-backbone} option for diagnostic or alternative runs, but this
option is not part of the frozen CNN training configuration. For the
\gls{clip}-based proxy, the pretrained visual encoder was always frozen, and
only the binary linear head was optimized.

The training objective was implemented using unweighted cross-entropy loss. No
class weighting was applied because every fold and each derived
training--validation partition remained balanced between the two binary
classes. Parameter updates were performed using the AdamW optimizer with the
fixed learning-rate and weight-decay values reported above.

Before training begins, the script validates the complete clean-fold manifest.
The validation procedure verifies:

\begin{itemize}
\item the presence of the required manifest columns;
\item the exclusive use of the two accepted binary assignments;
\item the presence of all five expected folds;
\item the exact count of 100 images per class and fold;
\item the uniqueness of the image identifiers;
\item the availability of every referenced image file;
\item the correspondence between each file and its recorded
\gls{sha256} digest.
\end{itemize}

Training is interrupted when a source image is missing or when its digest does
not match the value recorded in the split manifest. This prevents a checkpoint
from being silently produced from a dataset state that differs from the frozen
partition definition.

Reproducibility controls are applied to the principal pseudo-random sources.
The fixed seed is propagated to the Python standard-library generator, NumPy,
PyTorch, and all available CUDA devices. The implementation disables cuDNN
benchmark-based algorithm selection and requests deterministic cuDNN behavior.

The execution device may be selected explicitly as \texttt{cpu} or
\texttt{cuda}, or resolved automatically according to CUDA availability. The
software and hardware environment is documented separately as part of the
reproducibility context. Device selection does not alter the frozen fold
assignments or declared training configuration, although the execution
environment remains relevant to the exact numerical reproduction of the
training process.

During each epoch, the implementation records training loss, training accuracy,
validation loss, and validation accuracy. The checkpoint is updated whenever
the current validation accuracy is greater than or equal to the best value
observed during the preceding epochs. Consequently, when the same best
validation accuracy occurs in multiple epochs, the latest qualifying epoch is
retained. The held-out fold remains excluded from this selection process.

four model-dependent adversarial attacks and one model-agnostic
adversarial-style condition:

\begin{itemize}
\item \gls{fgsm};
\item One Pixel;
\item Sigma-Zero;
\item SuperDeepFool;
\item Color Shift.
\end{itemize}

The first four procedures depend on a designated fold-specific proxy-model
checkpoint. \gls{fgsm}, Sigma-Zero, and SuperDeepFool use white-box access to
model gradients or decision-boundary information, whereas One Pixel relies on
score-based interaction with the observable output probabilities of the proxy
model. Color Shift is implemented within the same generation stage for
experimental consistency but does not require gradients, output scores, or
checkpoint access. It is therefore recorded explicitly as a model-agnostic
adversarial-style condition rather than as a white-box or score-based attack.

EfficientNet-B0 was used as the frozen primary proxy target for all
model-dependent attacks. For each input image, the generator reads the fold
identifier from the clean manifest and loads the corresponding checkpoint:

\begin{center}
\codepath{models/checkpoints/efficientnet_b0/<fold>.pt}
\end{center}

Because each checkpoint was trained while excluding its associated fold, the
target image was not part of the training data used to produce the checkpoint
against which its perturbation was generated. This fold-aware association
preserves the separation between training and attack generation established in
Section~\ref{subsec:implementation-training}.

Before any attack is executed, the script verifies the presence of the required
manifest columns, the exclusive use of the two accepted binary assignments, the
uniqueness of image identifiers, the availability of all clean source files,
and the correspondence of their \gls{sha256} and \gls{md5} values with the
clean-fold manifest. For model-dependent conditions, the required fold-specific
checkpoint must also be available. Missing files or integrity mismatches cause
the generation process to terminate.

\paragraph{\gls{fgsm}.}

The \gls{fgsm} implementation first preprocesses the clean image according to
the target-model normalization. The loss gradient is computed with respect to
the reference operational assignment in normalized model space and converted
to the corresponding pixel-space gradient. The adversarial tensor is then
produced as:

\begin{equation}
    \mathbf{x}_{\mathrm{adv}}
    =
    \operatorname{clip}_{[0,1]}
    \left(
        \mathbf{x}
        +
        \epsilon\,
        \operatorname{sign}
        \left(
            \nabla_{\mathbf{x}}
            \mathcal{L}(\mathbf{x},y)
        \right)
    \right),
\end{equation}

where \(y\) denotes the encoded reference operational assignment and
\(\epsilon = 8/255\). The resulting tensor is converted back to an RGB image
and stored as a lossless PNG file. The manifest records the clean and
adversarial predictions, maximum predicted-class probabilities,
reference-class probabilities, and pixel-space perturbation measurements.

\paragraph{One Pixel.}

The One Pixel implementation uses Differential Evolution to optimize the
location and RGB value of a single modified pixel. Each optimization candidate
contains five variables: horizontal coordinate, vertical coordinate, and the
three color-channel values. The objective minimizes the probability assigned
by the target proxy model to the reference operational class. Consistent with
the general formulation introduced in
Section~\ref{subsec:background_attack_families}, each candidate can be
represented by the parameter vector
\(\boldsymbol{\theta}=(u,v,r,g,b)\), where \((u,v)\) identifies the modified
pixel and \((r,g,b)\) specifies its replacement color. Let
\(T(\mathbf{x};\boldsymbol{\theta})\) denote the image obtained by applying
this modification. The implemented score-based optimization can be expressed
as:

\begin{equation}
    \min_{\boldsymbol{\theta}}
    p_y\!\left(T(\mathbf{x};\boldsymbol{\theta})\right)
    \qquad
    \text{subject to}
    \qquad
    \left|
        \left\{
            (i,j):
            T(\mathbf{x};\boldsymbol{\theta})_{ij}
            \neq
            \mathbf{x}_{ij}
        \right\}
    \right|
    \leq 1,
\end{equation}

where \(p_y(\cdot)\) is the probability assigned by the fold-specific target
model to the reference operational class \(y\). The constraint is expressed
over pixel locations rather than individual color components, since the three
RGB values of the selected pixel may change jointly.

A deterministic image-specific seed is derived from the base seed, condition
name, and stable image identifier through \gls{sha256}. This mechanism avoids
using an identical candidate sequence for every image while preserving
repeatability across executions. The optimization is terminated early when a
candidate causes the proxy prediction to differ from the reference operational
assignment. Regardless of whether this condition is achieved, the best
candidate identified during the search is exported and documented.

\paragraph{Sigma-Zero.}

Sigma-Zero was integrated through the reference implementation exposed by the
\texttt{adversarial-library} project rather than through a locally rewritten
version. The dependency is pinned to the inspected repository commit:

\begin{center}
\texttt{b14f81a3e1c414a573b969b402c99e65bfe2ca33}
\end{center}

The reference function expects unnormalized pixel tensors in the interval
\([0,1]\). A dedicated adapter therefore converts the FAIR-Lab
model-normalized input back to pixel space and exposes a wrapper that reapplies
the target-model normalization before forwarding the tensor to the
fold-specific proxy model. The attack is untargeted and aims to identify a
sparse adversarial perturbation by optimizing an approximation of the
\(\ell_0\)-norm objective. In implementation-oriented form, the underlying
untargeted sparse-perturbation problem can be written as:

\begin{equation}
    \min_{\mathbf{x}_{\mathrm{adv}} \in [0,1]^d}
    \left\|
        \mathbf{x}_{\mathrm{adv}}-\mathbf{x}
    \right\|_0
    \qquad
    \text{subject to}
    \qquad
    \operatorname*{arg\,max}_{k}
    f_k(\mathbf{x}_{\mathrm{adv}})
    \neq
    y,
\end{equation}

where \(f_k(\cdot)\) denotes the logit associated with class \(k\), \(y\) is
the reference operational class, and the \(\ell_0\) term counts the input
components modified relative to the clean image. The frozen implementation
approximates this discrete objective through the iterative optimization and
threshold-adjustment procedure summarized in
Table~\ref{tab:implementation-adversarial-parameters}.

\paragraph{SuperDeepFool.}

SuperDeepFool was implemented internally from the published
\(\mathrm{SDF}(\infty,1)\) procedure rather than by copying or vendoring an
external repository. The implementation first performs DeepFool-style
iterations to identify an adversarial boundary point. It subsequently applies
a SuperDeepFool projection based on the gradient difference between the
reference class and the boundary class. The corresponding
untargeted minimum-perturbation objective for the frozen
\(\mathrm{SDF}(\infty,1)\) configuration can be summarized as:

\begin{equation}
    \min_{\boldsymbol{\delta}}
    \left\|
        \boldsymbol{\delta}
    \right\|_{\infty}
    \qquad
    \text{subject to}
    \qquad
    \operatorname*{arg\,max}_{k}
    f_k(\mathbf{x}+\boldsymbol{\delta})
    \neq
    y,
    \qquad
    \mathbf{x}+\boldsymbol{\delta}
    \in [0,1]^d.
\end{equation}

At an adversarial boundary point \(\mathbf{x}_{b}\), the projection stage uses
the gradient difference between the boundary class \(k_b\) and the reference
class \(y\):

\begin{equation}
    \mathbf{w}_{b}
    =
    \nabla_{\mathbf{x}} f_{k_b}(\mathbf{x}_{b})
    -
    \nabla_{\mathbf{x}} f_{y}(\mathbf{x}_{b}).
\end{equation}

This local gradient difference defines the orientation used by the projection
step to seek a smaller \(\ell_{\infty}\)-bounded adversarial displacement.

When the projection remains adversarial, the projected point is retained. When
the projection returns to the original predicted class, the implementation
falls back to the adversarial boundary point identified by the DeepFool stage.
The manifest records the number of outer, DeepFool, and projection iterations,
the convergence state, and whether the projection preserved adversariality.

\paragraph{Color Shift.}

Color Shift modifies the RGB channels directly in the original image space and
then adjusts saturation and contrast. No proxy model is queried during
generation, and no attack-success value is assigned at this stage. The
condition is stored as JPEG rather than PNG because controlled recompression is
part of the frozen transformation configuration. The target-model field is set
to \texttt{model\_agnostic}, while checkpoint-related fields remain empty or
are marked as not applicable.

The model-dependent outputs are written under the structure:

\begin{center}
\codepath{attacks/adversarial/<attack_name>/efficientnet_b0/<fold>/<label>/}
\end{center}

\begin{center}

\end{center}

\end{equation}

differs from the reference operational assignment.

The generation-time indicator must be distinguished from the comparative
attack success rate computed by the evaluation pipeline. The generation-time
field describes the output of the target checkpoint for the generated artifact,
regardless of whether the corresponding clean sample was already
misclassified. The comparative attack success rate instead considers only
samples correctly classified by the same checkpoint under the clean condition
and measures the proportion of those samples rendered incorrect by the attack.

prediction transitions under the shared manipulated condition rather than an
adversarial transfer success rate. Generation-time records are retained for
traceability, whereas comparative quantitative results are reported in
Chapter~\ref{chap:results}.

expected 1\,000 outputs, with 200 samples per fold and 500 samples per binary
reference assignment. They also verify the uniqueness of the generated
identifiers and perturbed \gls{sha256} values. Existing attack directories and
run-specific manifests are not overwritten unless the explicit
\texttt{--force} option is supplied.

\subsection{Anti-Forensic Transformation Implementation}
\label{subsec:implementation-antiforensic}
% ─────────────────────────────────────────────────────────────────────────────

The anti-forensic transformation stage was implemented through:

\begin{center}
\codepath{datasets/scripts/attacks/13_generate_anti_forensic_attacks.py}
\end{center}

The script consumes the same canonical binary manifest used by the adversarial
generation stage:

\begin{center}
\codepath{datasets/splits/manifests/clean_folds_manifest.csv}
\end{center}

Accordingly, each transformation is applied to the complete set of 1\,000 clean
binary images, comprising 500 \texttt{weapon} and 500
\texttt{non\_weapon} samples. The 500 \gls{ood} inputs remain outside this
stage and are preserved in their clean form for the separate
out-of-distribution evaluation.

The frozen anti-forensic suite comprises five deterministic and model-agnostic
transformations:

\begin{itemize}
\item \gls{jpegrecompression};
\item \gls{resampleresize};
\item \gls{gaussianblur};
\item \gls{histogrammodification};
\item \gls{contraststretching}.
\end{itemize}

These transformations do not require access to model gradients, logits,
probabilities, or checkpoints. They implement common image post-processing
operations that modify compression characteristics, spatial detail, local
intensity distributions, or global contrast. The selected configurations were
intended to retain sufficient task-relevant semantic content for meaningful
evaluation. The reference operational assignment of each source image is
propagated unchanged to the corresponding transformed artifact and is not
reassessed during generation.

Before generation, the script validates the required manifest fields, the
exclusive use of the two accepted binary reference assignments, and the
uniqueness of the image identifiers. It also verifies the existence of every
clean input and recomputes its \gls{sha256} and \gls{md5} values. Generation is
interrupted when an input file is missing or when either recorded digest does
not correspond to the file being processed. \gls{sha256} remains the primary
integrity control, whereas \gls{md5} is retained as an auxiliary
interoperability identifier.

Each source image is opened using Pillow, corrected according to its embedded
orientation information through an EXIF transpose operation, and converted to
a three-channel RGB representation. The transformation-specific operation is
then applied, and the resulting image is stored as a \gls{jpeg} file. The
dedicated recompression condition uses quality 70. The remaining transformations
are serialized at quality 95 to limit, without eliminating, additional
compression effects beyond those introduced by the principal transformation.

\paragraph{\gls{jpegrecompression}.}

The recompression condition does not introduce an explicit spatial or tonal
transformation before serialization. Instead, the RGB representation is
re-encoded as a \gls{jpeg} image with quality 70. This condition implements a
controlled moderate lossy-recompression scenario involving quantization and
block-based coding artifacts, without applying the additional operations used
by the other transformation families.

\paragraph{\gls{resampleresize}.}

For an image with dimensions \(W \times H\), the intermediate dimensions are
computed as:

\begin{equation}
W_{\mathrm{down}}
=
\max\left(1,\operatorname{round}(0.5W)\right),
\qquad
H_{\mathrm{down}}
=
\max\left(1,\operatorname{round}(0.5H)\right).
\end{equation}

The image is first resized to
\(W_{\mathrm{down}} \times H_{\mathrm{down}}\) and then restored to
\(W \times H\). Both operations use bicubic interpolation. The final output
therefore retains the original spatial dimensions while incorporating the
information loss introduced by the intermediate downsampling and reconstruction
stages.

\paragraph{\gls{gaussianblur}.}

The Gaussian blur condition applies a radius of 1.5 to suppress high-frequency
spatial detail. The image dimensions and RGB representation remain unchanged
before final JPEG serialization. The transformation is deterministic and does
not depend on the reference operational assignment, assigned fold, or
proxy-model output.

\paragraph{\gls{histogrammodification}.}

Histogram Modification is implemented through per-channel histogram
equalization. The operation redistributes the available intensity values to
alter the tonal distribution of the image. No manually selected thresholds or
image-specific model outputs are used. The same deterministic operation is
applied to every sample in the binary subset.

\paragraph{\gls{contraststretching}.}

Contrast Stretching is implemented through automatic contrast normalization.
The transformation is applied using \texttt{ImageOps.autocontrast} with a
cutoff percentage of 1.0 before remapping the remaining intensity range. This
operation modifies the global tonal distribution while retaining the original
image dimensions and the source image's reference operational assignment.

The transformed images are written according to the structure:

\begin{center}
\codepath{attacks/anti_forensic/<transformation>/<fold>/<label>/}
\end{center}

Generated file names follow the pattern:

\begin{center}
\texttt{<image\_id>\_\_<transformation>.jpg}
\end{center}

The folder hierarchy retains both the deterministic fold assignment and the
binary reference assignment of the source image. No relabeling is performed
during generation, and the transformation name is recorded separately from the
reference operational assignment.

Each of the five conditions produces 1\,000 transformed files, distributed as
200 images per fold and 500 images per binary reference assignment. The
complete anti-forensic stage therefore produces:

\times

\end{equation}

The final checks also confirm the uniqueness of the generated image identifiers

Only the following flat directory was imported into the selected black-box
software systems:

\begin{center}

\end{center}

The metadata and structured audit directories were excluded from the imported
corpus. This separation prevents the evaluated systems from accessing
experiment-specific directory structures and prevents the analyst from
inferring the expected assignment or perturbation condition directly from the
file path during the initial evaluation. It does not conceal the visual content
of the image or any perturbation effect that is perceptible from the image
itself.

Every bundle item was assigned a sequential identifier using the format:

\begin{center}
\texttt{bundle\_000001}
\end{center}

through:

\begin{center}
\texttt{bundle\_011500}
\end{center}

The blind file name contains only the bundle identifier and the original file
extension, for example:

\begin{center}
\texttt{bundle\_000001.jpg}
\end{center}

or:

\begin{center}
\texttt{bundle\_000002.png}
\end{center}

The original extension is retained because the experimental conditions include
both JPEG-encoded and lossless PNG artifacts. No conversion, rescaling,
recompression, or metadata sanitization is performed by the bundle builder.
Files are copied without modifying their byte content.

The implementation explicitly checks blind file names against a collection of
forbidden semantic and experimental tokens. These tokens include the binary
assignment values, \gls{ood} indicators, perturbation names, fold identifiers,
and proxy-model names. Blind-path validation also requires the file stem to
correspond exactly to the assigned bundle identifier.

The structured audit view is maintained separately and reproduces the
experimental hierarchy. Clean inputs are organized by fold and reference
assignment; \gls{ood} inputs are maintained under the separate evaluation
branch; adversarial artifacts are organized by condition, target model, fold,
and reference assignment; and anti-forensic artifacts are organized by
transformation, fold, and reference assignment. Structured file names include
both the bundle identifier and the corresponding generated-image identifier.
This view supports internal verification but must not be used as input to the
black-box software systems.

The canonical bundle mapping is stored as:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_manifest.csv}
\end{center}

For each of the 11\,500 logical items, the manifest records:

\begin{itemize}
\item the assigned \texttt{bundle\_id} and blind input file name;
\item the sample type and perturbation family;
\item the perturbation name and target proxy model, when applicable;
\item the fold and reference operational assignment;
\item the source dataset;
\item the original and generated image identifiers;
\item the source manifest and source file path;
\item the blind and structured bundle paths;
\item the original, manifest-recorded, and copied-file hashes;
\item the hash-verification result;
\item the output size, extension, layout, and creation timestamp.
\end{itemize}

This mapping permits a black-box result associated only with an anonymized file
name to be reconnected, after export, to its source image, reference operational
assignment, fold, and experimental condition. The mapping is withheld during
the blind analysis and used only during the normalization stage described in
Section~\ref{subsec:implementation-normalization}.

A reduced hash-oriented mapping is also stored as:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}
\end{center}

Despite its file name, this record contains both \gls{sha256} and \gls{md5}
values. It associates the cryptographic digests with the bundle identifier,
blind file name, sample type, perturbation information, reference operational
assignment, and original and generated image identifiers. The auxiliary
\gls{md5} value supports matching against software systems that expose
MD5-oriented export fields, while \gls{sha256} remains the primary integrity
identifier.

During materialization, each copied file is hashed and compared with the value
recorded in its originating manifest. The bundle summary confirms that all
manifest-recorded hashes correspond to the copied files. It also verifies that
the 11\,500 bundle identifiers and logical-item \gls{sha256} values are unique.

The principal run-level record is:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_summary.json}
\end{center}

The summary records the bundle layout, output locations, counts by sample type,
perturbation family, perturbation name, and reference operational assignment,
together with the following validation conditions:

\begin{itemize}
\item uniqueness of all bundle identifiers;
\item uniqueness of all logical-item \gls{sha256} values;
\item agreement between copied-file and manifest-recorded hashes;
\item absence of forbidden semantic and experimental tokens from blind
paths;
\item separation of internal metadata from the black-box input directory.
\end{itemize}

All five checks were satisfied by the frozen bundle.

An additional audit examines metadata embedded within the image files
themselves. The audit is implemented as a non-destructive inspection and
produces:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/embedded_metadata_audit.csv}
\end{center}

and:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/embedded_metadata_audit_summary.json}
\end{center}

For each blind input, the procedure inspects readable image-information fields
and EXIF entries and searches them for terms that could expose binary
assignments, perturbation conditions, fold identifiers, model names, or other
experiment-revealing descriptors. The audit does not remove or rewrite
metadata because doing so would change the files supplied to the selected
black-box software systems. Its purpose is to document this potential
information channel and support a separate sensitivity assessment. The audit
does not by itself establish that any evaluated system accessed or used the
identified metadata. The corresponding findings are reported in
Section~\ref{subsec:results-embedded-metadata-sensitivity}.

The bundle can be generated in blind-only, structured-only, or combined mode.
The frozen execution used the combined layout. It materialized the same
11\,500 logical items in both the blind and structured views, resulting in
11\,500 files per view. Rebuilding an existing bundle requires the explicit
\texttt{--force} option, which removes the previous bundle directory before
materializing the new corpus.

The completed bundle provides a stable and auditable input population for the
selected black-box software systems. The concrete versions, import procedures,
classification categories, retrieval configurations, and export formats adopted
for those systems are documented in
Section~\ref{sec:implementation-forensic-tools}.

as a reconstruction of the internal \gls{magnetai} decision boundary or as

platform did not expose a numerical confidence value suitable for direct
comparison with the proxy-model probabilities.

not match the defined weapon-oriented rule. These values are recorded as
unmapped software outputs and assigned to the common normalized

class. This defensive rule prevents an unrelated or previously unseen tag from

This blind-input design concealed experiment-specific descriptors encoded in
the file-system structure. It did not conceal the visual content of the images
or perturbation effects directly perceptible from the inputs.

The same fixed set of eight firearm-oriented English prompts was used for each
semantic-distance configuration:

\begin{enumerate}
\item \texttt{firearm};
\item \texttt{gun};
\item \texttt{pistol};
\item \texttt{handgun};
\item \texttt{revolver};
\item \texttt{rifle};
\item \texttt{shotgun};
\item \texttt{assault rifle}.
\end{enumerate}

The prompt set was defined before the frozen evaluations and was not modified
on the basis of the observed results. In particular, the broader term
\texttt{weapon} was not included because the experimental positive class was
firearm-oriented rather than a general category encompassing all possible
weapons.

Each prompt was executed separately under the three distance-limit settings
20, 50, and 80. This procedure produced 24 prompt-level exports:

\begin{equation}
8\ \text{fixed prompts}
\times
3\ \text{distance settings}
=
24\ \text{export files}.
\end{equation}

The exports were named according to the pattern:

\begin{center}
\texttt{excire\_<prompt>\_distance<limit>.csv}
\end{center}

For file-system compatibility, the multiword prompt
\texttt{assault rifle} was represented as \texttt{assault\_rifle} in the
export file name. The prompt and distance configuration can therefore be
reconstructed deterministically from each export name.

The Excire exports are retrieval hit lists rather than complete classification
tables. Each file contains the paths of the images returned for one prompt
under one distance setting, generally as a headerless list with one path per
line. An image may occur in multiple prompt exports when it is retrieved by
more than one query. Conversely, an image absent from an individual export does
not produce an explicit negative row in that file.

For each distance configuration, the eight hit lists were combined through a
set-union rule. An image was assigned a positive operational decision when it
was retrieved by at least one fixed prompt:

\begin{equation}
\bigvee_{p \in \mathcal{P}}
\operatorname{retrieved}(x,p)
=
\texttt{true}
\quad\Longrightarrow\quad
\texttt{weapon\_detected = true},
\end{equation}

where \(\mathcal{P}\) denotes the frozen set of eight prompts.

Images not retrieved by any prompt under the same distance configuration were
completed against the canonical 11\,500-item bundle and assigned:

\begin{equation}
\bigwedge_{p \in \mathcal{P}}
\neg\operatorname{retrieved}(x,p)
\quad\Longrightarrow\quad
\texttt{weapon\_detected = false}.
\end{equation}

The resulting normalized prediction was therefore:

\begin{equation}
\texttt{normalized\_prediction}
=
\begin{cases}
\texttt{weapon},
& \text{if at least one fixed prompt retrieved the image},\\
\texttt{non\_weapon},
& \text{otherwise}.
\end{cases}
\end{equation}

This rule is an operational recoding of semantic-retrieval membership. It does
not imply that \gls{excirefoto2025} internally performs binary
\texttt{weapon}/\texttt{non\_weapon} classification. Similarly, the distance
settings are software-specific retrieval parameters and must not be interpreted
as calibrated probabilities or as directly comparable confidence thresholds.

The three distance settings were retained as separate system configurations
throughout normalization and metric computation. Their retrieval results were
not merged into a single combined Excire decision. Each setting therefore
produced a complete table of 11\,500 normalized predictions, allowing the
observable behavior associated with each retrieval configuration to be
analyzed independently.

For auditability, the normalized records preserve both the union decision and
the individual prompt memberships. Each row includes:

\begin{itemize}
\item the semantic-distance limit;
\item the complete frozen prompt set;
\item the number of prompts that retrieved the image;
\item the list of prompts producing a hit;
\item one binary hit indicator for each of the eight prompts;
\item the bundle identifier, hashes, sample type, experimental condition,
fold, reference operational assignment, and source-image identifiers;
\item the resulting \texttt{weapon\_detected} and normalized-prediction
fields.
\end{itemize}

This representation preserves distinctions that would be lost by retaining
only the final binary decision. Two images may, for example, both be normalized
as positive even though one was retrieved by a single prompt and the other by
several semantically related prompts.

The three frozen runs produced separate prompt-level export sets. After union
and completion against the canonical bundle, every configuration contained
exactly one normalized prediction for each of the 11\,500 bundle items, and no
bundle image remained unmatched. This complete matching establishes output
coverage for every bundle item but does not establish the correctness of the
derived binary decisions. The corresponding retrieval volumes and their
sensitivity to the distance setting are reported in
Section~\ref{subsec:results-excire}.

\begin{center}
\codepath{forensic_tools/excire_foto_2025/raw_exports/}
\end{center}

The 24 original CSV files contained local Windows paths in addition to the
anonymized bundle file names. They were therefore retained under the
controlled-access policy rather than distributed through the public repository.

The public repository preserves a sanitized extract containing bundle
identifiers, distance configurations, prompt-membership information, and
normalized decision fields:

\begin{center}
\codepath{forensic_tools/excire_foto_2025/public_extracts/excire_prompt_hits_extract.csv}
\end{center}

The corresponding normalized configurations and metric outputs are stored
separately as:

\begin{center}
\texttt{excire\_foto\_2025\_d20},
\qquad
\texttt{excire\_foto\_2025\_d50},
\qquad
\texttt{excire\_foto\_2025\_d80}.
\end{center}

A single image may be associated with multiple exported classifications, with
each label optionally followed by a percentage value. Representative field
structures include:

\begin{center}
\texttt{Armi (100\%)}
\end{center}

\begin{center}
\texttt{Pistola (100\%); Armi (100\%)}
\end{center}

and:

\begin{center}
\texttt{Fucile (91\%) | Oggetto tenuto in mano (78\%)}
\end{center}

The parser separates labels expressed through semicolons, vertical bars,
commas, or line breaks and removes the parenthesized percentage values before
applying the operational mapping. The percentages are preserved only as part of
the raw observable output. They are not treated as calibrated probabilities and
do not influence the binary decision.

The frozen mapping assigns a positive decision when the observable
\texttt{Classifications} field contains at least one of the following labels:

\begin{itemize}
\item \texttt{Armi};
\item \texttt{Pistola};
\item \texttt{Fucile}.
\end{itemize}

Formally, the operational recoding is:

\begin{equation}
\left\{
\texttt{Armi},
\texttt{Pistola},
\texttt{Fucile}
\right\}
\cap
\mathcal{C}(x)
\neq
\varnothing
\quad\Longrightarrow\quad
\texttt{weapon\_detected = true},
\end{equation}

where \(\mathcal{C}(x)\) denotes the set of normalized classifications exported
for image \(x\).

For every other successfully matched bundle record, the software-specific
decision is:

\begin{equation}
\left\{
\texttt{Armi},
\texttt{Pistola},
\texttt{Fucile}
\right\}
\cap
\mathcal{C}(x)
=
\varnothing
\quad\Longrightarrow\quad
\texttt{weapon\_detected = false}.
\end{equation}

The corresponding common normalized states are:

\begin{equation}
\texttt{weapon\_detected = true}
\longrightarrow
\texttt{weapon},
\end{equation}

\begin{equation}
\texttt{weapon\_detected = false}
\longrightarrow
\texttt{non\_weapon}.
\end{equation}

The inclusion of \texttt{Pistola} and \texttt{Fucile} alongside the broader
\texttt{Armi} label defines the extended mapping used for the frozen thesis
evaluation. This prevents firearm-specific positive classifications from being
discarded merely because the broader \texttt{Armi} category is absent from the
same exported field.

This rule is an operational recoding of an observable software output. It does
not imply that \gls{cellebriteinseyets} internally implements the same binary
taxonomy, that the exported labels are mutually exclusive, or that the
associated percentage values represent directly comparable model
probabilities.

The original report contained 11\,829 image rows. Of these, 11\,500 were
matched to the complete forensic evaluation bundle, whereas 329 rows did not
correspond to bundle items. The unmatched records were retained as an aggregate
audit count and excluded from the quantitative robustness analysis. Complete
bundle coverage confirms that a matched exported decision was available for
every experimental item but does not establish classification correctness.

The matching procedure associates report records with the canonical bundle
through available cryptographic hashes, anonymized file names, and bundle
identifiers. For each successfully matched record, the normalized output
retains:

\begin{itemize}
\item the \texttt{bundle\_id} and input file name;
\item the matching method and matched state;
\item the available \gls{sha256} and \gls{md5} values;
\item the clean, \gls{ood}, or perturbed sample type;
\item the perturbation family and condition;
\item the fold and reference operational assignment;
\item the original and generated image identifiers;
\item the original \texttt{Classifications} value;
\item the normalized binary decision and mapping reason.
\end{itemize}

The heterogeneous outputs produced by the selected black-box software systems

\begin{center}

The implementation reads the controlled-access raw exports associated with the

evaluation bundle. The primary normalization inputs are:

\end{center}

and:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}
\end{center}

These records provide the mapping among anonymized software-input files,
cryptographic hashes, reference operational assignments, folds, sample types,
perturbation conditions, source-image identifiers, and generated-image
identifiers. The reference assignments and experimental metadata are joined to
the observable software outputs only during this post-export stage and are not
provided to the evaluated systems during analysis.

The normalization pipeline processes four software families while retaining
the three \gls{excirefoto2025} distance settings as distinct configurations.
The resulting normalized configuration identifiers are:

\begin{itemize}
\item \texttt{magnet\_axiom};
\item \texttt{griffeye};
\item \texttt{cellebrite\_inseyets};
\item \texttt{excire\_foto\_2025\_d20};
\item \texttt{excire\_foto\_2025\_d50};
\item \texttt{excire\_foto\_2025\_d80}.
\end{itemize}

Each normalized configuration is evaluated against the same 11\,500-item
bundle. The canonical normalized population therefore contains:

\begin{equation}
6\ \text{configurations}
\times
11\,500\ \text{bundle items}
=
69\,000\ \text{matched decisions}.
\end{equation}

\paragraph{Bundle indexing and record matching.}

When the bundle metadata is loaded, the implementation constructs three lookup
indexes:

\begin{enumerate}
\item a \gls{sha256}-based index;
\item an \gls{md5}-based index;
\item an anonymized file-name index.
\end{enumerate}

For conventional row-oriented exports, each parsed software record is matched
according to the following priority:

\begin{center}
\texttt{SHA-256}
\(\succ\)
\texttt{MD5}
\(\succ\)
\texttt{exact file name}
\(\succ\)
\texttt{file name embedded in an exported path or text field}.
\end{center}

The matching method is preserved explicitly in the normalized record. This
allows subsequent verification of whether an association was established
through the primary cryptographic identifier or through a fallback identifier
exposed by the software export.

Hash values are normalized before comparison by removing separators and
non-hexadecimal formatting characters. File-system paths are reduced to their
base file names before lookup so that differences between Windows paths and
repository-relative directory structures do not prevent association with the
blind bundle.

The \gls{excirefoto2025} workflow requires a distinct matching procedure
because its exports contain only the images retrieved by each semantic query.
The anonymized file names listed in the eight prompt-level hit lists are first
mapped to bundle items. The union of those hits is then completed against the
full bundle manifest, thereby producing an explicit operational decision for
every image, including those absent from all prompt exports.

\texttt{weapon\_detected} state according to the frozen rules summarized in

\paragraph{Common normalized schema.}

The normalized representation separates software-observable information from
the reference assignments and experimental metadata recovered from the bundle.
Its principal fields include:

\begin{itemize}
\item \texttt{tool\_name}, \texttt{bundle\_id},
\texttt{matched}, and \texttt{match\_method};

\item \texttt{sample\_type}, \texttt{attack\_family},
\texttt{attack\_name}, and \texttt{attack\_target\_model};

\item \texttt{fold}, \texttt{final\_label}, and
\texttt{source\_dataset};

\item \texttt{original\_image\_id} and
\texttt{generated\_image\_id};

\item the anonymized input file name and available \gls{sha256} and
\gls{md5} values;

\item the original exported label, tag, classification, bookmark, or
prompt-membership information;

\item \texttt{weapon\_detected},
\texttt{normalized\_prediction}, and
\texttt{mapping\_reason};

\item binary correctness, false-negative, and false-positive indicators
when the reference operational assignment is \texttt{weapon} or
\texttt{non\_weapon}.
\end{itemize}

The literal field name \texttt{final\_label} is preserved because it belongs to
the implemented schema; semantically, its value represents the reference
operational assignment inherited from the frozen bundle.

Software-specific information is retained in additional fields rather than
being discarded after binary recoding. These fields include the original AXIOM
tags, Cellebrite classifications, Excire distance limit and per-prompt hit
indicators, and the primary and secondary Griffeye bookmarks.

The schema therefore supports structured cross-system comparison without
discarding the observable evidence from which each normalized decision was
derived.

For records whose reference assignment is \texttt{ood}, the binary correctness,
false-negative, and false-positive fields are left undefined. An \gls{ood}
input is not treated as either a positive or a negative reference instance. Its
normalized \texttt{weapon\_detected} state is preserved separately and is later
used to compute the \gls{ood} weapon-flag rate.

\paragraph{Deduplication and completeness.}

Some software exports may contain more than one record associated with the same
bundle item. The normalizer therefore supports deterministic consolidation to
one row per normalized configuration and bundle identifier.

When several matched rows refer to the same pair, the consolidated decision is
selected according to the following conservative rule:

\begin{enumerate}
\item if at least one row contains a positive decision, the consolidated
result is positive;

\item otherwise, if at least one row contains an explicit negative
decision, the consolidated result is negative;

\item otherwise, the consolidated result is \texttt{unknown}.
\end{enumerate}

The consolidation procedure retains the combined export-file references, row
numbers, observable labels, mapping reasons, and raw-row count. When an
explicit software-specific numerical value is available, the maximum exported
value may be preserved as part of the original observable record. Such values
are not converted into a common calibrated confidence measure, and no
confidence value is fabricated for systems that do not expose one.

Unmatched records are excluded from the canonical prediction table because they
do not belong to the official forensic evaluation bundle. They remain
documented through the export audit and separate unmatched-record outputs.

After software-specific parsing and the preliminary exclusion of the 553
non-bundle Griffeye records, the normalization workspace contained 69\,329
candidate records. This population comprised the expected 69\,000 bundle-level
decisions and 329 unmatched Cellebrite report records. Excluding the latter
produced exactly 69\,000 matched normalized decisions:

\begin{equation}
69\,329
-
329
=
69\,000.
\end{equation}

This final count corresponds to complete coverage of the 11\,500-item bundle
for all six normalized configurations. No matched bundle decision remained
without a common normalized state after the frozen mappings were applied.
Complete coverage establishes output availability and successful matching; it
does not establish classification correctness.

\paragraph{Binary metric computation.}

For each binary evaluation group, the implementation derives the confusion
matrix using the fixed layout:

\begin{equation}
\begin{bmatrix}
\mathrm{TN} & \mathrm{FP} \\
\mathrm{FN} & \mathrm{TP}
\end{bmatrix}.
\end{equation}

The resulting metric records contain:

\begin{itemize}
\item accuracy and balanced accuracy;
\item class-specific precision, recall, and F1-score;
\item macro-averaged precision, recall, and F1-score;
\item \gls{tp}, \gls{tn}, \gls{fp}, and \gls{fn} counts;
\item \gls{fpr} and \gls{fnr};
\item misclassification rate;
\item \texttt{weapon}-to-\texttt{non\_weapon} and
\texttt{non\_weapon}-to-\texttt{weapon} error counts;
\item mean maximum predicted-class probability.
\end{itemize}

The \gls{fpr} and \gls{fnr} are implemented as:

\begin{equation}
\mathrm{FPR}
=
\frac{\mathrm{FP}}
{\mathrm{FP}+\mathrm{TN}},
\qquad
\mathrm{FNR}
=
\frac{\mathrm{FN}}
{\mathrm{FN}+\mathrm{TP}}.
\end{equation}

Clean proxy-model metrics are grouped by architecture. Adversarial-stage
metrics are grouped by evaluated architecture, perturbation condition, and
attack target model. This grouping includes the four model-dependent
adversarial attacks and the model-agnostic Color Shift condition.
Anti-forensic metrics are grouped by evaluated architecture and transformation
condition.

The attack-target field is retained because the model-dependent adversarial
artifacts were generated against fold-aware EfficientNet-B0 checkpoints but
were subsequently evaluated by all three proxy architectures. This distinction
supports separate analysis of direct target-model behavior and cross-model
transfer. Color Shift remains explicitly marked as model-agnostic and is not
interpreted as a transfer attack.

The maximum predicted-class probabilities are retained as intra-model
diagnostic values. They are not assumed to be calibrated across architectures
and are not used as directly comparable confidence measures between ResNet18,
EfficientNet-B0, and the \gls{clip}-based proxy.

\paragraph{Clean-to-perturbed comparison.}

Each perturbed prediction is associated with its corresponding clean prediction
through the tuple:

\begin{center}
\texttt{evaluated\_model},
\quad
\texttt{evaluation\_fold},
\quad
\texttt{original\_image\_id}.
\end{center}

The prediction table is enriched with the clean prediction, clean correctness
state, clean class probabilities, clean maximum probability, and probability
difference relative to the perturbed input.

For each proxy model and perturbation condition, the comparative layer
computes:

\begin{itemize}
\item clean accuracy and perturbed accuracy;
\item the schema field \texttt{robust\_accuracy}, whose stored value is
equivalent to the perturbed accuracy;
\item accuracy drop;
\item clean and perturbed macro F1-scores;
\item macro F1-score drop;
\item induced-error count and induced-error rate;
\item attack success rate for model-dependent adversarial attacks;
\item mean maximum-probability shift;
\item directional error counts and rates.
\end{itemize}

The term \texttt{robust\_accuracy} is retained because it is part of the
implemented comparative schema. It does not denote a separate quantity from
the perturbed-condition accuracy.

Let \(\mathcal{C}_{\mathrm{clean}}\) denote the set of samples correctly
classified under the corresponding clean condition. The induced-error rate for
perturbation condition \(p\) is implemented as:

\begin{equation}
    \mathrm{IER}_{p}
    =
    \frac{
        \left|
        \left\{
        i \in \mathcal{C}_{\mathrm{clean}}
        :
        \hat{y}^{(p)}_{i} \neq y_{i}
        \right\}
        \right|
    }{
        \left|
        \mathcal{C}_{\mathrm{clean}}
        \right|
    }.
\end{equation}

Images already misclassified in the clean condition are excluded from this
denominator because they cannot represent newly induced errors.

For the four model-dependent adversarial attacks, this clean-correct transition
rate is also reported as the attack success rate. For Color Shift and the five
anti-forensic transformations, the same transition is reported as an
induced-error rate and is not interpreted as adversarial attack success or
transfer success.

The maximum-probability shift is computed as:

\begin{equation}
\Delta c
=
c_{\mathrm{perturbed}}
-
c_{\mathrm{clean}},
\end{equation}

and averaged within each model--condition group. This quantity compares the
maximum predicted-class probability before and after perturbation. It does not
necessarily compare the probability assigned to the same class when the
predicted class changes, and it is used only as an intra-model diagnostic.

\paragraph{Proxy-model \gls{ood} metrics.}

The \gls{ood} branch is summarized independently for each proxy architecture.
The resulting records contain:

\begin{itemize}
\item the fold-aggregated number of checkpoint responses;
\item the number and rate of predictions assigned to \texttt{weapon};
\item the number of predictions assigned to \texttt{non\_weapon};
\item the mean maximum predicted-class probability;
\item the high-confidence threshold;
\item the number and rate of predictions whose maximum probability meets
or exceeds that threshold.
\end{itemize}

The frozen high-confidence threshold is:

\begin{equation}
\tau_{\mathrm{high}}
=
0.90.
\end{equation}

The high-confidence count includes predictions assigned to either binary class.
It characterizes confident closed-set assignment of an \gls{ood} input. The
predicted-weapon rate instead characterizes the operational tendency to flag
\gls{ood} content as firearm-related.

Neither quantity represents supervised correctness because the \gls{ood}
branch has no positive or negative binary reference assignment. The associated
probabilities remain architecture-specific diagnostic outputs and are not
treated as calibrated across proxy models.

\paragraph{Case-selection procedure.}

diagnostic buckets:

\begin{enumerate}
\item a correctly classified clean \texttt{weapon} image;
\item a clean \texttt{weapon} false negative;
\item a high-confidence \gls{ood} input assigned to the
\texttt{weapon} class;
\item a clean-correct image rendered incorrect by an anti-forensic
transformation;
\item a clean-correct image rendered incorrect with high maximum
predicted-class probability by a model-dependent adversarial attack.
\end{enumerate}

maximum predicted-class probability, fold, and input path.
Perturbation-induced failures are additionally ranked according to a predefined
diagnostic priority: \texttt{weapon}-to-\texttt{non\_weapon} transitions are
considered first, followed by
\texttt{non\_weapon}-to-\texttt{weapon} transitions and other induced
misclassifications.

human review, producing a 15-case intermediate selection. The reviewer

predicted-class probability, perturbation condition, and selection rationale.

ranks, case identifiers, and pseudonymous reviewer identifier.

\paragraph{Attribution processing and visual outputs.}

For each attribution target, the channel-wise attribution tensor is converted
into a two-dimensional map by summing the absolute attribution magnitudes
across the three input channels. The resulting map is min--max normalized to
the interval \([0,1]\).

Because absolute values are used, the visualizations represent attribution
magnitude rather than contribution direction. They identify image regions
associated with larger attribution magnitudes for the selected model output
along the baseline-to-input path, but they do not distinguish positive evidence
from negative evidence.

The implementation produces the following diagnostic outputs for each case:

\begin{itemize}
\item the resized RGB input image;
\item a colorized attribution heatmap;
\item an overlay combining the input and heatmap;
\item a normalized grayscale attribution mask;
\item a binary mask containing pixels at or above the selected attribution
percentile;
\item a side-by-side diagnostic comparison;
\item a histogram of normalized attribution values.
\end{itemize}

The heatmap uses the \texttt{inferno} color map. The overlay combines the
resized input with the colorized heatmap using an attribution opacity of 0.45.
The binary high-attribution mask is computed from the 90th percentile of the
normalized map and therefore identifies approximately the 10\% of image
locations with the highest attribution magnitudes. The exact proportion may
vary when multiple locations share the percentile threshold.

The thesis retains four visual assets for each of the five selected cases:

\begin{enumerate}
\item input image;
\item standalone heatmap;
\item heatmap overlay;
\item top-10\% attribution mask.
\end{enumerate}

\paragraph{Convergence diagnostics.}

The historical thesis images were generated using 32 integration steps. The

acceptance rule introduced later in the hardened entry point. They are
therefore interpreted as qualitative diagnostic visualizations, and no strict

The hardened entry point additionally supports adaptive convergence
diagnostics. Starting from the requested number of integration steps, the
procedure can double the integration resolution until the normalized
convergence delta is at most 0.05 or the maximum of 256 steps is reached. A
regenerated case is marked as \texttt{passed} only when the threshold is
satisfied; otherwise, the state \texttt{threshold\_not\_met} is retained.

This adaptive functionality was introduced after the historical 32-step assets
had been generated and was not used to produce the figures analyzed in this
thesis. It is therefore documented as an available validation control rather
than as a property of the retained thesis assets.

\section{Traceability, Integrity, and Reproducibility Controls}
\label{sec:implementation-traceability}

Traceability, integrity, and controlled reproducibility were implemented as
cross-cutting properties of the complete experimental workflow rather than as
controls added only after evaluation. The resulting framework links the frozen
dataset, deterministic partitions, proxy-model checkpoints, derived
perturbations, black-box inputs, normalized software outputs, metric tables,
explainability cases, and reporting assets through stable identifiers,
cryptographic digests, manifests, and version-controlled metadata.

The implementation distinguishes three related but non-equivalent objectives:

\begin{itemize}
\item \emph{traceability}, defined as the ability to reconstruct the
provenance and processing history of an experimental input, derived
artifact, model, or result record;

\item \emph{integrity}, defined as the ability to verify that an input,
artifact, model, or record has not changed relative to its canonical
recorded state;

\item \emph{controlled reproducibility}, defined as the ability to inspect
or rerun the workflow to the extent permitted by data-access restrictions,
licensed-software requirements, and the available execution environment.
\end{itemize}

This distinction is necessary because public access to code and metadata does
not imply unrestricted redistribution of the source images or availability of
the proprietary software required to repeat the black-box processing.

\paragraph{Stable identity and provenance chain.}

The pipeline assigns stable identifiers at successive processing stages.
Prepared source images receive an \texttt{image\_id}; generated perturbations
receive a \texttt{generated\_image\_id}; black-box inputs receive an anonymized
\texttt{bundle\_id}; and selected explainability cases receive a
\texttt{case\_id}. Model checkpoints are identified through the combination of
proxy architecture and held-out fold.

The resulting provenance chain can be represented as:

\begin{equation}
\begin{split}
\texttt{image\_id}
&\longrightarrow
\texttt{generated\_image\_id}
\longrightarrow
\texttt{bundle\_id} \\
&\longrightarrow
\texttt{normalized\_prediction}
\longrightarrow
\texttt{metric\_row}
\longrightarrow
\texttt{reporting\_asset}.
\end{split}
\end{equation}

For clean binary samples and \gls{ood} inputs, the original and generated
identifiers may coincide because no new derived image artifact is created. For
adversarial and anti-forensic artifacts, the generated identifier preserves the
association with the corresponding clean source image while distinguishing the
perturbation condition and, where applicable, the target proxy model.

The manifests retain repository-relative paths rather than relying on
machine-specific absolute locations. This allows outputs generated on different
workstations to be associated with the same logical repository structure. Run
summaries and registries additionally preserve configurations, creation
timestamps, sample counts, fold assignments, and output locations.

\paragraph{Cryptographic integrity controls.}

\gls{sha256} is the primary integrity digest throughout the pipeline.
\gls{md5} is retained only as an auxiliary interoperability identifier because
some forensic software exports expose MD5-oriented fields or matching
workflows. It is not treated as the primary integrity mechanism.

Per-file hashes are recorded at the principal transformation and transfer
boundaries, including:

\begin{itemize}
\item prepared and frozen source images;
\item deterministic clean and \gls{ood} partitions;
\item adversarial and anti-forensic artifacts;
\item blind and structured bundle copies;
\item proxy-model checkpoints;
\item selected explainability inputs and their fold-specific checkpoints;
\item sanitized black-box software extracts and canonical metric records.
\end{itemize}

Thesis-level explainability outputs are validated through their canonical
manifest paths, selection metadata, and reporting-asset audits rather than
being treated as independently hash-authenticated model artifacts.

Whenever a file is copied between stages, the destination hash is recomputed
and compared with the canonical value recorded in the originating manifest. A
mismatch causes the relevant script to terminate rather than silently accepting
a different file.

The checkpoint digests stored in:

\begin{center}
\codepath{models/model_registry.json}
\end{center}

bind every proxy architecture and held-out fold to the corresponding serialized
model checkpoint. These values are checked before model-dependent adversarial
generation and by the hardened explainability entry point.

Archive-level integrity is maintained separately from per-file integrity. The
canonical controlled-archive digests are stored in:

\begin{center}
\codepath{docs/artifact/CONTROLLED_ARTIFACT_CHECKSUMS.sha256}
\end{center}

The complete-archive digest authenticates the downloaded ZIP file, whereas:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}
\end{center}

supports verification of each of the 11\,500 restored blind inputs
individually. This distinction prevents a valid archive-level digest from
replacing verification of the expected file population after extraction.

\paragraph{Deterministic configuration controls.}

A fixed seed of 42 is used for the principal stochastic procedures, including
fold construction, internal training--validation partitioning, and
image-specific randomized search initialization where applicable. The seed is
recorded in the corresponding configuration and summary records.

The use of a fixed seed supports repeatability of the logical partitions and
pseudo-random initialization. It does not imply that every numerical result is
guaranteed to be bit-identical across different operating systems, hardware
architectures, library versions, or CPU and GPU implementations. PyTorch and
cuDNN deterministic options reduce nondeterministic behavior where supported,
but the execution environment remains part of the reproducibility boundary.

The frozen configurations also specify:

\begin{itemize}
\item accepted assignment values and expected group counts;
\item the five clean folds and separate \gls{ood} branch;
\item preprocessing and normalization parameters;
\item training hyperparameters;
\item perturbation parameters;
\item model and checkpoint associations;
\item black-box software versions and observable-output mappings;
\item metric definitions and confusion-matrix layout;
\item explainability target, baseline, integration steps, and selection
criteria.
\end{itemize}

These values are stored in machine-readable CSV or JSON records rather than
being represented only in narrative documentation.

\paragraph{Overwrite and rerun controls.}

The principal generation and evaluation scripts implement fail-visible output
guards. Existing canonical outputs are not silently replaced. A rebuild
generally requires the explicit \texttt{--force} option, which removes or
replaces only the output scope associated with the selected run.

This policy reduces the risk of combining outputs generated under different
configurations or overwriting a frozen result with a partial diagnostic
execution. Partial experiments and exploratory runs must use separate output
locations and must not replace the canonical manifests, predictions, or metric
tables.

An explicit forced rebuild does not by itself establish equivalence with the
frozen research artifact. The regenerated files must still satisfy the expected
counts, identifier constraints, integrity values, and downstream validation
procedures.

\paragraph{Audit summaries and machine-readable invariants.}

Each major stage produces sample-level records and a run-level summary. The
summary files record input manifests, parameters, output paths, expected and
actual counts, validation results, and creation metadata. This design permits
structural checks to be performed without reopening every image or manually
inspecting every prediction.

The principal invariants include:

\begin{itemize}
\item 1\,500 records in the frozen dataset;
\item 1\,000 binary samples and 500 \gls{ood} inputs;
\item five folds containing 200 binary images each;
\item 15 fold-aware proxy-model checkpoints;
\item 5\,000 adversarial and 5\,000 anti-forensic artifacts;
\item 11\,500 unique forensic evaluation bundle items;
\item 40\,500 proxy-model prediction rows;
\item 69\,000 canonical sanitized black-box software decisions;
\item 186 black-box software metric rows;
\item five canonical thesis-level explainability cases and 20 associated
thesis assets.
\end{itemize}

These counts are implementation invariants and completeness checks. Their
presence does not establish model or software robustness; the quantitative
behavior of the evaluated systems is analyzed separately in
Chapter~\ref{chap:results}.

The complete black-box software raw exports are excluded from the public

The canonical table can be reconstructed through:

\paragraph{Environment and security boundary.}

The pipeline was developed using Python virtual environments in Windows and
Linux environments, including Windows PowerShell and Kali Linux, with CPU- or
CUDA-enabled execution selected according to the computational stage.
Black-box evaluation additionally requires compatible licensed software and a
suitable workstation.

The repository records the dependency specification and operational setup but
does not claim to reproduce a byte-identical operating-system environment.
Exact usernames, credentials, API keys, signed download URLs, commercial
license information, session data, and unnecessary local absolute paths are
excluded.

The public branch also excludes:

\begin{itemize}
\item unrestricted copies of the image corpora;
\item complete raw black-box software exports;
\item proprietary case databases;
\item evidence-related material not required for the experimental record;
\item private or temporary artifact-access URLs;
\item generated LaTeX auxiliary files.
\end{itemize}

This minimization preserves the information required to audit the experimental
claims while reducing disclosure of unrelated sensitive or proprietary
material.

\paragraph{Version control and artifact freezing.}

Source code, manifests, registries, sanitized decisions, metric tables,
documentation, and thesis sources are maintained through Git version control.
Large proxy-model checkpoints are managed through Git LFS, while their
\gls{sha256} values remain recorded in the model registry.

The repository policy treats the thesis research artifact as a versioned frozen
object. Substantive changes to the data, perturbations, checkpoints, normalized
decisions, metrics, or thesis conclusions require a new versioned release
rather than silent replacement of the existing frozen state. Documentation
corrections, security fixes, and non-substantive archival improvements must
remain clearly distinguishable from changes to the experimental evidence.

Taken together, these controls provide a traceable connection between the
implemented protocol and the results reported in the following chapter. They
do not eliminate the limitations associated with controlled data access,
hardware and software variation, human review, or proprietary black-box
systems. Instead, they make these boundaries explicit and preserve the
information required to audit the evaluation within them.

Chapter~\ref{chap:results} presents the quantitative outcomes obtained from the
frozen implementation and analyzes their implications for the operational
robustness of the evaluated proxy models and selected black-box software
systems.
