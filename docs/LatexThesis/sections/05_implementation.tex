\chapter{Implementation and Experimental Setup}
\label{chap:implementation}
% ─────────────────────────────────────────────────────────────────────────────

This chapter documents the concrete implementation of the \gls{fairlab}
methodology introduced in Chapter~\ref{chap:methodology}. It describes the
preparation and freezing of the image corpus, deterministic data partitioning,
fold-aware proxy-model training, adversarial and anti-forensic artifact
generation, construction of the forensic evaluation bundle, normalization of
black-box software outputs, explainability analysis, and the controls used to
preserve artifact identity, provenance, integrity, and reproducibility.

The chapter reports how the protocol was instantiated and which technical
artifacts were produced. Quantitative outcomes and their operational
interpretation are reported separately in Chapter~\ref{chap:results}, preventing
implementation choices, software configurations, and data-management
procedures from being conflated with measured robustness.

Both evaluation levels operate on the same frozen source population. The
1\,000 clean binary images and 500 clean \gls{ood} images constitute the source
corpus, while 10\,000 adversarial and anti-forensic artifacts are derived
exclusively from the binary subset. The proxy models process manifest-linked
inputs and derived artifacts, whereas the selected black-box software systems
receive neutrally identified, byte-identical copies through the forensic
evaluation bundle. Equivalence between these views is verified through
\gls{sha256} digests.

\section{Experimental Workflow and Implementation Environment}
\label{sec:implementation-overview}
% ─────────────────────────────────────────────────────────────────────────────

phase produces explicit records or artifacts used by subsequent phases. The

At the repository level, the implementation is divided into functional
components. Dataset preparation, split generation, and bundle construction are
maintained under \codepath{datasets/}; perturbation manifests and reports under
\codepath{attacks/}; proxy architectures, checkpoints, and training records
under \codepath{models/}; proxy predictions and normalized black-box outputs
under \codepath{evaluation/}; commercial-tool documentation and sanitized
extracts under \codepath{forensic_tools/}; explainability scripts and artifacts
under \codepath{explainability/}; and consolidated metrics, reporting assets,
and validators under \codepath{results/}. The authoritative thesis source is
maintained under \codepath{docs/LatexThesis/}.

The implementation was managed through Python virtual environments and executed
across Windows PowerShell and Linux/Kali environments according to the
requirements of each stage. Black-box processing additionally required licensed
installations of the selected software systems. The repository-level
\codepath{requirements.txt} file defines the Python dependency set, including
the libraries used for data processing, image manipulation, proxy-model
training and inference, adversarial generation, source acquisition,
visualization, and explainability. PyTorch and Torchvision provide the
deep-learning framework, \texttt{open\_clip\_torch} supports the
\gls{clip}-based proxy model, and Captum supports the \gls{ig} workflow.

The code supports CPU and CUDA-enabled execution. Manifest inspection, output
normalization, metric validation, and reporting audits can be performed without
dedicated acceleration, whereas proxy-model training, iterative adversarial
generation, and explainability regeneration constitute the most computationally
demanding stages.

The repository is distributed as a research artifact rather than as a
self-contained software package or a byte-identical operating-system image.
Procedural reproducibility and artifact-level auditability are supported
through numbered scripts, frozen manifests, fold-aware checkpoints, prediction
tables, explicit parameters, integrity digests, validation reports, and
controlled experimental artifacts. The public repository provides the material
required for structural inspection, metric recomputation, reporting validation,
and audit, while the complete image corpora, exact frozen black-box input
bundle, and complete proprietary software exports remain subject to controlled
access.

\section{Dataset Preparation and Organization}

\subsection{Technical Preparation and Source Consolidation}
\label{subsec:implementation-dataset-preparation}
% ─────────────────────────────────────────────────────────────────────────────

The initial candidate pool was assembled from five source collections maintained
under \codepath{datasets/raw/}: a public Kaggle-based collection, the
specialized DeepFirearm corpus, open-web images, content acquired from Telegram
and YouTube, and material collected from non-indexed web sources. The
collections remained organized according to acquisition provenance, while
source names, directory structures, and inherited labels were retained only as
provenance information and were not used as final operational assignments.

Technical preparation was performed by
\codepath{datasets/scripts/prepared/08_build_prepared_dataset.py}. The script
processes the five configured source directories in a fixed order, recursively
enumerates supported image files, and constructs the unified candidate pool
under \codepath{datasets/prepared/final_pool/}. It does not perform semantic
annotation or final sample selection, which are handled by the human review
procedure described in
Section~\ref{subsec:implementation-human-review}.

Candidate discovery was restricted to files with the extensions
\texttt{.jpg}, \texttt{.jpeg}, \texttt{.png}, \texttt{.bmp},
\texttt{.webp}, \texttt{.tif}, and \texttt{.tiff}. Each file was opened and
structurally verified using Pillow. Images that could not be decoded or
verified were recorded as \texttt{unreadable\_image}, whereas images whose
width or height was below 300 pixels were excluded under the
\texttt{below\_min\_size} condition. Unexpected failures were recorded with
the corresponding exception type.

For every technically valid image, the script computed a \gls{sha256} digest
over the original file bytes. Exact-duplicate detection was performed globally
across all five source collections. Because the source directories and their
contents were processed deterministically, the first occurrence of each digest
was retained, while every subsequent occurrence was recorded as a discarded
duplicate and linked to the retained sample.

Accepted images were assigned stable identifiers following the format
\texttt{img\_00000001} and copied to
\codepath{datasets/prepared/final_pool/images/}. The original file extension
was preserved, and no resizing, recompression, or format conversion was
performed. After each copy operation, the destination file was hashed again and
compared with the source digest. A mismatch caused execution to terminate,
preventing modified, corrupted, or incomplete copies from entering the prepared
pool.

The resulting prepared pool contained 15\,321 technically valid and
byte-distinct images from 19\,769 candidate files. Of the remaining files,
3\,124 were excluded because they were unreadable, structurally invalid, or
below the minimum dimensional threshold, and 1\,324 were discarded as exact
duplicates.

The preparation stage generated four principal audit records:

\begin{itemize}
\item \codepath{datasets/prepared/final_pool/metadata.csv}, containing one
record for each retained image;

\item
\codepath{datasets/prepared/final_pool/reports/invalid_images.csv},
documenting technically excluded files and their exclusion reasons;

\item
\codepath{datasets/prepared/final_pool/reports/duplicates_discarded.csv},
linking each discarded duplicate to the retained sample and its
\gls{sha256} digest;

\item
\codepath{datasets/prepared/final_pool/reports/prepared_build_summary.json},
containing global and source-specific preparation statistics.
\end{itemize}

For each retained image, \texttt{metadata.csv} records the stable image
identifier, prepared filename and relative path, source group, source dataset,
original relative path and filename, \gls{sha256} digest, dimensions, file
size, extension, and technical-validity state. These fields preserve the
relationship between the prepared sample and its acquisition source.

The output of this stage is a technically validated and globally deduplicated
candidate pool, not the final experimental dataset. Reduction of the
15\,321-image prepared pool to the frozen experimental corpus was performed
only through the human review and final-selection procedure described in the
following subsection.

\subsection{Review Documentation and Human-in-the-Loop Validation}
\label{subsec:implementation-human-review}
% ─────────────────────────────────────────────────────────────────────────────

The transition from technical preparation to semantic assessment was
implemented through the full review manifest generated by
\codepath{datasets/scripts/prepared/09_generate_review_manifest_full.py} and
stored at
\codepath{datasets/prepared/manifests/review_manifest_full.csv}. The script
creates one review record for each of the 15\,321 images retained in the
prepared pool.

Identity, provenance, and technical metadata are propagated from
\codepath{datasets/prepared/final_pool/metadata.csv}, including the stable image
identifier, \gls{sha256} digest, prepared path, source dataset, original source
path, dimensions, file size, extension, and technical-validity state. The
digest is not recomputed because it was already established and verified during
technical preparation.

The manifest extends these fields with separate columns for semantic assessment
and review-state management. It also reserves fields for optional automatic
prelabeling. These fields were initialized without model outputs, and
\texttt{prelabel\_status} was set to \texttt{pending}. No automatic score,
model prediction, or class suggestion was used to determine the final human
assignments.

Manual assessment was performed through the interactive application implemented
by
\codepath{datasets/scripts/final/10_manual_selection_protocol_reviewer.py}.
At its first execution, the application initializes the persistent working
database
\codepath{datasets/final/manifests/manual_selection_protocol_db.csv}
from the full review manifest. Subsequent executions resume the existing
database and the previously saved session state.

The interface presents images in batches of ten arranged in a five-column grid
and supports mouse- and keyboard-based assignment to \texttt{weapon},
\texttt{non\_weapon}, and \texttt{ood}, together with the review-only
\texttt{exclude} disposition. Additional controls support zooming, page
navigation, undo operations, explicit assignment removal, saving, and
resumption.

Two operating modes were implemented:

\begin{itemize}
\item in \texttt{review\_pending} mode, the reviewer inspects pending images
from a selected source and assigns an operational class or exclusion
disposition;

\item in \texttt{review\_selection} mode, the reviewer re-examines images
already assigned to one selected experimental group, optionally filters them by
source, and may remove an unsuitable assignment by returning the sample to the
pending pool.
\end{itemize}

The second mode provides an explicit quality-control mechanism for reviewing
the selected corpus without treating an initial assignment as immutable.

Figure~\ref{fig:implementation-human-review-interface} documents the
interactive environment used during the human-in-the-loop selection process.

The interface displays the operational criteria established in
Chapter~\ref{chap:methodology}. Clear and realistic firearm-related content is
assigned to \texttt{weapon}; realistic and interpretable negative content is
assigned to \texttt{non\_weapon}; borderline, synthetic, replica-like,
strongly degraded, anomalous, or otherwise out-of-task content is assigned to
\texttt{ood}; and unusable or irrelevant content is assigned to
\texttt{exclude}. Borderline samples are not forced into either binary class.

The application enforces global targets of 500 images for each of the
\texttt{weapon}, \texttt{non\_weapon}, and \texttt{ood} groups. Once a target
is reached, further assignments to that group are blocked until an existing
selection is removed. Soft source-level targets of 100 samples per group and
source are displayed as advisory balancing alerts and do not constrain reviewer
decisions.

The implemented procedure is therefore target-driven rather than an exhaustive
semantic annotation of the prepared pool. The global targets define the final
sample counts, while the source-level alerts support composition control
without requiring equal representation from every source.

Each assignment, clearing, removal, or undo operation records the timestamp,
reviewer identifier, session mode, source filter, image identifier, source
dataset, preceding assignment, new assignment, and review state in
\codepath{datasets/final/reports/manual_selection_log.csv}. The current
position, operating mode, active filters, last action, and recent undo history
are stored in
\codepath{datasets/final/reports/manual_selection_state.json}.

The application automatically saves the working database, updates the session
state, and regenerates the principal output records after review actions.
Existing CSV files are backed up with timestamped names before replacement, and
temporary files followed by atomic replacement are used to reduce the risk of
partial or corrupted writes.

The final working database contained 1\,500 reviewed records and 13\,821

1\,000-image binary subset.

The implemented process separates technical file validity, semantic suitability
for the experimental task, and final inclusion in the frozen corpus. The final
dataset composition and the consistency controls applied to its canonical
manifests are described in
Section~\ref{subsec:implementation-dataset-freezing}.

checks. In the frozen execution,
\texttt{final\_1500\_exact} and
\texttt{adversarial\_subset\_1000\_exact} were both set to
\texttt{true}, confirming the expected sizes of the complete corpus and binary

Freezing was implemented at the manifest level. After the target counts and
consistency checks had been satisfied, the exported manifests became the
canonical inputs for all downstream stages. Subsequent scripts consume their
image identifiers, paths, assignments, source information, and
\gls{sha256} digests without modifying the human-reviewed decisions.

Any replacement, removal, or reassignment of a frozen sample therefore requires
regeneration of all dependent partitions, derived artifacts, bundle records,
predictions, and metrics. An isolated downstream modification would no longer
correspond to the canonical dataset definition.

The frozen manifests define which images belong to the experiment and their
reference operational assignments. The deterministic generation of the binary
folds and the separate \gls{ood} evaluation manifest is described in
Section~\ref{subsec:implementation-split-generation}.

\codepath{datasets/final/manifests/manual_selection_adversarial_subset.csv}.

secondary objective because the source distributions of the two classes are
not uniform.

The records in each stratum are shuffled using a deterministic pseudo-random
generator initialized from the global seed, class assignment, and source
identifier. Each sample is then assigned to a fold that has not reached its
class quota. Among eligible folds, the implementation selects the fold with the
lowest existing count for the same class and source, followed by the lowest
current class occupancy and the fold identifier as deterministic tie-breaking
criteria.

\subsection{Training Configuration and Fold-Aware Checkpoints}
\label{subsec:implementation-training}
% ─────────────────────────────────────────────────────────────────────────────

The proxy models were trained through a fold-aware leave-one-fold-out
procedure. For each architecture and target fold, the target fold was reserved
as the held-out evaluation partition, while the remaining four folds were used
to construct the training and internal validation sets. No checkpoint was
therefore trained on the fold on which it was subsequently evaluated or used
for fold-matched model-dependent adversarial generation.

For each architecture--fold run, the four non-held-out folds contained 800
images. A deterministic stratified split reserved 15\% of these records for
internal validation, independently within each binary class. The resulting
partitions contained:

\begin{itemize}
\item 680 images for parameter optimization;
\item 120 images for internal validation;
\item 200 images in the untouched held-out fold.
\end{itemize}

The training--validation split was generated using seed 42. Records were
separated by class, shuffled deterministically within each class, and
recombined, preserving equal representation of \texttt{weapon} and
\texttt{non\_weapon}. The held-out fold was not used for parameter updates or
checkpoint selection.

configuration, including the batch size and backbone-freezing state, is stored
inside each fold-specific checkpoint.

The objective function was implemented using unweighted cross-entropy loss.
Class weighting was not applied because the training and validation partitions
remained balanced between the two supervised classes. Parameter updates used
AdamW with the learning-rate and weight-decay values reported in
Table~\ref{tab:implementation-proxy-training-configuration}.

Before training, the script validates the complete clean-fold manifest by
checking:

\begin{itemize}
\item the presence of the required columns;
\item the exclusive use of the two accepted binary assignments;
\item the presence of all five expected folds;
\item the exact count of 100 images per class and fold;
\item the uniqueness of the image identifiers;
\item the availability of every referenced image file;
\item the correspondence between each file and its recorded
\gls{sha256} digest.
\end{itemize}

Execution terminates when an image is missing or its digest does not match the
split manifest, preventing a checkpoint from being produced from a dataset
state inconsistent with the frozen partition definition.

The fixed seed is propagated to the Python standard-library pseudo-random
generator, NumPy, PyTorch, and all available CUDA devices. The implementation
disables cuDNN benchmark-based algorithm selection and requests deterministic
cuDNN behavior. These controls reduce variation from the principal
pseudo-random sources, although exact numerical reproduction may still depend
on the software and hardware environment.

The execution device may be selected as \texttt{cpu} or \texttt{cuda}, or
resolved automatically according to CUDA availability. Device selection does
not modify the frozen folds or declared optimization parameters. The preserved
complete-suite execution log records CPU-based training for the reported
checkpoints.

During each epoch, the script records training loss, training accuracy,
validation loss, and validation accuracy. All 10 epochs are executed; no early
stopping is applied. The checkpoint is overwritten whenever the current
validation accuracy is greater than or equal to the best value observed during
the preceding epochs. When the same maximum accuracy occurs in multiple
epochs, the latest qualifying checkpoint is retained. The held-out fold remains
excluded from this selection procedure.

\codepath{models/checkpoints/<model_name>/<fold>.pt}. The complete suite
contains:

\begin{equation}
3\ \text{proxy architectures}
\times
5\ \text{held-out folds}
=
15\ \text{checkpoints}.
\end{equation}

For ResNet18 and EfficientNet-B0, each checkpoint contains the trained model
state, class mapping, held-out-fold identifier, input size, training
configuration, creation timestamp, and metric history available when the
checkpoint was saved. For the \gls{clip}-based proxy, the checkpoint stores the
trained binary-head parameters and identifies the external ViT-B/32
architecture and pretrained weights required to reconstruct the frozen visual
encoder.

\subsection{Adversarial Attack Implementation}
\label{subsec:implementation-adversarial}
% ─────────────────────────────────────────────────────────────────────────────

Adversarial generation was implemented through
\codepath{datasets/scripts/attacks/14_generate_adversarial_attacks.py}, using
\codepath{datasets/splits/manifests/clean_folds_manifest.csv} as the canonical
input. The script generates one perturbed artifact from each of the 1\,000
clean binary images for every selected condition.

The frozen suite comprises four model-dependent attacks---\gls{fgsm}, One
Pixel, Sigma-Zero, and SuperDeepFool---and the model-agnostic Color Shift
condition. FGSM, Sigma-Zero, and SuperDeepFool require white-box access to
gradients or decision-boundary information. One Pixel uses score-based access
to the output probabilities of the target proxy model. Color Shift does not
query a model and is therefore recorded as an adversarial-style condition
rather than as a white-box or score-based attack.

EfficientNet-B0 was used as the primary proxy target for all model-dependent
conditions. For each source image, the generator reads the fold identifier from
the clean manifest and loads the corresponding checkpoint from
\codepath{models/checkpoints/efficientnet_b0/<fold>.pt}. Because that checkpoint
was trained while excluding the associated fold, the source image was not part
of the checkpoint's training data.

Before generation, the script verifies the required manifest fields, accepted
binary assignments, uniqueness of image identifiers, availability of all clean
inputs, and correspondence of their \gls{sha256} and \gls{md5} values with the
clean-fold manifest. Model-dependent conditions additionally require the
corresponding fold-specific checkpoint. Missing files or integrity mismatches

\paragraph{\gls{fgsm}.}

The FGSM implementation preprocesses the clean image according to the
EfficientNet-B0 normalization and computes the loss gradient with respect to
the reference operational assignment. The normalized gradient is converted to
pixel space before applying the perturbation:

\begin{equation}
\mathbf{x}_{\mathrm{adv}}
=
\operatorname{clip}_{[0,1]}
\left(
\mathbf{x}
+
\epsilon\,
\operatorname{sign}
\left(
\nabla_{\mathbf{x}}
\mathcal{L}(\mathbf{x},y)
\right)
\right),
\end{equation}

where \(y\) is the encoded reference operational assignment and
\(\epsilon = 8/255\). The adversarial tensor is converted to RGB and stored as
a lossless PNG file. The generation record includes clean and adversarial
predictions, predicted-class confidence, reference-class probability, and
pixel-space perturbation measurements.

\paragraph{One Pixel.}

The One Pixel implementation uses Differential Evolution to optimize the
coordinates and RGB value of one modified pixel. Each candidate is represented
by
\(\boldsymbol{\theta}=(u,v,r,g,b)\), where \((u,v)\) identifies the pixel and
\((r,g,b)\) specifies its replacement value. Let
\(T(\mathbf{x};\boldsymbol{\theta})\) denote the corresponding transformed
image. The implemented score-based objective is:

\begin{equation}
\min_{\boldsymbol{\theta}}
p_y\!\left(T(\mathbf{x};\boldsymbol{\theta})\right)
\qquad
\text{subject to}
\qquad
\left|
\left\{
(i,j):
T(\mathbf{x};\boldsymbol{\theta})_{ij}
\neq
\mathbf{x}_{ij}
\right\}
\right|
\leq 1,
\end{equation}

where \(p_y(\cdot)\) is the probability assigned by the fold-specific target
model to the reference class \(y\). The constraint applies to pixel locations,
since all three channels of the selected pixel may change jointly.

A deterministic image-specific seed is derived from the base seed, condition
name, and stable image identifier through \gls{sha256}. Optimization terminates
early when a candidate changes the prediction relative to the reference
assignment. Otherwise, the best candidate identified before the iteration
limit is exported.

\paragraph{Sigma-Zero.}

Sigma-Zero was integrated through the reference implementation exposed by the
\texttt{adversarial-library} project, pinned to commit
\texttt{b14f81a3e1c414a573b969b402c99e65bfe2ca33}. The FAIRLab adapter invokes
the reference function directly rather than reimplementing it.

The reference function operates on unnormalized tensors in \([0,1]\). The
adapter therefore converts the model-normalized input to pixel space and wraps
the EfficientNet-B0 checkpoint so that model normalization is reapplied before
logit computation. The untargeted sparse-perturbation objective can be
summarized as:

\begin{equation}
\min_{\mathbf{x}_{\mathrm{adv}} \in [0,1]^d}
\left\|
\mathbf{x}_{\mathrm{adv}}-\mathbf{x}
\right\|_0
\qquad
\text{subject to}
\qquad
\operatorname*{arg\,max}_{k}
f_k(\mathbf{x}_{\mathrm{adv}})
\neq
y,
\end{equation}

where \(f_k(\cdot)\) is the logit associated with class \(k\). The discrete
objective is approximated through the iterative optimization and adaptive
threshold procedure configured in
Table~\ref{tab:implementation-adversarial-parameters}.

\paragraph{SuperDeepFool.}

SuperDeepFool was implemented internally from the published
\(\mathrm{SDF}(\infty,1)\) procedure and does not vendor or copy the official
repository. The implementation first performs DeepFool-style iterations to
identify an adversarial boundary point and then applies a projection based on
the gradient difference between the boundary and reference classes.

The frozen untargeted objective is:

\begin{equation}
\min_{\boldsymbol{\delta}}
\left\|
\boldsymbol{\delta}
\right\|_{\infty}
\qquad
\text{subject to}
\qquad
\operatorname*{arg\,max}_{k}
f_k(\mathbf{x}+\boldsymbol{\delta})
\neq
y,
\qquad
\mathbf{x}+\boldsymbol{\delta}
\in [0,1]^d.
\end{equation}

At a boundary point \(\mathbf{x}_{b}\), the projection uses:

\begin{equation}
\mathbf{w}_{b}
=
\nabla_{\mathbf{x}} f_{k_b}(\mathbf{x}_{b})
-
\nabla_{\mathbf{x}} f_{y}(\mathbf{x}_{b}),
\end{equation}

where \(k_b\) is the boundary class. If the projected point remains
adversarial, it is retained; otherwise, the implementation falls back to the
adversarial boundary point. The manifest records iteration counts, convergence
status, and whether the projection preserved adversariality.

\paragraph{Color Shift.}

Color Shift modifies the RGB channels in the original image space and then
applies the configured saturation and contrast factors. No model is queried
during generation, and the generation-time attack-success field is marked as
not applicable. JPEG quality 95 is used because controlled recompression forms
part of the condition. The target-model field is set to
\texttt{model\_agnostic}, and checkpoint-related fields are left empty or
marked as not applicable.

Model-dependent outputs follow the pattern
\codepath{attacks/adversarial/<attack_name>/<target_model>/<fold>/<label>/}.
Color Shift uses the same structure with
\texttt{target\_model = model\_agnostic}. Generated filenames follow:

\[
\texttt{<image\_id>\_\_<attack\_name>\_\_<target\_model>.<extension>}.
\]

Each condition produces 1\,000 artifacts, comprising 500
\texttt{weapon} and 500 \texttt{non\_weapon} samples, with 200 artifacts per
fold. The complete stage therefore produces:

\begin{equation}
5\ \text{conditions}
\times
1\,000\ \text{binary images}
=
5\,000\ \text{perturbed artifacts}.
\end{equation}

\subsection{Anti-Forensic Transformation Implementation}
\label{subsec:implementation-antiforensic}
% ─────────────────────────────────────────────────────────────────────────────

Anti-forensic artifact generation was implemented through
\codepath{datasets/scripts/attacks/13_generate_anti_forensic_attacks.py}, using
\codepath{datasets/splits/manifests/clean_folds_manifest.csv} as the canonical
input. Each transformation was applied to all 1\,000 clean binary images,
comprising 500 \texttt{weapon} and 500 \texttt{non\_weapon} samples. The 500
clean \gls{ood} inputs remained outside this stage.

The frozen suite comprises five deterministic and model-agnostic
transformations: \gls{jpegrecompression}, \gls{resampleresize},
\gls{gaussianblur}, \gls{histogrammodification}, and
\gls{contraststretching}. These conditions do not access model gradients,
logits, probabilities, or checkpoints. The reference operational assignment of
each source image is propagated unchanged to the corresponding transformed
artifact.

Before generation, the script verifies the required manifest fields, accepted
binary assignments, and uniqueness of image identifiers. It also checks the
existence of every clean input and recomputes its \gls{sha256} and \gls{md5}
digests. Missing files or mismatches between the recorded and computed values
terminate execution. SHA-256 remains the primary integrity control, whereas
MD5 is retained as an auxiliary interoperability identifier.

Each source image is opened with Pillow, corrected according to its embedded
orientation through an EXIF transpose operation, and converted to RGB before
the transformation-specific operation is applied. All generated artifacts are
stored as \gls{jpeg} files. The dedicated recompression condition uses quality
70, while the remaining transformations use quality 95 to limit additional
encoding effects beyond the principal operation.

\paragraph{\gls{jpegrecompression}.}

The recompression condition does not apply an explicit spatial or tonal
operation before serialization. The RGB image is re-encoded at JPEG quality 70,
introducing a controlled lossy-compression condition through quantization and
block-based encoding effects.

\paragraph{\gls{resampleresize}.}

For an image with original dimensions \(W \times H\), the intermediate
dimensions are computed as:

\begin{equation}
W_{\mathrm{down}}
=
\max\left(1,\operatorname{round}(0.5W)\right),
\qquad
H_{\mathrm{down}}
=
\max\left(1,\operatorname{round}(0.5H)\right).
\end{equation}

The image is first resized to
\(W_{\mathrm{down}} \times H_{\mathrm{down}}\) and then restored to
\(W \times H\). Both operations use bicubic interpolation. The output
therefore retains the original spatial dimensions while incorporating the
information loss introduced by the intermediate downsampling and
reconstruction.

\paragraph{\gls{gaussianblur}.}

The Gaussian Blur condition applies a radius of 1.5 to suppress high-frequency
spatial detail. Image dimensions remain unchanged before final JPEG
serialization.

\paragraph{\gls{histogrammodification}.}

Histogram Modification is implemented through
\texttt{ImageOps.equalize}, which performs histogram equalization on the RGB
image channels. The same deterministic operation is applied to every sample,
without image-specific thresholds or model-derived information.

\paragraph{\gls{contraststretching}.}

Contrast Stretching is implemented through
\texttt{ImageOps.autocontrast} with a cutoff value of 1.0. The operation
remaps the remaining intensity range after excluding the configured proportion
of extreme values, modifying global contrast while retaining the original
image dimensions.

The hierarchy preserves the deterministic fold and binary reference assignment
of the source image. The transformation name remains separate from the
reference assignment, and no relabeling is performed during generation.

This separation prevents experiment-specific descriptors from being disclosed
directly through the imported directory hierarchy or file names and limits the
analyst's access to the hidden control mapping during the initial evaluation.
It does not conceal the visual content of an image, perceptible perturbation
effects, or information that may remain embedded within the image file itself.

Every logical item was assigned a sequential identifier from
\texttt{bundle\_000001} through \texttt{bundle\_011500}. Blind file names
contain only this identifier and the source file's format extension, as in
\texttt{bundle\_000001.jpg} or \texttt{bundle\_000002.png}.

The identifiers are neutral and deterministic rather than semantically
descriptive. The bundle builder does not claim to randomize the logical item
ordering; blindness is achieved through neutral naming, flat-path
materialization, exclusion of the internal mapping, and separation of control
metadata from the imported directory.

The source file format is retained, with the corresponding extension
normalized to lowercase. The builder performs no conversion, resizing,
recompression, or metadata sanitization. Files are copied without modifying
their byte content.

Blind file names are checked against a list of forbidden semantic and
experimental tokens, including binary assignment values, \gls{ood}
indicators, perturbation names, fold identifiers, and proxy-model names. The
file stem must also correspond exactly to the assigned bundle identifier.

The structured audit view reproduces the experimental hierarchy separately.
Clean inputs are organized by fold and reference assignment; \gls{ood} inputs
are maintained under the dedicated evaluation branch; adversarial artifacts are
organized by condition, target model, fold, and reference assignment; and
anti-forensic artifacts are organized by transformation, fold, and reference
assignment. This view supports internal verification and must not be imported
into the black-box software systems.

EXIF entries and searches their keys and values for terms that may reveal
reference assignments, perturbation conditions, fold identifiers, model names,
weapon-related descriptors, or other potentially informative content.

The audit does not remove or rewrite metadata, because doing so would alter the
files supplied to the selected black-box systems. Its purpose is to document a
potential residual information channel and support the separate sensitivity
analysis reported in
Section~\ref{subsec:results-embedded-metadata-sensitivity}. The presence of a
matched term does not by itself demonstrate that a black-box system accessed,
interpreted, or used the corresponding metadata.

The bundle builder supports blind-only, structured-only, and combined layouts.
The frozen execution used the combined layout and materialized the same 11\,500
logical items in both operational views, producing 11\,500 blind files and
11\,500 structured audit copies. Rebuilding an existing bundle requires the
explicit \texttt{--force} option, which removes the existing bundle directory
before materialization.

The completed bundle provides a stable and auditable input population for the
selected black-box software systems. Their concrete versions, import
procedures, classification categories, retrieval configurations, and export
formats are documented in
Section~\ref{sec:implementation-forensic-tools}.

\texttt{weapon} was intentionally excluded because the experimental positive

Each prompt was executed separately under the semantic-distance limits 20, 50,
and 80. This procedure produced:

\begin{equation}
8\ \text{fixed prompts}
\times
3\ \text{distance settings}
=
24\ \text{prompt-level export files}.
\end{equation}

The export names follow the pattern
\texttt{excire\_<prompt>\_distance<limit>.csv}. For file-system
compatibility, the multiword prompt \texttt{assault rifle} is represented as
\texttt{assault\_rifle} in the corresponding file name. The prompt and
distance configuration can therefore be reconstructed deterministically from
each export name.

The Excire outputs are retrieval hit lists rather than complete classification
tables. Each file contains the paths of the images returned for one prompt
under one distance setting, generally as a headerless list with one path per
line. An image may occur in multiple files when it is retrieved by more than
one prompt. Consequently, the raw hit totals reported in
Table~\ref{tab:implementation-excire-configuration} represent prompt-level
memberships and may exceed the number of unique positive images.

The normalizer reads each hit list deterministically, removes surrounding
quotation marks, ignores an optional path-oriented header, extracts the file
name from each exported path, and matches it against the neutral file names in
the canonical bundle manifest. The original local directory component does not
contribute to the experimental decision.

For a bundle image \(x\), semantic-distance setting \(d\), and frozen prompt
set \(\mathcal{P}\), the operational rule is:

\[
\texttt{weapon\_detected}(x;d)
=
\begin{cases}
\texttt{true},
&
\text{if }
\exists p \in \mathcal{P}:
\operatorname{retrieved}(x,p,d),
\\
\texttt{false},
&
\text{otherwise}.
\end{cases}
\]

The corresponding common normalized prediction is \texttt{weapon} when
\texttt{weapon\_detected = true} and \texttt{non\_weapon} otherwise.
Images absent from all eight hit lists under the same distance setting are
completed against the canonical 11\,500-item bundle as operational negative
decisions.

This rule is an operational recoding of semantic-retrieval membership. It does
not imply that \gls{excirefoto2025} internally performs binary
\texttt{weapon}/\texttt{non\_weapon} classification. Similarly, the
software-specific distance limits must not be interpreted as calibrated
probabilities, numerical confidence values, or thresholds directly comparable
with those of another system.

The D20, D50, and D80 settings were retained as separate system configurations
throughout normalization and metric computation. Their retrieval results were
not combined into a single Excire decision. Each setting produced one complete
table containing exactly 11\,500 normalized predictions.

For auditability, each normalized record preserves:

\begin{itemize}
\item the semantic-distance limit;
\item the complete frozen prompt set;
\item the number and names of prompts that retrieved the image;
\item one binary membership indicator for each of the eight prompts;
\item the bundle identifier and neutral input file name;
\item the \gls{sha256} and \gls{md5} values;
\item the sample type, perturbation family, condition, fold, reference
operational assignment, source dataset, and source-image identifiers;
\item the resulting \texttt{weapon\_detected} and normalized-prediction
fields.
\end{itemize}

Preserving the individual prompt memberships prevents the union operation from
discarding relevant retrieval information. Two images may receive the same
positive normalized decision even when one is retrieved by a single prompt and
the other by several semantically related prompts.

After the union and bundle-completion procedures, every configuration contained
exactly one normalized prediction for each of the 11\,500 bundle items, and no
bundle item remained unmatched. The three configurations therefore produced
34\,500 normalized Excire records in total. Complete matching establishes
output coverage but does not establish the correctness of the resulting
operational decisions.

commas, or line breaks and removes the parenthesized percentage values before
applying the operational mapping. The percentages are preserved only as part of
the raw observable output. They are not treated as calibrated probabilities and
do not influence the binary decision.

The frozen mapping assigns a positive decision when the observable
\texttt{Classifications} field contains at least one of the following labels:

\begin{itemize}
\item \texttt{Armi};
\item \texttt{Pistola};
\item \texttt{Fucile}.
\end{itemize}

Formally, the operational recoding is:

\begin{equation}
\left\{
\texttt{Armi},
\texttt{Pistola},
\texttt{Fucile}
\right\}
\cap
\mathcal{C}(x)
\neq
\varnothing
\quad\Longrightarrow\quad
\texttt{weapon\_detected = true},
\end{equation}

where \(\mathcal{C}(x)\) denotes the set of normalized classifications exported
for image \(x\).

For every other successfully matched bundle record, the software-specific
decision is:

\begin{equation}
\left\{
\texttt{Armi},
\texttt{Pistola},
\texttt{Fucile}
\right\}
\cap
\mathcal{C}(x)
=
\varnothing
\quad\Longrightarrow\quad
\texttt{weapon\_detected = false}.
\end{equation}

The corresponding common normalized states are:

\begin{equation}
\texttt{weapon\_detected = true}
\longrightarrow
\texttt{weapon},
\end{equation}

\begin{equation}
\texttt{weapon\_detected = false}
\longrightarrow
\texttt{non\_weapon}.
\end{equation}

The inclusion of \texttt{Pistola} and \texttt{Fucile} alongside the broader
\texttt{Armi} label defines the extended mapping used for the frozen thesis
evaluation. This prevents firearm-specific positive classifications from being
discarded merely because the broader \texttt{Armi} category is absent from the
same exported field.

This rule is an operational recoding of an observable software output. It does
not imply that \gls{cellebriteinseyets} internally implements the same binary
taxonomy, that the exported labels are mutually exclusive, or that the
associated percentage values represent directly comparable model
probabilities.

The original report contained 11\,829 image rows. Of these, 11\,500 were
matched to the complete forensic evaluation bundle, whereas 329 rows did not
correspond to bundle items. The unmatched records were retained as an aggregate
audit count and excluded from the quantitative robustness analysis. Complete
bundle coverage confirms that a matched exported decision was available for
every experimental item but does not establish classification correctness.

The matching procedure associates report records with the canonical bundle
through available cryptographic hashes, anonymized file names, and bundle
identifiers. For each successfully matched record, the normalized output
retains:

\begin{itemize}
\item the \texttt{bundle\_id} and input file name;
\item the matching method and matched state;
\item the available \gls{sha256} and \gls{md5} values;
\item the clean, \gls{ood}, or perturbed sample type;
\item the perturbation family and condition;
\item the fold and reference operational assignment;
\item the original and generated image identifiers;
\item the original \texttt{Classifications} value;
\item the normalized binary decision and mapping reason.
\end{itemize}

The complete XLSX report also contained file-system, evidence, and case-export
information not required for the classification mapping. Because these fields
may expose local paths or case-specific metadata, the raw report is managed as
a controlled-access record rather than distributed through the public
repository.

Its expected local location is:

\begin{center}
\codepath{forensic_tools/cellebrite_inseyets/raw_exports/FAIRLAB_CELLEBRITE_INSEYETS_RUN_01/}
\end{center}

The public repository instead retains a sanitized extract containing the
anonymized bundle identifiers, the observable classification values, and the
normalized decision fields:

\begin{center}
\codepath{forensic_tools/cellebrite_inseyets/public_extracts/cellebrite_classifications_extract.csv}
\end{center}

The run registry, software-version log, export audit, normalized prediction
table, and metric outputs document the frozen software configuration and the
correspondence between the controlled raw report and the sanitized decision

\paragraph{Bundle indexing and record matching.}

When the bundle metadata is loaded, the implementation constructs three lookup
indexes:

\begin{enumerate}
\item a \gls{sha256}-based index;
\item an \gls{md5}-based index;
\item an anonymized file-name index.
\end{enumerate}

For conventional row-oriented exports, each parsed software record is matched
according to the following priority:

\begin{center}
\texttt{SHA-256}
\(\succ\)
\texttt{MD5}
\(\succ\)
\texttt{exact file name}
\(\succ\)
\texttt{file name embedded in an exported path or text field}.
\end{center}

The matching method is preserved explicitly in the normalized record. This
allows subsequent verification of whether an association was established
through the primary cryptographic identifier or through a fallback identifier
exposed by the software export.

Hash values are normalized before comparison by removing separators and
non-hexadecimal formatting characters. File-system paths are reduced to their
base file names before lookup so that differences between Windows paths and
repository-relative directory structures do not prevent association with the
blind bundle.

The \gls{excirefoto2025} workflow requires a distinct matching procedure
because its exports contain only the images retrieved by each semantic query.
The anonymized file names listed in the eight prompt-level hit lists are first
mapped to bundle items. The union of those hits is then completed against the
full bundle manifest, thereby producing an explicit operational decision for
every image, including those absent from all prompt exports.

\paragraph{Common normalized schema.}

The normalized representation separates software-observable information from
the reference assignments and experimental metadata recovered from the bundle.
Its principal fields include:

\begin{itemize}
\item \texttt{tool\_name}, \texttt{bundle\_id},
\texttt{matched}, and \texttt{match\_method};

\item \texttt{sample\_type}, \texttt{attack\_family},
\texttt{attack\_name}, and \texttt{attack\_target\_model};

\item \texttt{fold}, \texttt{final\_label}, and
\texttt{source\_dataset};

\item \texttt{original\_image\_id} and
\texttt{generated\_image\_id};

\item the anonymized input file name and available \gls{sha256} and
\gls{md5} values;

\item the original exported label, tag, classification, bookmark, or
prompt-membership information;

\item \texttt{weapon\_detected},
\texttt{normalized\_prediction}, and
\texttt{mapping\_reason};

\item binary correctness, false-negative, and false-positive indicators
when the reference operational assignment is \texttt{weapon} or
\texttt{non\_weapon}.
\end{itemize}

The literal field name \texttt{final\_label} is preserved because it belongs to
the implemented schema; semantically, its value represents the reference
operational assignment inherited from the frozen bundle.

Software-specific information is retained in additional fields rather than
being discarded after binary recoding. These fields include the original AXIOM
tags, Cellebrite classifications, Excire distance limit and per-prompt hit
indicators, and the primary and secondary Griffeye bookmarks.

The schema therefore supports structured cross-system comparison without
discarding the observable evidence from which each normalized decision was
derived.

For records whose reference assignment is \texttt{ood}, the binary correctness,
false-negative, and false-positive fields are left undefined. An \gls{ood}
input is not treated as either a positive or a negative reference instance. Its
normalized \texttt{weapon\_detected} state is preserved separately and is later
used to compute the \gls{ood} weapon-flag rate.

\paragraph{Deduplication and completeness.}

Some software exports may contain more than one record associated with the same
bundle item. The normalizer therefore supports deterministic consolidation to
one row per normalized configuration and bundle identifier.

When several matched rows refer to the same pair, the consolidated decision is
selected according to the following conservative rule:

\begin{enumerate}
\item if at least one row contains a positive decision, the consolidated
result is positive;

\item otherwise, if at least one row contains an explicit negative
decision, the consolidated result is negative;

\item otherwise, the consolidated result is \texttt{unknown}.
\end{enumerate}

The consolidation procedure retains the combined export-file references, row
numbers, observable labels, mapping reasons, and raw-row count. When an
explicit software-specific numerical value is available, the maximum exported
value may be preserved as part of the original observable record. Such values
are not converted into a common calibrated confidence measure, and no
confidence value is fabricated for systems that do not expose one.

Unmatched records are excluded from the canonical prediction table because they
do not belong to the official forensic evaluation bundle. They remain
documented through the export audit and separate unmatched-record outputs.

After software-specific parsing and the preliminary exclusion of the 553
non-bundle Griffeye records, the normalization workspace contained 69\,329
candidate records. This population comprised the expected 69\,000 bundle-level
decisions and 329 unmatched Cellebrite report records. Excluding the latter
produced exactly 69\,000 matched normalized decisions:

\begin{equation}
69\,329
-
329
=
69\,000.
\end{equation}

This final count corresponds to complete coverage of the 11\,500-item bundle
for all six normalized configurations. No matched bundle decision remained
without a common normalized state after the frozen mappings were applied.
Complete coverage establishes output availability and successful matching; it
does not establish classification correctness.

The proxy-model outputs and the normalized black-box software decisions were

Proxy-model predictions and metrics were generated through:

\begin{center}

Black-box software metrics were generated as part of the normalization pipeline

\begin{center}
\codepath{evaluation/scripts/19_normalize_forensic_ai_tool_predictions.py}
\end{center}

Although the two pipelines process different forms of observable information,
they use the same positive and negative reference classes:

\begin{equation}
\text{positive class}
=
\texttt{weapon},
\qquad
\text{negative class}
=
\texttt{non\_weapon}.
\end{equation}

The \gls{ood} branch is handled separately and does not contribute to the

\paragraph{Proxy-model prediction generation.}

The proxy-model evaluation pipeline consumes:

\begin{itemize}
\item the clean-fold manifest;
\item the separate \gls{ood} evaluation manifest;
\item the adversarial-generation manifests;
\item the anti-forensic transformation manifest;
\item the 15 fold-specific proxy-model checkpoints.
\end{itemize}

Each clean or perturbed binary sample is evaluated by the checkpoint associated
with its assigned fold. This ensures that the model used for prediction was
trained while excluding the fold containing the corresponding source image.

For each evaluated input, the implementation records:

\begin{itemize}
\item the evaluated architecture and fold-specific checkpoint;
\item the clean, \gls{ood}, or perturbed sample type;
\item the perturbation family, condition, and target model;
\item the original and generated image identifiers;
\item the assigned fold and reference operational assignment;
\item the image path and actual \gls{sha256} and \gls{md5} values;
\item the predicted class;
\item the maximum predicted-class probability;
\item the probabilities assigned to \texttt{weapon} and
\texttt{non\_weapon};
\item the probability assigned to the reference class for binary samples;
\item the correctness state and any evaluation error.
\end{itemize}

The complete prediction-level record is:

\begin{center}
\codepath{evaluation/proxy_models/proxy_model_predictions.csv}
\end{center}

procedure used elsewhere in the pipeline. The file hashes are recomputed, and
the corresponding fold-aware model adapter applies the architecture-specific

\end{aligned}
\end{equation}

\paragraph{Binary metric computation.}

For each binary evaluation group, the implementation derives the confusion
matrix using the fixed layout:

\begin{equation}
\begin{bmatrix}
\mathrm{TN} & \mathrm{FP} \\
\mathrm{FN} & \mathrm{TP}
\end{bmatrix}.
\end{equation}

The resulting metric records contain:

\begin{itemize}
\item accuracy and balanced accuracy;
\item class-specific precision, recall, and F1-score;
\item macro-averaged precision, recall, and F1-score;
\item \gls{tp}, \gls{tn}, \gls{fp}, and \gls{fn} counts;
\item \gls{fpr} and \gls{fnr};
\item misclassification rate;
\item \texttt{weapon}-to-\texttt{non\_weapon} and
\texttt{non\_weapon}-to-\texttt{weapon} error counts;
\item mean maximum predicted-class probability.
\end{itemize}

The \gls{fpr} and \gls{fnr} are implemented as:

\begin{equation}
\mathrm{FPR}
=
\frac{\mathrm{FP}}
{\mathrm{FP}+\mathrm{TN}},
\qquad
\mathrm{FNR}
=
\frac{\mathrm{FN}}
{\mathrm{FN}+\mathrm{TP}}.
\end{equation}

Clean proxy-model metrics are grouped by architecture. Adversarial-stage
metrics are grouped by evaluated architecture, perturbation condition, and
attack target model. This grouping includes the four model-dependent
adversarial attacks and the model-agnostic Color Shift condition.
Anti-forensic metrics are grouped by evaluated architecture and transformation
condition.

The attack-target field is retained because the model-dependent adversarial
artifacts were generated against fold-aware EfficientNet-B0 checkpoints but
were subsequently evaluated by all three proxy architectures. This distinction
supports separate analysis of direct target-model behavior and cross-model
transfer. Color Shift remains explicitly marked as model-agnostic and is not
interpreted as a transfer attack.

The maximum predicted-class probabilities are retained as intra-model
diagnostic values. They are not assumed to be calibrated across architectures
and are not used as directly comparable confidence measures between ResNet18,
EfficientNet-B0, and the \gls{clip}-based proxy.

\paragraph{Clean-to-perturbed comparison.}

Each perturbed prediction is associated with its corresponding clean prediction
through the tuple:

\begin{center}
\texttt{evaluated\_model},
\quad
\texttt{evaluation\_fold},
\quad
\texttt{original\_image\_id}.
\end{center}

The prediction table is enriched with the clean prediction, clean correctness
state, clean class probabilities, clean maximum probability, and probability
difference relative to the perturbed input.

For each proxy model and perturbation condition, the comparative layer
computes:

\begin{itemize}
\item clean accuracy and perturbed accuracy;
\item the schema field \texttt{robust\_accuracy}, whose stored value is
equivalent to the perturbed accuracy;
\item accuracy drop;
\item clean and perturbed macro F1-scores;
\item macro F1-score drop;
\item induced-error count and induced-error rate;
\item attack success rate for model-dependent adversarial attacks;
\item mean maximum-probability shift;
\item directional error counts and rates.
\end{itemize}

The term \texttt{robust\_accuracy} is retained because it is part of the
implemented comparative schema. It does not denote a separate quantity from
the perturbed-condition accuracy.

Let \(\mathcal{C}_{\mathrm{clean}}\) denote the set of samples correctly
classified under the corresponding clean condition. The induced-error rate for
perturbation condition \(p\) is implemented as:

\begin{equation}
    \mathrm{IER}_{p}
    =
    \frac{
        \left|
        \left\{
        i \in \mathcal{C}_{\mathrm{clean}}
        :
        \hat{y}^{(p)}_{i} \neq y_{i}
        \right\}
        \right|
    }{
        \left|
        \mathcal{C}_{\mathrm{clean}}
        \right|
    }.
\end{equation}

Images already misclassified in the clean condition are excluded from this
denominator because they cannot represent newly induced errors.

For the four model-dependent adversarial attacks, this clean-correct transition
rate is also reported as the attack success rate. For Color Shift and the five
anti-forensic transformations, the same transition is reported as an
induced-error rate and is not interpreted as adversarial attack success or
transfer success.

The maximum-probability shift is computed as:

\begin{equation}
\Delta c
=
c_{\mathrm{perturbed}}
-
c_{\mathrm{clean}},
\end{equation}

and averaged within each model--condition group. This quantity compares the
maximum predicted-class probability before and after perturbation. It does not
necessarily compare the probability assigned to the same class when the
predicted class changes, and it is used only as an intra-model diagnostic.

\paragraph{Proxy-model \gls{ood} metrics.}

The \gls{ood} branch is summarized independently for each proxy architecture.
The resulting records contain:

\begin{itemize}
\item the fold-aggregated number of checkpoint responses;
\item the number and rate of predictions assigned to \texttt{weapon};
\item the number of predictions assigned to \texttt{non\_weapon};
\item the mean maximum predicted-class probability;
\item the high-confidence threshold;
\item the number and rate of predictions whose maximum probability meets
or exceeds that threshold.
\end{itemize}

The frozen high-confidence threshold is:

\begin{equation}
\tau_{\mathrm{high}}
=
0.90.
\end{equation}

The high-confidence count includes predictions assigned to either binary class.
It characterizes confident closed-set assignment of an \gls{ood} input. The
predicted-weapon rate instead characterizes the operational tendency to flag
\gls{ood} content as firearm-related.

Neither quantity represents supervised correctness because the \gls{ood}
branch has no positive or negative binary reference assignment. The associated
probabilities remain architecture-specific diagnostic outputs and are not
treated as calibrated across proxy models.

\paragraph{Black-box software metric computation.}

Black-box software metrics are computed from the normalized decisions described
in Section~\ref{subsec:implementation-normalization}. Only matched binary
records with an interpretable \texttt{true} or \texttt{false}
\texttt{weapon\_detected} value contribute to the binary confusion matrix.
Records assigned to \texttt{unknown} are excluded from the binary denominators
and reported separately.

The implementation computes:

\begin{itemize}
\item accuracy;
\item balanced accuracy;
\item \texttt{weapon} precision, recall, and F1-score;
\item \texttt{non\_weapon} specificity;
\item \gls{fpr} and \gls{fnr};
\item \gls{tp}, \gls{tn}, \gls{fp}, and \gls{fn} counts;
\item the count and rate of \texttt{unknown} normalized decisions;
\item the number and rate of \gls{ood} inputs flagged as
\texttt{weapon};
\item the number of \gls{ood} inputs not flagged or assigned to
\texttt{unknown}.
\end{itemize}

characterizes observable flagging behavior and is not interpreted as supervised
accuracy or error.

\begin{itemize}

\item sample type;
\item perturbation family;
\item individual perturbation condition;

\paragraph{Case-selection procedure.}

diagnostic buckets:

\begin{enumerate}
\item a correctly classified clean \texttt{weapon} image;
\item a clean \texttt{weapon} false negative;
\item a high-confidence \gls{ood} input assigned to the

\item a clean-correct image rendered incorrect by an anti-forensic

\item a clean-correct image rendered incorrect with high maximum

\texttt{non\_weapon}-to-\texttt{weapon} transitions and other induced

\paragraph{Attribution processing and visual outputs.}

For each attribution target, the channel-wise attribution tensor is converted
into a two-dimensional map by summing the absolute attribution magnitudes
across the three input channels. The resulting map is min--max normalized to
the interval \([0,1]\).

Because absolute values are used, the visualizations represent attribution
magnitude rather than contribution direction. They identify image regions
associated with larger attribution magnitudes for the selected model output
along the baseline-to-input path, but they do not distinguish positive evidence
from negative evidence.

The implementation produces the following diagnostic outputs for each case:

\begin{itemize}
\item the resized RGB input image;
\item a colorized attribution heatmap;
\item an overlay combining the input and heatmap;
\item a normalized grayscale attribution mask;
\item a binary mask containing pixels at or above the selected attribution
percentile;
\item a side-by-side diagnostic comparison;
\item a histogram of normalized attribution values.
\end{itemize}

The heatmap uses the \texttt{inferno} color map. The overlay combines the
resized input with the colorized heatmap using an attribution opacity of 0.45.
The binary high-attribution mask is computed from the 90th percentile of the
normalized map and therefore identifies approximately the 10\% of image
locations with the highest attribution magnitudes. The exact proportion may
vary when multiple locations share the percentile threshold.

The thesis retains four visual assets for each of the five selected cases:

\begin{enumerate}
\item input image;
\item standalone heatmap;
\item heatmap overlay;
\item top-10\% attribution mask.
\end{enumerate}

\section{Traceability, Integrity, and Reproducibility Controls}
\label{sec:implementation-traceability}
% ─────────────────────────────────────────────────────────────────────────────

Traceability, integrity, and controlled reproducibility were implemented as
cross-cutting properties of the complete experimental workflow rather than as
controls added only after evaluation. The resulting framework links the frozen
dataset, deterministic partitions, proxy-model checkpoints, derived
perturbations, black-box inputs, normalized software outputs, metric tables,
explainability cases, and reporting assets through stable identifiers,
cryptographic digests, manifests, and version-controlled metadata.

The implementation distinguishes three related but non-equivalent objectives:

\begin{itemize}
\item \emph{traceability}, defined as the ability to reconstruct the
provenance and processing history of an experimental input, derived
artifact, model, or result record;

\item \emph{integrity}, defined as the ability to verify that an input,
artifact, model, or record has not changed relative to its canonical
recorded state;

\item \emph{controlled reproducibility}, defined as the ability to inspect
or rerun the workflow to the extent permitted by data-access restrictions,
licensed-software requirements, and the available execution environment.
\end{itemize}

This distinction is necessary because public access to code and metadata does
not imply unrestricted redistribution of the source images or availability of
the proprietary software required to repeat the black-box processing.

\paragraph{Stable identity and provenance chain.}

The pipeline assigns stable identifiers at successive processing stages.
Prepared source images receive an \texttt{image\_id}; generated perturbations
receive a \texttt{generated\_image\_id}; black-box inputs receive an anonymized
\texttt{bundle\_id}; and selected explainability cases receive a
\texttt{case\_id}. Model checkpoints are identified through the combination of
proxy architecture and held-out fold.

The resulting provenance chain can be represented as:

\begin{equation}
\begin{split}
\texttt{image\_id}
&\longrightarrow
\texttt{generated\_image\_id}
\longrightarrow
\texttt{bundle\_id} \\
&\longrightarrow
\texttt{normalized\_prediction}
\longrightarrow
\texttt{metric\_row}
\longrightarrow
\texttt{reporting\_asset}.
\end{split}
\end{equation}

For clean binary samples and \gls{ood} inputs, the original and generated
identifiers may coincide because no new derived image artifact is created. For
adversarial and anti-forensic artifacts, the generated identifier preserves the
association with the corresponding clean source image while distinguishing the
perturbation condition and, where applicable, the target proxy model.

The manifests retain repository-relative paths rather than relying on
machine-specific absolute locations. This allows outputs generated on different
workstations to be associated with the same logical repository structure. Run
summaries and registries additionally preserve configurations, creation
timestamps, sample counts, fold assignments, and output locations.

\paragraph{Cryptographic integrity controls.}

\gls{sha256} is the primary integrity digest throughout the pipeline.
\gls{md5} is retained only as an auxiliary interoperability identifier because
some forensic software exports expose MD5-oriented fields or matching
workflows. It is not treated as the primary integrity mechanism.

Per-file hashes are recorded at the principal transformation and transfer
boundaries, including:

\begin{itemize}
\item prepared and frozen source images;
\item deterministic clean and \gls{ood} partitions;
\item adversarial and anti-forensic artifacts;
\item blind and structured bundle copies;
\item proxy-model checkpoints;
\item selected explainability inputs and their fold-specific checkpoints;
\item sanitized black-box software extracts and canonical metric records.
\end{itemize}

Thesis-level explainability outputs are validated through their canonical
manifest paths, selection metadata, and reporting-asset audits rather than
being treated as independently hash-authenticated model artifacts.

Whenever a file is copied between stages, the destination hash is recomputed
and compared with the canonical value recorded in the originating manifest. A
mismatch causes the relevant script to terminate rather than silently accepting
a different file.

The checkpoint digests stored in:

\begin{center}
\codepath{models/model_registry.json}
\end{center}

bind every proxy architecture and held-out fold to the corresponding serialized
model checkpoint. These values are checked before model-dependent adversarial
generation and by the hardened explainability entry point.

Archive-level integrity is maintained separately from per-file integrity. The
canonical controlled-archive digests are stored in:

\begin{center}
\codepath{docs/artifact/CONTROLLED_ARTIFACT_CHECKSUMS.sha256}
\end{center}

The complete-archive digest authenticates the downloaded ZIP file, whereas:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}
\end{center}

supports verification of each of the 11\,500 restored blind inputs
individually. This distinction prevents a valid archive-level digest from
replacing verification of the expected file population after extraction.

\paragraph{Deterministic configuration controls.}

A fixed seed of 42 is used for the principal stochastic procedures, including
fold construction, internal training--validation partitioning, and
image-specific randomized search initialization where applicable. The seed is
recorded in the corresponding configuration and summary records.

The use of a fixed seed supports repeatability of the logical partitions and
pseudo-random initialization. It does not imply that every numerical result is
guaranteed to be bit-identical across different operating systems, hardware
architectures, library versions, or CPU and GPU implementations. PyTorch and
cuDNN deterministic options reduce nondeterministic behavior where supported,
but the execution environment remains part of the reproducibility boundary.

The frozen configurations also specify:

\begin{itemize}
\item accepted assignment values and expected group counts;
\item the five clean folds and separate \gls{ood} branch;
\item preprocessing and normalization parameters;
\item training hyperparameters;
\item perturbation parameters;
\item model and checkpoint associations;
\item black-box software versions and observable-output mappings;
\item metric definitions and confusion-matrix layout;
\item explainability target, baseline, integration steps, and selection
criteria.
\end{itemize}

These values are stored in machine-readable CSV or JSON records rather than
being represented only in narrative documentation.

\paragraph{Overwrite and rerun controls.}

The principal generation and evaluation scripts implement fail-visible output
guards. Existing canonical outputs are not silently replaced. A rebuild
generally requires the explicit \texttt{--force} option, which removes or
replaces only the output scope associated with the selected run.

This policy reduces the risk of combining outputs generated under different
configurations or overwriting a frozen result with a partial diagnostic
execution. Partial experiments and exploratory runs must use separate output
locations and must not replace the canonical manifests, predictions, or metric
tables.

An explicit forced rebuild does not by itself establish equivalence with the
frozen research artifact. The regenerated files must still satisfy the expected
counts, identifier constraints, integrity values, and downstream validation
procedures.

\paragraph{Audit summaries and machine-readable invariants.}

Each major stage produces sample-level records and a run-level summary. The
summary files record input manifests, parameters, output paths, expected and
actual counts, validation results, and creation metadata. This design permits
structural checks to be performed without reopening every image or manually
inspecting every prediction.

The principal invariants include:

\begin{itemize}
\item 1\,500 records in the frozen dataset;
\item 1\,000 binary samples and 500 \gls{ood} inputs;
\item five folds containing 200 binary images each;
\item 15 fold-aware proxy-model checkpoints;
\item 5\,000 adversarial and 5\,000 anti-forensic artifacts;
\item 11\,500 unique forensic evaluation bundle items;
\item 40\,500 proxy-model prediction rows;
\item 69\,000 canonical sanitized black-box software decisions;
\item 186 black-box software metric rows;
\item five canonical thesis-level explainability cases and 20 associated
thesis assets.
\end{itemize}

These counts are implementation invariants and completeness checks. Their
presence does not establish model or software robustness; the quantitative
behavior of the evaluated systems is analyzed separately in
Chapter~\ref{chap:results}.

does not grant unrestricted redistribution rights, remove obligations imposed
by the original sources, or provide access to proprietary model internals.

\paragraph{Environment and security boundary.}

The pipeline was developed using Python virtual environments in Windows and
Linux environments, including Windows PowerShell and Kali Linux, with CPU- or
CUDA-enabled execution selected according to the computational stage.
Black-box evaluation additionally requires compatible licensed software and a
suitable workstation.

The repository records the dependency specification and operational setup but
does not claim to reproduce a byte-identical operating-system environment.
Exact usernames, credentials, API keys, signed download URLs, commercial
license information, session data, and unnecessary local absolute paths are
excluded.

The public branch also excludes:

\begin{itemize}
\item unrestricted copies of the image corpora;
\item complete raw black-box software exports;
\item proprietary case databases;
\item evidence-related material not required for the experimental record;
\item private or temporary artifact-access URLs;
\item generated LaTeX auxiliary files.
\end{itemize}

This minimization preserves the information required to audit the experimental
claims while reducing disclosure of unrelated sensitive or proprietary
material.

\paragraph{Version control and artifact freezing.}

Source code, manifests, registries, sanitized decisions, metric tables,
documentation, and thesis sources are maintained through Git version control.
Large proxy-model checkpoints are managed through Git LFS, while their
\gls{sha256} values remain recorded in the model registry.

The repository policy treats the thesis research artifact as a versioned frozen
object. Substantive changes to the data, perturbations, checkpoints, normalized
decisions, metrics, or thesis conclusions require a new versioned release
rather than silent replacement of the existing frozen state. Documentation
corrections, security fixes, and non-substantive archival improvements must
remain clearly distinguishable from changes to the experimental evidence.

Taken together, these controls provide a traceable connection between the
implemented protocol and the results reported in the following chapter. They
do not eliminate the limitations associated with controlled data access,
hardware and software variation, human review, or proprietary black-box
systems. Instead, they make these boundaries explicit and preserve the
information required to audit the evaluation within them.

Chapter~\ref{chap:results} presents the quantitative outcomes obtained from the
frozen implementation and analyzes their implications for the operational
robustness of the evaluated proxy models and selected black-box software
systems.
