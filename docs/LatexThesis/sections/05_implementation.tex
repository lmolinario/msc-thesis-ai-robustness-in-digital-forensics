\chapter{Implementation and Experimental Setup}
\label{chap:implementation}
% ─────────────────────────────────────────────────────────────────────────────

This chapter documents the concrete implementation of the \gls{fairlab}
methodology introduced in Chapter~\ref{chap:methodology}. It describes how the
experimental protocol was instantiated through the preparation and freezing of
the image corpus, the generation of deterministic data partitions, the
training of fold-aware proxy models, the production of adversarial and
anti-forensic variants, and the construction of the forensic evaluation
bundle.

The chapter also reports the configurations adopted for the selected black-box
software systems, the procedures used to match and normalize their observable
outputs, and the technical controls introduced to preserve artifact identity,
provenance, integrity, and reproducibility. The implementation of the
explainability workflow and the generation of the consolidated evaluation
artifacts are documented as part of the same experimental pipeline.

The distinction between implementation and experimental evidence is maintained
throughout the chapter. The present chapter describes how the protocol was
realized and which technical artifacts were produced, whereas the quantitative
outcomes and their operational interpretation are reported separately in
Chapter~\ref{chap:results}. This separation prevents implementation choices,
software configurations, and data-management procedures from being conflated
with the measured robustness of the evaluated systems.

A central implementation principle is that the two evaluation levels operate
on the same frozen experimental corpus. The 1\,000 clean binary images and the
500 clean \gls{ood} images define the common source population, while the
10\,000 adversarial and anti-forensic variants are derived exclusively from
the binary subset. The proxy models process the manifest-linked experimental
artifacts, whereas the selected black-box software systems receive
byte-identical anonymized copies through the blind forensic evaluation bundle.
The equivalence between these two views is verified through \gls{sha256}
digests. Consequently, the parallel comparison is based on the same samples
and experimental conditions rather than on independently assembled datasets.

\section{Experimental Workflow and Implementation Environment}
\label{sec:implementation-overview}
% ─────────────────────────────────────────────────────────────────────────────
The experimental protocol was implemented as a staged and traceable pipeline
covering source acquisition, dataset preparation, human review, data
partitioning, proxy-model training, perturbation generation, controlled
evaluation, black-box output normalization, explainability analysis, and final
reporting. Each stage produces explicit intermediate artifacts that become the
inputs of the subsequent stage. These artifacts include manifests, model
checkpoints, prediction tables, integrity digests, validation reports, and
consolidated metric files.

The implementation is organized as a numbered sequence of scripts. This
organization makes the execution order explicit and reduces ambiguity regarding
the provenance of the generated outputs. The numbered pipeline begins with the
controlled restoration or acquisition of the source corpora and continues
through dataset preparation, manual validation, model training, perturbation
generation, evaluation, bundle construction, explainability analysis, black-box
normalization, and reporting. Additional validation utilities operate on the
frozen outputs without modifying the canonical experimental artifacts.

At the repository level, the implementation is divided into functional
components. Dataset preparation and bundle construction are maintained under
\codepath{datasets/}; perturbation manifests are stored under
\codepath{attacks/}; proxy architectures, checkpoints, and training records are
maintained under \codepath{models/}; prediction generation and black-box
normalization are organized under \codepath{evaluation/}; explainability
artifacts are maintained under \codepath{explainability/}; and consolidated
metrics, reporting assets, and validation utilities are stored under
\codepath{results/}. The authoritative thesis source is maintained separately
under \codepath{docs/LatexThesis/}.

The software implementation was managed through Python virtual environments.
The workflow was executed across Windows PowerShell and Linux/Kali contexts,
depending on the stage, while the black-box evaluations required compatible
licensed installations of the selected commercial software systems. The Python
dependency set is declared in the repository-level
\codepath{requirements.txt} file and includes the libraries used for numerical
processing, image manipulation, proxy-model training and inference,
adversarial generation, explainability, visualization, and source acquisition.
The deep-learning implementation is based on PyTorch and Torchvision, with
\texttt{open\_clip\_torch} used for the \gls{clip}-based proxy and Captum used
for the Integrated Gradients workflow.

The code supports both CPU and CUDA-enabled execution, with device selection
depending on the computational requirements of the individual stage and on the
available execution environment. Lightweight operations, including manifest
inspection, output normalization, metric validation, and reporting audits, can
be performed without dedicated acceleration. Proxy-model training, iterative
adversarial generation, and explainability regeneration constitute the most
computationally demanding stages.

The repository is distributed as a research artifact rather than as a
self-contained software package or a byte-identical operating-system image.
Accordingly, reproducibility is preserved primarily through numbered scripts,
frozen manifests, fold-aware checkpoints, prediction tables, explicit
parameters, integrity hashes, validation reports, and controlled data
artifacts. The public repository retains the material required for structural
inspection, metric recomputation, and audit, whereas the full image corpora, the
exact frozen black-box input, and complete proprietary exports remain subject
to controlled access. This boundary preserves auditability without
redistributing restricted or licensed material.

\section{Dataset Preparation and Organization}
\label{sec:implementation-dataset}
% ─────────────────────────────────────────────────────────────────────────────


\subsection{Technical Preparation and Source Consolidation}
\label{subsec:implementation-dataset-preparation}

The initial image pool was assembled from five heterogeneous source
collections maintained under \codepath{datasets/raw/}. These collections were
organized according to their acquisition provenance rather than according to
the final experimental labels. The source structure comprised a public
Kaggle-based collection, the specialized DeepFirearm corpus, open-web images,
content derived from Telegram and YouTube, and material obtained from
non-indexed web sources. This organization preserved the origin of each sample
while preventing source names, directory structures, or pre-existing labels
from being inherited automatically as experimental ground truth.

The technical preparation stage was implemented by:

\begin{center}
\codepath{datasets/scripts/prepared/08_build_prepared_dataset.py}
\end{center}

The script scans the supported source directories in a fixed order and
constructs a unified candidate pool under:

\begin{center}
\codepath{datasets/prepared/final_pool/}
\end{center}

This stage is deliberately limited to technical preparation. It does not
perform semantic annotation, assign the final labels
\texttt{weapon}, \texttt{non\_weapon}, or \texttt{ood}, or determine whether
an image is suitable for inclusion in the frozen experimental dataset. These
decisions are deferred to the human review process described in
Section~\ref{subsec:implementation-human-review}.

Candidate discovery was restricted to files with the extensions
\texttt{.jpg}, \texttt{.jpeg}, \texttt{.png}, \texttt{.bmp},
\texttt{.webp}, \texttt{.tif}, and \texttt{.tiff}. Each candidate was opened
and verified through the Pillow image-processing library. Images that could not
be decoded or structurally verified were recorded as unreadable, whereas
images with either dimension below 300 pixels were excluded through the
\texttt{below\_min\_size} condition. Unexpected decoding errors were retained
in the invalid-image report together with the corresponding exception type.

For every technically valid image, the script computed a \gls{sha256} digest
over the original file bytes. Exact duplicate detection was then performed
globally across all source collections rather than independently within each
source. When the same digest occurred more than once, the first deterministically
encountered instance was retained and the subsequent occurrence was recorded as
a discarded duplicate. This procedure prevented the same byte-identical image
from appearing multiple times in the prepared pool, including when it had been
collected from different sources or stored under different file names.

Accepted images were assigned stable identifiers with the format:

\begin{center}
\texttt{img\_00000001}
\end{center}

and copied to:

\begin{center}
\codepath{datasets/prepared/final_pool/images/}
\end{center}

The original file extension was preserved, and no resizing, recompression, or
format conversion was applied during this stage. After each copy operation, the
destination file was hashed again and compared with the digest of the source
file. A mismatch caused the pipeline to terminate, thereby preventing a
modified or incomplete copy from entering the prepared pool.

The resulting prepared pool contained 15\,321 technically valid and
byte-distinct images from an initial set of 19\,769 candidate files. A total of
3\,124 files were excluded because they were unreadable, structurally invalid,
or below the minimum dimensional threshold, while 1\,324 additional files were
discarded as exact duplicates.

The preparation stage generated four principal audit artifacts:

\begin{itemize}
    \item \codepath{datasets/prepared/final_pool/metadata.csv}, containing one
    row for each retained image;
    \item
    \codepath{datasets/prepared/final_pool/reports/invalid_images.csv},
    documenting technically excluded files and the corresponding exclusion
    reason;
    \item
    \codepath{datasets/prepared/final_pool/reports/duplicates_discarded.csv},
    linking each discarded duplicate to the retained image and its
    \gls{sha256} digest;
    \item
    \codepath{datasets/prepared/final_pool/reports/prepared_build_summary.json},
    containing global and source-specific preparation statistics.
\end{itemize}

For each retained image, \texttt{metadata.csv} records the stable image
identifier, prepared file name and path, source group, source dataset, original
relative path and file name, \gls{sha256} digest, image dimensions, file size,
extension, and technical-validity state. This structure preserves the
provenance of the candidate pool without treating provenance as a semantic
label.

The output of this stage is therefore a technically validated and deduplicated
candidate pool, not the final experimental dataset. The reduction from 15\,321
prepared images to the frozen set used in the experiments was performed only
after explicit human assessment of semantic relevance, class membership,
visual interpretability, and source diversity.

\subsection{Review Documentation and Human-in-the-Loop Validation}
\label{subsec:implementation-human-review}

The transition from technical preparation to semantic assessment was implemented
through a dedicated review manifest. The manifest was generated from the
prepared-pool metadata by:

\begin{center}
\codepath{datasets/scripts/prepared/09_generate_review_manifest_full.py}
\end{center}

and stored as:

\begin{center}
\codepath{datasets/prepared/manifests/review_manifest_full.csv}
\end{center}

The script creates one review record for each image retained in the prepared
pool. Identity, provenance, and technical metadata are propagated from
\codepath{datasets/prepared/final_pool/metadata.csv}, including the stable image
identifier, \gls{sha256} digest, prepared path, source dataset, original source
path, image dimensions, file size, extension, and technical-validity state. The
digest is not recomputed at this stage because it has already been established
and verified during technical preparation.

The review manifest extends these technical fields with a separate set of
columns for semantic annotation and review-state management. These fields
include the final operational label, review status, reviewer identifier,
timestamp, notes, exclusion reason, and information for documenting
out-of-distribution cases. The schema also reserves fields for an optional
automatic prelabeling stage; however, these fields were initialized as empty
and their status was set to \texttt{pending}. No automatic score, model
prediction, or class suggestion was used to determine the final labels in the
manual reviewer.

The semantic review was conducted through the dedicated interactive
application implemented by:

\begin{center}
\codepath{datasets/scripts/final/10_manual_selection_protocol_reviewer.py}
\end{center}

The reviewer loads the full manifest into a persistent working database:

\begin{center}
\codepath{datasets/final/manifests/manual_selection_protocol_db.csv}
\end{center}

and presents the images in batches of ten, arranged in a five-column grid. The
interface supports mouse- and keyboard-based assignment of the operational
labels \texttt{weapon}, \texttt{non\_weapon}, \texttt{ood}, and
\texttt{exclude}, together with image zooming, page navigation, decision
reversal, session changes, saving, and resumption of a previous review state.

Two operating modes were implemented. In \texttt{review\_pending} mode, the
reviewer inspects unassigned images from a selected source and assigns an
operational disposition. In \texttt{review\_selection} mode, images already
assigned to one of the selected classes can be inspected again, optionally
filtered by source, and returned to the pending pool when the previous
assignment is considered unsuitable. This second mode provides an explicit
quality-control pass over the selected images rather than treating an initial
assignment as immutable.

The class-assignment criteria displayed by the reviewer reproduce the
operational definitions established in Chapter~\ref{chap:methodology}.
Recognizable and realistic firearm-related content is assigned to
\texttt{weapon}; realistic and interpretable negative content is assigned to
\texttt{non\_weapon}; borderline, synthetic, replica-like, degraded, anomalous,
or semantically out-of-task content is assigned to the separate
\texttt{ood} branch; and unusable or irrelevant material is assigned to
\texttt{exclude}. When a sample cannot be assigned to either binary class with
sufficient semantic clarity, the interface directs the reviewer not to force
the case into \texttt{weapon} or \texttt{non\_weapon}.

The application enforces global targets of 500 images for each of the
\texttt{weapon}, \texttt{non\_weapon}, and \texttt{ood} groups. Once the target
for a class is reached, further assignments to that class are blocked unless an
existing selection is first removed. Advisory source-level targets of 100
samples per class and source are also displayed. These source-level targets do
not block reviewer decisions; they operate only as balancing alerts and suggest
inspection of sources that remain underrepresented.

Every labeling, clearing, or reassignment action is associated with the image
identifier, source dataset, reviewer identifier, timestamp, previous label, new
label, session mode, and review state. The events are appended to:

\begin{center}
\codepath{datasets/final/reports/manual_selection_log.csv}
\end{center}

The current session position, review mode, active filters, and recent undo state
are preserved in:

\begin{center}
\codepath{datasets/final/reports/manual_selection_state.json}
\end{center}

This state-management mechanism allows the review to be interrupted and resumed
without discarding previous decisions. Before replacing existing working files,
the application also creates timestamped backups, while temporary files and
atomic replacement are used to reduce the risk of partial or corrupted writes.

The frozen working database contained 1\,500 reviewed records and 13\,821
records that remained pending. Therefore, the complete technically prepared

until the predefined targets of 500 \texttt{weapon}, 500
\texttt{non\_weapon}, and 500 \texttt{ood} images had been reached and

The implemented review process therefore separates three distinct elements:
technical file validity, semantic suitability for the experimental task, and
final inclusion in the frozen corpus. This distinction ensures that neither
source provenance nor technical readability is treated as sufficient evidence
of class membership. The resulting frozen composition and the consistency
checks applied to the exported manifests are described in
Section~\ref{subsec:implementation-dataset-freezing}.

were not included in the frozen dataset and remained available in the working

The reviewer generated the final manifests directly from the persistent
selection database. Records assigned to \texttt{weapon},
\texttt{non\_weapon}, or \texttt{ood} were exported to the complete frozen
manifest, whereas the binary subset was obtained by retaining only the first
two operational labels. No independent relabeling or automatic transformation
was performed between these exports. This guarantees that the binary subset is
a strict subset of the complete frozen manifest and that its labels remain
identical to the corresponding human-reviewed decisions.

The final summary report is stored as:

\begin{center}
\codepath{datasets/final/reports/manual_selection_summary.json}
\end{center}

The report records the output locations, final counts, remaining class targets,
number of reviewed and pending records, source-level advisory targets, and
completion checks. In the frozen execution, both principal consistency
conditions were satisfied:

\begin{itemize}
    \item \texttt{final\_1500\_exact = true}, confirming the presence of
    exactly 500 samples in each of the three final groups;
    \item \texttt{adversarial\_subset\_1000\_exact = true}, confirming that
    the binary subset contains exactly 1\,000 samples.
\end{itemize}

Freezing was implemented at the manifest level. Once the exact targets and
consistency checks had been satisfied, the exported manifests became the
authoritative inputs for the downstream pipeline. Subsequent scripts consume
the recorded image identifiers, paths, labels, source information, and
\gls{sha256} values without modifying the semantic decisions. Any replacement
or correction of a selected image therefore requires regeneration of the
dependent splits, perturbations, bundle records, predictions, and metrics,
rather than an undocumented change to an isolated downstream artifact.

This approach separates dataset definition from later experimental processing.
The frozen manifests establish which images belong to the study and how they
are operationally interpreted, while subsequent stages determine how those
same images are partitioned, transformed, evaluated, and matched to observable
software outputs. The deterministic construction of the clean folds and the

\begin{center}
\texttt{seed = 42}
\end{center}

Each fold contains exactly 200 images, comprising 100 \texttt{weapon} and 100
\texttt{non\_weapon} samples. Class balance is enforced as a hard constraint,
whereas source balance is treated as a secondary objective. This distinction is
necessary because the source distributions of the two classes are not
identical and cannot always be divided uniformly across all folds.

The fold-assignment procedure operates independently for each class and source
dataset. The records associated with a specific class--source combination are
shuffled through a deterministic pseudo-random generator derived from the
global seed, class label, and source identifier. Each image is then assigned to
an eligible fold that has not reached its class quota. Among the eligible
folds, priority is given to the fold containing the lowest current number of
samples from the same source and class. The current overall class occupancy and
the fold identifier are used as secondary tie-breaking criteria.

\subsection{Architectures and Preprocessing}
\label{subsec:implementation-architectures}

The transparent classification layer was implemented through three
\emph{proxy models}: ResNet18, EfficientNet-B0, and a \gls{clip}-based visual
classifier. In this work, the term \emph{proxy model} denotes a fully
inspectable experimental model used to apply controlled training,
perturbation, evaluation, and explainability procedures. These models do not
replicate the proprietary architectures or internal decision mechanisms of the
commercial forensic tools. Instead, they provide a transparent reference layer
through which gradients, logits, probabilities, checkpoints, and attribution
maps can be accessed directly.

All three proxies implement the same binary classification task:

\begin{equation}
    \texttt{non\_weapon} \rightarrow 0,
    \qquad
    \texttt{weapon} \rightarrow 1.
\end{equation}

The separate \gls{ood} branch is not represented as a third supervised output
and is excluded from proxy-model training. It is processed only during the
dedicated out-of-distribution evaluation described in
Chapter~\ref{chap:results}.

The model suite was implemented in:

\begin{center}

\end{center}

and its frozen architecture definitions are recorded in:

binary-head parameters rather than a complete independent copy of the
pretrained visual encoder. Reconstructing the complete proxy requires the
external ViT-B/32 base weights identified in the model registry.

A common image-loading procedure was applied across the three architectures.
Each file is opened through Pillow, corrected according to its embedded
orientation information by applying an EXIF transpose operation, and converted
to three-channel RGB representation. Images are then transformed into tensors
according to the model-specific preprocessing pipeline.

All proxy inputs are resized to:

\begin{center}
\texttt{224 $\times$ 224 pixels}
\end{center}

The training transformation applies the following sequence:

\begin{enumerate}
    \item deterministic resizing to \(224 \times 224\) pixels;
    \item random horizontal flipping with probability \(0.5\);
    \item conversion to a PyTorch tensor;
    \item architecture-specific channel normalization.
\end{enumerate}

The validation and evaluation transformation uses the same resizing,
tensor-conversion, and normalization operations but does not apply random
horizontal flipping. No additional random crop, rotation, color augmentation,
or geometric distortion is introduced by the training script.

\subsection{Training Configuration and Fold-Aware Checkpoints}
\label{subsec:implementation-training}
The proxy models were trained according to a leave-one-fold-out protocol. For
each architecture and each target fold, the target fold was reserved as the
held-out evaluation partition, while the remaining four folds were used to
construct the training and internal validation sets. Consequently, no
checkpoint was trained on the same fold on which it was subsequently evaluated
or used to generate fold-matched model-dependent perturbations.

For each run, the four non-held-out folds contained 800 images. The
implementation created an internal stratified validation partition by reserving
15\% of these samples independently within each binary class. This produced:

\begin{itemize}
    \item 680 images for parameter optimization;
    \item 120 images for internal validation;
    \item 200 images in the untouched held-out fold.
\end{itemize}

The split between training and internal validation data was generated
deterministically with seed 42. Records were first separated by class, shuffled
within each class, and then recombined, thereby preserving the balance between
\texttt{weapon} and \texttt{non\_weapon}. The held-out fold was not involved
in checkpoint selection.

ResNet18 and EfficientNet-B0 were fine-tuned from their ImageNet-initialized
weights, including their convolutional backbones and newly introduced binary
classifier layers. The implementation also provides a
\texttt{--freeze-backbone} option for diagnostic or alternative runs, but this
option is not part of the frozen CNN training configuration. For the
\gls{clip}-based proxy, the pretrained visual encoder was always frozen and
only the binary linear head was optimized.

The training objective was implemented through unweighted cross-entropy loss.
No class weighting was required because each fold and each derived
training--validation partition remained balanced between the two classes.
Parameter updates were performed through the AdamW optimizer using the fixed
learning rate and weight-decay values reported above.

Before training begins, the script validates the complete clean-fold manifest.
The validation procedure verifies:

\begin{itemize}
    \item the presence of the required manifest columns;
    \item the exclusive use of the two accepted binary labels;
    \item the presence of all five expected folds;
    \item the exact count of 100 images per class and fold;
    \item the uniqueness of the image identifiers;
    \item the availability of every referenced image file;
    \item the correspondence between each file and its recorded
    \gls{sha256} digest.
\end{itemize}

Training is interrupted when a source image is missing or when its digest does
not match the value recorded in the split manifest. This prevents a checkpoint
from being silently produced from a dataset state that differs from the frozen
partition definition.

Reproducibility controls are also applied to the main pseudo-random sources.
The fixed seed is propagated to the Python standard-library generator, NumPy,
PyTorch, and all available CUDA devices. The implementation disables cuDNN
benchmark-based algorithm selection and requests deterministic cuDNN behavior.
The execution device may be selected explicitly as \texttt{cpu} or
\texttt{cuda}, or resolved automatically according to CUDA availability. The
exact software and hardware environment is documented separately from the
model-training logic because device selection does not alter the frozen fold
or checkpoint definitions.

During each epoch, the implementation records training loss, training accuracy,
validation loss, and validation accuracy. The checkpoint is updated whenever
the current validation accuracy is greater than or equal to the best value
observed in the preceding epochs. When the same best value occurs more than
once, the later qualifying epoch replaces the earlier checkpoint. The held-out
fold remains excluded from this selection process.

\begin{center}
\codepath{models/checkpoints/<model_name>/<fold>.pt}
\end{center}

The complete suite comprises 15 checkpoints:

\begin{equation}
    3\ \text{proxy architectures}
    \times
    5\ \text{held-out folds}
    =
    15\ \text{checkpoints}.
\end{equation}

For ResNet18 and EfficientNet-B0, each checkpoint contains the trained model
state, binary label mapping, held-out-fold identifier, input size, complete
training configuration, creation timestamp, and epoch-level metric history. For
the \gls{clip}-based proxy, the checkpoint stores the trained binary-head
parameters and records the external ViT-B/32 architecture and pretrained
weight identifier required to reconstruct the frozen visual encoder.

\subsection{Adversarial Attack Implementation}
\label{subsec:implementation-adversarial}


The adversarial generation stage was implemented through:

\begin{center}
\codepath{datasets/scripts/attacks/14_generate_adversarial_attacks.py}
\end{center}

The script consumes the authoritative clean-fold manifest:

\begin{center}
\codepath{datasets/splits/manifests/clean_folds_manifest.csv}
\end{center}

and generates one perturbed variant of each of the 1\,000 clean binary images
for every selected perturbation condition. The frozen suite comprises four
model-dependent adversarial attacks and one model-agnostic color manipulation:

\begin{itemize}
    \item \gls{fgsm};
    \item One Pixel;
    \item Sigma-Zero;
    \item SuperDeepFool;
    \item Color Shift.
\end{itemize}

The first four procedures require direct access to a transparent proxy model
and are therefore implemented as checkpoint-dependent attacks. Color Shift is
implemented within the same generation stage for experimental consistency, but
it does not require model gradients, probabilities, or checkpoint access. It is
therefore recorded explicitly as a model-agnostic adversarial-style
perturbation rather than as a white-box attack.

EfficientNet-B0 was used as the frozen primary target for all model-dependent
attacks. For each input image, the generator reads the fold identifier from the
clean manifest and loads the corresponding checkpoint:

\begin{center}
\codepath{models/checkpoints/efficientnet_b0/<fold>.pt}
\end{center}

Because each checkpoint was trained while excluding its associated fold, the
target image was not part of the training data of the model used to generate
its perturbation. This fold-aware association preserves the separation between
training and attack generation established in
Section~\ref{subsec:implementation-training}.

Before any attack is executed, the script verifies the presence of the required
manifest columns, accepted binary labels, uniqueness of the image identifiers,
availability of all clean source files, and correspondence of their

model-dependent conditions, the required fold-specific checkpoint must also be

\paragraph{\gls{fgsm}.}

The \gls{fgsm} implementation first preprocesses the clean image according to
the target-model normalization. The loss gradient is computed with respect to
the true binary label in normalized model space and converted to the
corresponding pixel-space gradient. The adversarial tensor is then produced as:

\begin{equation}
    \mathbf{x}_{\mathrm{adv}}
    =
    \operatorname{clip}_{[0,1]}
    \left(
        \mathbf{x}
        +
        \epsilon\,
        \operatorname{sign}
        \left(
            \nabla_{\mathbf{x}}
            \mathcal{L}(\mathbf{x},y)
        \right)
    \right),
\end{equation}

where \(\epsilon=8/255\). The resulting tensor is converted back to an RGB
image and stored as a lossless PNG file. The manifest records the clean and
adversarial predictions, confidence values, true-label probabilities, and
pixel-space perturbation measurements.

\paragraph{One Pixel.}

The One Pixel implementation uses Differential Evolution to optimize the
location and RGB value of a single modified pixel. Each optimization candidate
contains five variables: horizontal coordinate, vertical coordinate, and the
three color-channel values. The objective minimizes the probability assigned
by the target proxy to the true label.

A deterministic image-specific seed is derived from the base seed, attack
name, and stable image identifier through \gls{sha256}. This mechanism avoids
using an identical candidate sequence for every image while preserving
repeatability across executions. The optimization is terminated early when a
candidate causes the proxy prediction to differ from the true label.
Regardless of whether misclassification is achieved, the best candidate found
during the search is exported and documented.

\paragraph{Sigma-Zero.}

Sigma-Zero was integrated through the reference implementation exposed by the
\texttt{adversarial-library} project rather than through a locally rewritten
version. The dependency is pinned to the inspected repository commit:

\begin{center}
\texttt{b14f81a3e1c414a573b969b402c99e65bfe2ca33}
\end{center}

The reference function expects unnormalized pixel tensors in the interval
\([0,1]\). A dedicated adapter therefore converts the FAIR-Lab
model-normalized input back to pixel space and exposes a wrapper that
reapplies the target-model normalization before forwarding the tensor to the
fold-specific proxy. The attack is untargeted and aims to identify a sparse
adversarial perturbation by optimizing an approximation of the
\(\ell_0\)-norm objective.

\paragraph{SuperDeepFool.}

SuperDeepFool was implemented internally from the published
\(\mathrm{SDF}(\infty,1)\) procedure rather than by copying or vendoring an
external repository. The implementation first performs DeepFool-style
iterations to identify an adversarial boundary point. It subsequently applies
a SuperDeepFool projection based on the gradient difference between the
reference class and the boundary class.

When the projection remains adversarial, the projected point is retained. When
the projection returns to the original class, the implementation falls back to
the adversarial boundary point identified by the DeepFool stage. The manifest
records the number of outer, DeepFool, and projection iterations, the
convergence state, and whether the projection preserved adversariality.

\paragraph{Color Shift.}

Color Shift modifies the RGB channels directly in the original image space and
then adjusts color saturation and contrast. No proxy model is queried during
generation, and no attack-success value is assigned at this stage. The
condition is stored as JPEG rather than PNG because controlled recompression is
part of the frozen transformation configuration. The target-model field is set
to \texttt{model\_agnostic}, while checkpoint-related fields remain empty or
not applicable.

The model-dependent outputs are written under the structure:

\begin{center}
\codepath{attacks/adversarial/<attack_name>/efficientnet_b0/<fold>/<label>/}
\end{center}

Color Shift outputs use the corresponding model-agnostic branch. Generated
file names follow the pattern:

\begin{center}
\texttt{<image\_id>\_\_<attack\_name>\_\_<target\_model>.<extension>}
\end{center}

\subsection{Anti-Forensic Transformation Implementation}
\label{subsec:implementation-antiforensic}
The anti-forensic transformation stage was implemented through:

\begin{center}
\codepath{datasets/scripts/attacks/13_generate_anti_forensic_attacks.py}
\end{center}

The script consumes the same authoritative binary manifest used by the
adversarial generation stage:

\begin{center}
\codepath{datasets/splits/manifests/clean_folds_manifest.csv}
\end{center}

Accordingly, each transformation is applied to the complete set of 1\,000
clean binary images, comprising 500 \texttt{weapon} and 500
\texttt{non\_weapon} samples. The 500 \gls{ood} images remain outside this
stage and are preserved as clean inputs for the separate
out-of-distribution evaluation.

The frozen anti-forensic suite comprises five deterministic and
model-agnostic transformations:

\begin{itemize}
    \item \gls{jpegrecompression};
    \item \gls{resampleresize};
    \item \gls{gaussianblur};
    \item \gls{histogrammodification};
    \item \gls{contraststretching}.
\end{itemize}

These transformations do not require access to model gradients, logits,
probabilities, or checkpoints. Their purpose is to reproduce common image
post-processing operations capable of modifying compression artifacts,
spatial detail, local intensity distributions, or global contrast while
preserving the semantic content and manually assigned label of the source
image.

Before generation, the script validates the required manifest fields, the
accepted binary labels, and the uniqueness of the image identifiers. It also
verifies the existence of every clean input and recomputes its \gls{sha256}
and \gls{md5} values. Generation is interrupted when an input file is missing
or when either recorded digest does not correspond to the file being
processed.

Each source image is opened through Pillow, corrected according to its embedded
orientation information through an EXIF transpose operation, and converted to
three-channel RGB representation. The transformation-specific operation is
then applied, and the resulting image is stored as a \gls{jpeg} file. Except
for the dedicated recompression condition, which uses quality 70, the remaining
outputs are encoded at quality 95 to minimize additional compression effects
not explicitly defined by the selected transformation.

configuration of the five conditions.

\paragraph{\gls{jpegrecompression}.}

The recompression condition does not introduce an explicit spatial or color
transformation before serialization. Instead, the original RGB representation
is encoded again as a \gls{jpeg} image with quality 70. This condition isolates
the effect of moderate lossy recompression, including quantization and
block-based coding artifacts, from the other transformation families.

\paragraph{\gls{resampleresize}.}

For an image with dimensions \(W \times H\), the intermediate dimensions are
computed as:

\begin{equation}
    W_{\mathrm{down}}
    =
    \max\left(1,\operatorname{round}(0.5W)\right),
    \qquad
    H_{\mathrm{down}}
    =
    \max\left(1,\operatorname{round}(0.5H)\right).
\end{equation}

The image is first resized to
\(W_{\mathrm{down}} \times H_{\mathrm{down}}\) and then restored to
\(W \times H\). Both operations use bicubic interpolation. The final output
therefore retains the original spatial dimensions while exhibiting the
information loss introduced by the intermediate downsampling and
reconstruction stages.

\paragraph{\gls{gaussianblur}.}

The Gaussian blur condition applies a radius of 1.5 to suppress high-frequency
spatial detail. The image dimensions and RGB representation remain unchanged
before final JPEG serialization. The transformation is deterministic and does
not depend on the image label, assigned fold, or proxy-model output.

\paragraph{\gls{histogrammodification}.}

Histogram Modification is implemented as histogram equalization. The operation
redistributes the available intensity values to alter the tonal distribution
of the image. No manually selected thresholds or image-specific model outputs
are used. The same deterministic operation is applied to every sample in the
binary subset.

\paragraph{\gls{contraststretching}.}

Contrast Stretching is implemented through automatic contrast normalization.
A cutoff value of 1.0 removes the corresponding percentage of extreme
intensity values before remapping the remaining range. This operation changes
the global tonal distribution while preserving the image dimensions and
operational label.

The transformed images are written according to the structure:

\begin{center}
\codepath{attacks/anti_forensic/<transformation>/<fold>/<label>/}
\end{center}

Generated file names follow the pattern:

\begin{center}
\texttt{<image\_id>\_\_<transformation>.jpg}
\end{center}

The folder hierarchy retains both the deterministic fold assignment and the
binary class label of the source image. No relabeling is performed during
generation, and the transformation name is recorded separately from the
semantic ground truth.

Each of the five conditions produces 1\,000 transformed files, distributed as
200 images per fold and 500 images per binary label. The complete
anti-forensic stage therefore produces:

\begin{equation}
    5\ \text{transformations}
    \times
    1\,000\ \text{binary images}
    =
    5\,000\ \text{transformed artifacts}.
\end{equation}

\begin{center}
\codepath{attacks/manifests/anti_forensic_attacks_manifest.csv}
\end{center}

For each output, the manifest records:

\begin{itemize}
    \item the generated and original image identifiers;
    \item the fold and manually assigned binary label;
    \item the original source provenance;
    \item the clean and transformed repository-relative paths;
    \item the anti-forensic family and transformation name;
    \item the serialized transformation parameters;
    \item the original and transformed \gls{sha256} and \gls{md5} values;
    \item the output file size, extension, and creation timestamp.
\end{itemize}

\end{center}

The final checks also confirm the uniqueness of the generated image identifiers

\texttt{weapon} was not included because the experimental positive class was
firearm-oriented rather than a general category encompassing all possible
weapons.

Each prompt was executed separately under the three distance-limit settings
20, 50, and 80. This procedure produced 24 prompt-level exports:

\begin{equation}
    8\ \text{fixed prompts}
    \times
    3\ \text{distance settings}
    =
    24\ \text{export files}.
\end{equation}

The exports were named according to the pattern:

\begin{center}
\texttt{excire\_<prompt>\_distance<limit>.csv}
\end{center}

For file-system compatibility, the multiword prompt
\texttt{assault rifle} was represented as \texttt{assault\_rifle} in the
export file name. The prompt and distance configuration can therefore be
reconstructed deterministically from each export name.

The Excire exports are retrieval hit lists rather than complete
classification tables. Each file contains the paths of the images returned for
one prompt under one distance setting, generally as a headerless list with one
path per line. An image may occur in several prompt exports when it is
retrieved by more than one query. Conversely, an image absent from an export
does not produce an explicit negative row in that file.

For each distance configuration, the eight hit lists were combined through a
set-union rule. An image was assigned a positive operational decision when it
was retrieved by at least one fixed prompt:

\begin{equation}
    \bigvee_{p \in \mathcal{P}}
    \operatorname{retrieved}(x,p)
    =
    \texttt{true}
    \quad\Longrightarrow\quad
    \texttt{weapon\_detected = true},
\end{equation}

where \(\mathcal{P}\) denotes the frozen set of eight prompts.

Images not retrieved by any prompt under the same distance configuration were
completed against the authoritative 11\,500-item bundle and assigned:

\begin{equation}
    \bigwedge_{p \in \mathcal{P}}
    \neg\operatorname{retrieved}(x,p)
    \quad\Longrightarrow\quad
    \texttt{weapon\_detected = false}.
\end{equation}

The resulting normalized prediction was therefore:

\begin{equation}
    \texttt{normalized\_prediction}
    =
    \begin{cases}
        \texttt{weapon},
        & \text{if at least one fixed prompt retrieved the image},\\
        \texttt{non\_weapon},
        & \text{otherwise}.
    \end{cases}
\end{equation}

This rule is an operational recoding of semantic retrieval membership. It does
not imply that \gls{excirefoto2025} internally performs binary
\texttt{weapon}/\texttt{non\_weapon} classification. Similarly, the distance
settings must not be interpreted as calibrated probabilities or as directly
comparable confidence thresholds.

The three distance settings were retained as separate system configurations
throughout normalization and metric computation. Their retrieval results were
not merged into one combined Excire decision. Each setting therefore produced
a complete table of 11\,500 normalized predictions, allowing the effect of the
retrieval configuration to be analyzed independently.

For auditability, the normalized records preserve both the union decision and
the individual prompt memberships. Each row includes:

\begin{itemize}
    \item the semantic distance limit;
    \item the complete frozen prompt set;
    \item the number of prompts that retrieved the image;
    \item the list of prompts producing a hit;
    \item one binary hit indicator for each of the eight prompts;
    \item the bundle identifier, hashes, sample type, experimental condition,
    fold, operational label, and source-image identifiers;
    \item the resulting \texttt{weapon\_detected} and normalized prediction
    fields.
\end{itemize}

This representation preserves distinctions that would be lost by retaining
only the final binary decision. For example, two images may both be normalized
as positive even though one was retrieved by a single prompt and the other by
several semantically related prompts.

The three frozen runs produced the prompt-level volumes reported in
Table~\ref{tab:implementation-excire-configuration}. These counts represent
retrieval records rather than unique images because the same image may appear
in multiple prompt hit lists. After union and bundle completion, every

and:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}

These artifacts provide the mapping among anonymized tool-input files,
cryptographic hashes, operational labels, folds, sample types, perturbation
conditions, source-image identifiers, and generated-image identifiers. Ground
truth is introduced only during this post-export stage and is not available to
the commercial tools during analysis.

The normalization pipeline processes four software families but retains the

resulting normalized system identifiers are:

\begin{itemize}
    \item \texttt{magnet\_axiom};
    \item \texttt{griffeye};
    \item \texttt{cellebrite\_inseyets};

    \item \texttt{excire\_foto\_2025\_d50};
    \item \texttt{excire\_foto\_2025\_d80}.
\end{itemize}

Each normalized configuration is evaluated against the same 11\,500-item
bundle. The canonical normalized population therefore contains:

\begin{equation}
    6\ \text{configurations}
    \times
    11\,500\ \text{bundle items}
    =
    69\,000\ \text{matched decisions}.
\end{equation}

\paragraph{Bundle indexing and record matching.}

When the bundle metadata is loaded, the implementation constructs three lookup
indexes:

\begin{enumerate}
    \item a \gls{sha256}-based index;
    \item an \gls{md5}-based index;
    \item an anonymized file-name index.
\end{enumerate}

For conventional row-oriented exports, each parsed software record is matched
according to the following priority:

\begin{equation}
    \gls{sha256}
    \succ
    \gls{md5}
    \succ
    \text{exact file name}
    \succ
    \text{file name embedded in an exported path or text field}.
\end{equation}

The matching method is preserved explicitly in the normalized record. This
allows later verification of whether an association was established through
the primary cryptographic identifier or through a fallback identifier exposed
by the software export.

Hash values are normalized before comparison by removing separators and
non-hexadecimal formatting characters. File-system paths are normalized to
their base file names before lookup so that differences between Windows and
repository-relative directory structures do not prevent association with the
blind bundle.

The \gls{excirefoto2025} workflow requires a distinct matching procedure
because its exports contain only the files retrieved by each semantic query.
The anonymized file names listed in the eight prompt-level hit lists are first
mapped to bundle items. The union of those hits is then completed against the
full bundle manifest, thereby producing an explicit decision for every image,
including those absent from all prompt exports.

    =
    \begin{cases}
        \texttt{weapon},
        & \text{if \texttt{weapon\_detected = true}},\\
        \texttt{non\_weapon},
        & \text{if \texttt{weapon\_detected = false}},\\
        \texttt{unknown},
        & \text{otherwise}.
    \end{cases}
\end{equation}

The \texttt{unknown} state prevents an unsupported or unrecognized exported
value from being silently interpreted as a negative result. All official
frozen configurations nevertheless produced an interpretable normalized
decision for every matched bundle item.

\paragraph{Common normalized schema.}

The normalized representation separates software-observable information from
the ground-truth and experimental metadata obtained from the bundle. Its
principal fields include:

\begin{itemize}
    \item \texttt{tool\_name}, \texttt{bundle\_id},
    \texttt{matched}, and \texttt{match\_method};
    \item \texttt{sample\_type}, \texttt{attack\_family},
    \texttt{attack\_name}, and \texttt{attack\_target\_model};
    \item \texttt{fold}, \texttt{final\_label}, and
    \texttt{source\_dataset};
    \item \texttt{original\_image\_id} and
    \texttt{generated\_image\_id};
    \item the anonymized input file name and available \gls{sha256} and
    \gls{md5} values;
    \item the original exported label, tag, classification, bookmark, or
    prompt-membership information;
    \item \texttt{weapon\_detected},
    \texttt{normalized\_prediction}, and
    \texttt{mapping\_reason};
    \item binary correctness, false-negative, and false-positive indicators
    when the ground-truth label is \texttt{weapon} or
    \texttt{non\_weapon}.
\end{itemize}

Tool-specific information is retained in additional fields rather than being
discarded after binary recoding. These fields include the original AXIOM tags,
Cellebrite classifications, Excire distance limit and per-prompt hit
indicators, and the primary and secondary Griffeye bookmarks.

The schema therefore supports cross-system comparison without erasing the
observable evidence from which each normalized decision was derived.

For records whose frozen ground-truth label is \texttt{ood}, the binary
correctness, false-negative, and false-positive fields are left undefined.
An \gls{ood} sample is not treated as either a positive or a negative
ground-truth instance. Its normalized \texttt{weapon\_detected} state is
preserved separately and is later used to compute the \gls{ood} weapon-flag
rate.

\paragraph{Deduplication and completeness.}

Some forensic exports may contain more than one record associated with the same
bundle item. The normalizer therefore supports deterministic consolidation to
one row per system configuration and bundle identifier.

When several matched rows refer to the same pair, the consolidated decision is
selected according to the following rule:

\begin{enumerate}
    \item if at least one row contains a positive decision, the consolidated
    result is positive;
    \item otherwise, if at least one row contains an explicit negative
    decision, the consolidated result is negative;
    \item otherwise, the consolidated result is \texttt{unknown}.
\end{enumerate}

The consolidation procedure retains the combined export-file references, row
numbers, observable labels, mapping reasons, and raw-row count. When numerical
confidence values are available, the maximum exported value is preserved;
however, no confidence value is fabricated for tools that do not expose one.

Unmatched records are excluded from the canonical prediction table because
they do not belong to the official forensic evaluation bundle. They remain
documented through the export audit and unmatched-record artifacts.

After tool-specific parsing and the preliminary exclusion of the 553
non-bundle Griffeye records, the normalization workspace contained 69\,329
candidate records. This population comprised the expected 69\,000 bundle-level
decisions and 329 unmatched Cellebrite report records. Excluding the latter
produced exactly 69\,000 matched normalized decisions:

\begin{equation}
    69\,329
    -
    329
    =
    69\,000.
\end{equation}

This final count corresponds to complete coverage of the 11\,500-item bundle
for all six normalized configurations. No matched bundle decision remained
uninterpretable after the frozen mappings were applied.

\subsection{Metric Computation and Evaluation Artifacts}
\label{subsec:implementation-metrics}

reconstructed from black-box software exports.

Proxy-model predictions and metrics were generated through:

\begin{center}
\codepath{evaluation/scripts/15_evaluate_proxy_models.py}
\end{center}

Commercial-tool metrics were generated as part of the normalization pipeline

\begin{center}
\codepath{evaluation/scripts/19_normalize_forensic_ai_tool_predictions.py}
\end{center}

Although the two pipelines process different observable information, they use
the same positive and negative classes:

\begin{equation}
    \text{positive class} = \texttt{weapon},
    \qquad
    \text{negative class} = \texttt{non\_weapon}.
\end{equation}

The \gls{ood} branch is handled separately and does not contribute to the

\paragraph{Proxy-model prediction generation.}

The proxy evaluation pipeline consumes:

\begin{itemize}
    \item the clean-fold manifest;
    \item the separate \gls{ood} manifest;
    \item the adversarial-generation manifests;
    \item the anti-forensic transformation manifest;
    \item the 15 fold-specific proxy-model checkpoints.
\end{itemize}

Each clean or perturbed binary sample is evaluated by the checkpoint associated
with its assigned fold. This ensures that the model used for prediction was
trained while excluding the fold containing the corresponding source image.

For each evaluated sample, the implementation records:

\begin{itemize}
    \item the evaluated architecture and fold-specific checkpoint;
    \item the clean, \gls{ood}, or perturbed sample type;
    \item the perturbation family, condition, and target model;
    \item the original and generated image identifiers;
    \item the assigned fold and operational label;
    \item the image path and actual \gls{sha256} and \gls{md5} values;
    \item the predicted class;
    \item the maximum predicted-class probability;
    \item the probabilities assigned to \texttt{weapon} and
    \texttt{non\_weapon};
    \item the probability assigned to the true label for binary samples;
    \item the correctness state and any evaluation error.
\end{itemize}

The complete prediction-level artifact is:

\begin{center}
\codepath{evaluation/proxy_models/proxy_model_predictions.csv}
\end{center}

procedure used elsewhere in the pipeline. The file hashes are recomputed, and
the corresponding fold-aware model adapter applies the architecture-specific
preprocessing defined in the model implementation.

\end{equation}

\begin{equation}

    \times
    3
    =
    3\,000
    \quad
    \text{clean prediction rows},
\end{equation}

and:

\begin{equation}

    \times

    =

    \quad

\end{equation}

\paragraph{Binary metric computation.}

For each binary evaluation group, the implementation derives the confusion
matrix using the fixed layout:

\begin{equation}
    \begin{bmatrix}
        \gls{tn} & \gls{fp} \\
        \gls{fn} & \gls{tp}
    \end{bmatrix}.
\end{equation}

The resulting metric records contain:

\begin{itemize}
    \item accuracy and balanced accuracy;
    \item class-specific precision, recall, and F1-score;
    \item macro-averaged precision, recall, and F1-score;
    \item \gls{tp}, \gls{tn}, \gls{fp}, and \gls{fn} counts;
    \item \gls{fpr} and \gls{fnr};
    \item misclassification rate;
    \item \texttt{weapon}-to-\texttt{non\_weapon} and
    \texttt{non\_weapon}-to-\texttt{weapon} error counts;
    \item mean predicted-class confidence.
\end{itemize}

The \gls{fpr} and \gls{fnr} are implemented as:

\begin{equation}
    \gls{fpr}
    =
    \frac{\gls{fp}}
         {\gls{fp}+\gls{tn}},
    \qquad
    \gls{fnr}
    =
    \frac{\gls{fn}}
         {\gls{fn}+\gls{tp}}.
\end{equation}

Clean proxy metrics are grouped by architecture. Adversarial metrics are
grouped by evaluated architecture, perturbation condition, and attack target
model. Anti-forensic metrics are grouped by evaluated architecture and
transformation condition.

The attack-target field is retained because the model-dependent adversarial
examples were generated against fold-aware EfficientNet-B0 checkpoints but
were subsequently evaluated on all three proxy architectures. This distinction
supports separate analysis of target-model vulnerability and cross-model
transfer behavior.

\paragraph{Clean-to-perturbed comparison.}

Each perturbed prediction is associated with its corresponding clean prediction
through the tuple:

\begin{center}
\texttt{evaluated\_model},
\quad
\texttt{evaluation\_fold},
\quad
\texttt{original\_image\_id}.
\end{center}

The prediction table is enriched with the clean prediction, clean correctness
state, clean class probabilities, clean confidence, and confidence difference
relative to the perturbed input.

For each model and perturbation condition, the comparative layer computes:

\begin{itemize}
    \item clean accuracy and perturbed accuracy;
    \item robust accuracy, defined as the perturbed accuracy;
    \item accuracy drop;
    \item clean and perturbed macro F1-scores;
    \item macro F1-score drop;
    \item attack success rate;
    \item induced-error count;
    \item mean confidence shift;
    \item directional error counts and rates.
\end{itemize}

An induced error occurs when the clean image is classified correctly but its
perturbed counterpart is classified incorrectly. The implemented attack
success rate is therefore:

\begin{equation}
    \text{attack success rate}
    =
    \frac{
        \text{number of clean-correct samples rendered incorrect}
    }{
        \text{number of clean-correct samples}
    }.
\end{equation}

This denominator differs from the complete number of evaluated samples because
images already misclassified in the clean condition cannot represent newly
induced errors.

The confidence shift is computed as:

\begin{equation}
    \Delta c
    =
    c_{\mathrm{perturbed}}
    -
    c_{\mathrm{clean}},
\end{equation}

and averaged within each model--condition group. The value refers to the
maximum predicted-class probability, not necessarily to the probability of the
ground-truth class.

\paragraph{Proxy-model \gls{ood} metrics.}

The \gls{ood} branch is summarized independently for each proxy architecture.
The resulting records contain:

\begin{itemize}
    \item the fold-aggregated number of predictions;
    \item the number and rate of predictions assigned to \texttt{weapon};
    \item the number of predictions assigned to \texttt{non\_weapon};
    \item the mean maximum predicted-class probability;
    \item the high-confidence threshold;
    \item the number and rate of predictions whose maximum probability meets
    or exceeds that threshold.
\end{itemize}

The frozen high-confidence threshold is:

\begin{equation}
    \tau_{\mathrm{high}}
    =
    0.90.
\end{equation}

The high-confidence count includes predictions assigned to either binary class.
It measures confident assignment of an \gls{ood} input to the closed-set task,
whereas the predicted-weapon rate measures the specific operational tendency
to flag \gls{ood} content as firearm-related.

\begin{enumerate}

\paragraph{Attribution processing and visual artifacts.}

For each target, the channel-wise attribution tensor is converted into a
two-dimensional map by summing the absolute attribution magnitudes across the
three input channels. The resulting map is min--max normalized to the interval
\([0,1]\).

Because absolute values are used, the visualizations represent attribution
magnitude rather than the direction of the contribution. They identify regions
to which the selected model output is sensitive along the baseline-to-input
path, but they do not distinguish positive evidence from negative evidence.

The implementation produces the following diagnostic assets for each case:

\begin{itemize}
    \item the resized RGB input image;
    \item a colorized attribution heatmap;
    \item an overlay combining the input and heatmap;
    \item a normalized grayscale attribution mask;
    \item a binary mask containing pixels at or above the selected attribution
    percentile;
    \item a side-by-side diagnostic comparison;
    \item a histogram of normalized attribution values.
\end{itemize}

The heatmap uses the \texttt{inferno} color map. The overlay combines the
resized input with the colorized heatmap using an attribution opacity of 0.45.
The binary high-attribution mask is computed from the 90th percentile of the
normalized map and therefore highlights approximately the highest-attribution
10\% of image locations.

The thesis retains four assets for each of the five selected cases:

\begin{enumerate}
    \item input image;
    \item standalone heatmap;
    \item heatmap overlay;
    \item top-10\% attribution mask.
\end{enumerate}

The resulting thesis-level visual corpus contains:

\begin{equation}
    5\ \text{cases}
    \times
    4\ \text{assets}
    =
    20\ \text{images}.
\end{equation}

\paragraph{Convergence diagnostics.}

The historical thesis images were generated with 32 integration steps. The
corresponding legacy convergence deltas are retained in the authoritative
selection manifest. Some of these values are large, particularly for selected
perturbed cases. The historical figures must therefore be interpreted as
qualitative diagnostic visualizations rather than as attributions for which a
strict numerical convergence threshold has been demonstrated.

The hardened entry point additionally supports adaptive convergence diagnostics.
Starting from the requested number of integration steps, the procedure can
double the integration resolution until the normalized convergence delta is at
most 0.05 or the maximum of 256 steps is reached. A regenerated case is marked
as \texttt{passed} only when the threshold is satisfied; otherwise, the state
\texttt{threshold\_not\_met} is retained.

This adaptive functionality was introduced after the historical 32-step assets
had been generated and was not used to produce the figures analyzed in this
thesis. It is therefore documented only as an available validation control. No
strict convergence claim is made for the retained historical assets, which are
used exclusively for qualitative diagnostic interpretation.

\section{Traceability, Integrity, and Reproducibility Controls}
\label{sec:implementation-traceability}
% ─────────────────────────────────────────────────────────────────────────────

Traceability, integrity, and controlled reproducibility were implemented as
cross-cutting properties of the complete experimental workflow rather than as
controls added only after evaluation. The resulting artifact links the frozen
dataset, deterministic partitions, proxy checkpoints, generated
perturbations, black-box inputs, normalized software outputs, metric tables,
explainability cases, and reporting assets through stable identifiers,
cryptographic digests, manifests, and version-controlled metadata.

The implementation distinguishes three related but non-equivalent objectives:

\begin{itemize}
    \item \emph{traceability}, defined as the ability to reconstruct the
    provenance and processing history of an experimental artifact;
    \item \emph{integrity}, defined as the ability to verify that an artifact
    has not changed relative to its authoritative recorded state;
    \item \emph{controlled reproducibility}, defined as the ability to inspect
    or rerun the workflow to the extent permitted by data-access restrictions,
    licensed-software requirements, and the available execution environment.
\end{itemize}

This distinction is necessary because public access to code and metadata does
not imply unrestricted redistribution of the source images or availability of
the proprietary software required to repeat the commercial-tool processing.

\paragraph{Stable identity and provenance chain.}

The pipeline assigns stable identifiers at successive processing stages.
Prepared source images receive an \texttt{image\_id}; generated perturbations
receive a \texttt{generated\_image\_id}; black-box inputs receive an anonymized
\texttt{bundle\_id}; and selected explainability cases receive a
\texttt{case\_id}. Model artifacts are identified through the combination of
architecture and held-out fold.

The resulting provenance chain can be represented as:

\begin{equation}
\begin{split}
    \texttt{image\_id}
    &\longrightarrow
    \texttt{generated\_image\_id}
    \longrightarrow
    \texttt{bundle\_id} \\
    &\longrightarrow
    \texttt{normalized\_prediction}
    \longrightarrow
    \texttt{metric\_row}
    \longrightarrow
    \texttt{reporting\_asset}.
\end{split}
\end{equation}

For clean and \gls{ood} samples, the original and generated identifiers may
coincide because no new image artifact is created. For adversarial and
anti-forensic samples, the generated identifier preserves the link to the
corresponding clean source image while distinguishing the perturbation
condition and, where applicable, the target proxy model.

The manifests retain repository-relative paths rather than relying on
machine-specific absolute locations. This allows artifacts generated on
different workstations to be associated with the same logical repository
structure. Run summaries and registries additionally preserve configurations,
creation timestamps, sample counts, fold assignments, and output locations.

\paragraph{Cryptographic integrity controls.}

\gls{sha256} is the primary integrity digest throughout the pipeline.
\gls{md5} is retained only as an auxiliary compatibility identifier because
some commercial forensic exports expose MD5-oriented fields or matching
workflows. It is not treated as the primary integrity mechanism.

Per-file hashes are recorded at the main transformation boundaries, including:

\begin{itemize}
    \item prepared and frozen source images;
    \item deterministic clean and \gls{ood} partitions;
    \item adversarial and anti-forensic outputs;
    \item blind and structured bundle copies;
    \item proxy-model checkpoints;
    \item selected explainability inputs and the corresponding fold-specific checkpoints;
    \item sanitized commercial-tool extracts and canonical metric artifacts.
\end{itemize}

Thesis-level explainability outputs are validated through their canonical
manifest paths, selection metadata, and reporting-asset audits rather than
being treated as independently hash-authenticated model artifacts.

Where an artifact is copied between stages, the output hash is recomputed and
compared with the authoritative value from the originating manifest. A mismatch
causes the relevant script to terminate rather than silently accepting a
different file.

The checkpoint digests stored in:

\begin{center}
\codepath{models/model_registry.json}
\end{center}

bind every proxy architecture and fold to the corresponding serialized model
artifact. These values are checked before model-dependent adversarial
generation and by the hardened explainability entry point.

Archive-level integrity is maintained separately from per-file integrity. The
authoritative controlled-archive digests are stored in:

\begin{center}
\codepath{docs/artifact/CONTROLLED_ARTIFACT_CHECKSUMS.sha256}
\end{center}

The complete-archive digest authenticates the downloaded ZIP file, whereas:

\begin{center}
\codepath{datasets/forensic_evaluation_bundle/metadata/bundle_hashes_sha256.csv}
\end{center}

authenticates each of the 11\,500 restored blind inputs individually. The
distinction prevents a valid archive-level digest from replacing the need to
verify the expected file population after extraction.

\paragraph{Deterministic configuration controls.}

A fixed seed of 42 is used for the principal stochastic procedures, including
fold construction, internal training--validation partitioning, and
image-specific randomized search initialization where applicable. The seed is
recorded in the corresponding configuration and summary artifacts.

The use of a fixed seed supports repeatability of the logical partitions and
algorithmic initialization. It does not imply that every numerical result is
guaranteed to be bit-identical across different operating systems, hardware
architectures, library versions, or CPU and GPU implementations. PyTorch and
cuDNN deterministic options reduce nondeterministic behavior where supported,
but the execution environment remains part of the reproducibility boundary.

The frozen configurations also specify:

\begin{itemize}
    \item accepted labels and expected class counts;
    \item the five clean folds and independent \gls{ood} branch;
    \item preprocessing and normalization parameters;
    \item training hyperparameters;
    \item perturbation parameters;
    \item model and checkpoint associations;
    \item commercial-tool versions and observable output mappings;
    \item metric definitions and confusion-matrix layout;
    \item explainability targets, baseline, integration steps, and selection
    criteria.
\end{itemize}

These values are stored in machine-readable CSV or JSON artifacts rather than
being represented only in narrative documentation.

\paragraph{Overwrite and rerun controls.}

The main generation and evaluation scripts implement fail-visible output
guards. Existing canonical outputs are not silently replaced. A rebuild
generally requires the explicit \texttt{--force} option, which removes or
replaces only the output scope associated with the selected run.

This policy reduces the risk of combining artifacts generated from different
configurations or of overwriting a frozen result with a partial diagnostic
execution. Partial experiments and exploratory runs must use separate output
locations and must not replace the canonical manifests, predictions, or metric
tables.

An explicit forced rebuild does not by itself establish equivalence with the
frozen artifact. The regenerated files must still satisfy the expected counts,
identifier constraints, hashes, and downstream validation procedures.

\paragraph{Audit summaries and machine-readable invariants.}

Each major stage produces both sample-level records and a run-level summary.
The summary files record the input manifests, parameters, output paths,
expected and actual counts, validation results, and creation metadata. This
design allows structural checks to be performed without reopening every image
or manually inspecting every prediction.

The principal invariants include:

\begin{itemize}
    \item 1\,500 records in the frozen dataset;
    \item 1\,000 binary and 500 \gls{ood} samples;
    \item five folds containing 200 binary images each;
    \item 15 fold-aware proxy checkpoints;
    \item 5\,000 adversarial and 5\,000 anti-forensic artifacts;
    \item 11\,500 unique forensic evaluation bundle items;
    \item 40\,500 proxy-model prediction rows;
    \item 69\,000 canonical sanitized commercial-tool decisions;
    \item 186 commercial-tool metric rows;
    \item five authoritative thesis-level explainability cases and 20 associated
    thesis assets.
\end{itemize}

These counts are implementation invariants and completeness checks. Their
presence does not establish model robustness; the quantitative behavior of the
evaluated systems is analyzed separately in
Chapter~\ref{chap:results}.

\paragraph{Environment and security boundary.}

The pipeline was developed using Python virtual environments across Windows and
Linux/Kali contexts, with CPU or CUDA-enabled execution depending on the
computational stage. Commercial evaluation additionally requires compatible
licensed software and a suitable workstation.

The repository records the dependency specification and operational setup but
does not claim to reproduce a byte-identical operating-system environment.
Exact usernames, credentials, API keys, signed download URLs, commercial
license information, session data, and unnecessary local absolute paths are
excluded.

The public branch also excludes:

\begin{itemize}
    \item unrestricted copies of the image corpora;
    \item complete raw commercial exports;
    \item proprietary case databases;
    \item evidence-related material not required for the experimental record;
    \item private or temporary artifact-access URLs;
    \item generated LaTeX auxiliary files.
\end{itemize}

This minimization preserves the information required to audit the experimental
claims while reducing disclosure of unrelated sensitive or proprietary
material.

\paragraph{Version control and artifact freezing.}

Source code, manifests, registries, sanitized decisions, metric tables,
documentation, and thesis sources are maintained through Git version control.
Large proxy checkpoints are managed through Git LFS while their
\gls{sha256} values remain recorded in the model registry.

The repository policy treats the thesis artifact as a versioned frozen object.
Substantive changes to data, perturbations, checkpoints, normalized decisions,
metrics, or thesis conclusions require a new versioned release rather than
silent replacement of the existing frozen state. Documentation corrections,
security fixes, and non-substantive archival improvements must remain clearly
distinguishable from changes to the experimental evidence.

Taken together, these controls provide a traceable connection between the
implemented protocol and the results reported in the following chapter. They
do not eliminate the limitations associated with controlled data access,
hardware and software variation, human review, or proprietary black-box
systems. They instead make those boundaries explicit and preserve the
information required to audit the evaluation within them.
